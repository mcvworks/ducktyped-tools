How SSL/TLS Handshakes Work

Last updated: March 8, 2026

Every HTTPS connection begins with a TLS handshake -- a carefully orchestrated exchange where the client and server agree on encryption parameters, verify the server's identity, and establish a shared secret key. This guide walks through the handshake process step by step for both TLS 1.2 and TLS 1.3.

What Happens Before the Handshake

Before the TLS handshake can begin, the client must establish a TCP connection to the server. This requires a TCP three-way handshake (SYN, SYN-ACK, ACK), which takes one round trip. The TLS handshake then runs on top of this TCP connection. This means an HTTPS connection requires at least two round trips before any application data is exchanged (one for TCP, one or two for TLS).

TLS 1.2 Handshake (2-RTT)

The TLS 1.2 handshake requires two full round trips between client and server:

Round Trip 1

  1. ClientHello -- the client sends:
    • Maximum TLS version supported
    • A 32-byte client random value
    • A list of supported cipher suites (e.g., TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384)
    • Supported compression methods (always null in practice)
    • Extensions (including SNI -- Server Name Indication -- which tells the server which hostname the client wants, enabling virtual hosting)
  2. ServerHello -- the server responds with:
    • The chosen TLS version
    • A 32-byte server random value
    • The selected cipher suite
    • The server's certificate (containing its public key)
    • Optionally, a ServerKeyExchange message with the server's ephemeral ECDHE public key (signed with the server's private key to prove authenticity)
    • A ServerHelloDone message

Round Trip 2

  1. Client verification and key exchange -- the client:
    • Verifies the server's certificate chain up to a trusted root CA
    • Generates its own ephemeral ECDHE key pair
    • Sends the ClientKeyExchange message with its public ECDHE key
    • Both sides independently compute the pre-master secret from the ECDHE key exchange
    • Derives the master secret from the pre-master secret, client random, and server random
    • Derives session keys from the master secret
    • Sends a ChangeCipherSpec message indicating all future messages will be encrypted
    • Sends a Finished message (encrypted with the new keys) containing a hash of all handshake messages
  2. Server confirmation -- the server:
    • Independently derives the same session keys
    • Sends its own ChangeCipherSpec and Finished messages

After both Finished messages are verified, the handshake is complete and encrypted application data can flow.

TLS 1.3 Handshake (1-RTT)

TLS 1.3 (RFC 8446, finalized in 2018) dramatically simplified the handshake, reducing it to a single round trip:

The Single Round Trip

  1. ClientHello -- the client sends everything needed upfront:
    • Supported TLS 1.3 cipher suites (only five are defined, all secure)
    • A list of supported groups (key exchange curves like X25519 or P-256)
    • Key shares -- the client speculatively generates ECDHE key pairs for its preferred groups and includes the public keys
    • Client random and extensions
  2. ServerHello + EncryptedExtensions + Certificate + Finished -- the server responds with everything in one message:
    • Selected cipher suite and key share
    • The server computes the shared secret immediately
    • Server certificate (now encrypted, unlike TLS 1.2)
    • Certificate verification signature
    • Finished message
  3. Client Finished -- the client verifies the server's certificate and sends its Finished message. Application data can be sent alongside this message.

Key Improvements in TLS 1.3

  • 1-RTT by default -- the handshake completes in one round trip instead of two, reducing latency.
  • Mandatory forward secrecy -- all cipher suites use ephemeral key exchange (ECDHE). Static RSA key exchange is removed entirely.
  • Encrypted certificates -- the server's certificate is sent encrypted, preventing passive observers from seeing which site is being accessed (SNI is still visible, though Encrypted Client Hello addresses this).
  • Simplified cipher suites -- only five cipher suites are defined, all using AEAD encryption (AES-GCM or ChaCha20-Poly1305). Legacy algorithms like RC4, 3DES, CBC modes, and SHA-1 are gone.
  • No renegotiation -- TLS 1.3 removes renegotiation, eliminating an entire class of attacks.

0-RTT Resumption

TLS 1.3 introduces 0-RTT (zero round-trip time) resumption for clients that have previously connected to a server. After an initial handshake, the server issues a session ticket. On the next connection, the client can use this ticket to send encrypted application data in the very first message -- before the handshake even completes.

This is ideal for latency-sensitive applications, but it comes with a caveat: 0-RTT data can be replayed by an attacker who captures the initial message. For this reason, 0-RTT should only be used for idempotent operations (like GET requests), never for state-changing operations (like POST requests or payments).

Cipher Suites Explained

A cipher suite defines the combination of algorithms used during and after the handshake. In TLS 1.2, a cipher suite name describes four components:

TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
 |     |     |        |       |      |
 |     |     |        |       |      Hash for PRF
 |     |     |        |       Mode (AEAD)
 |     |     |        Symmetric cipher + key size
 |     |     Authentication (certificate type)
 |     Key exchange mechanism
 Protocol

In TLS 1.3, cipher suite names are simpler because key exchange and authentication are negotiated separately:

TLS_AES_256_GCM_SHA384
TLS_CHACHA20_POLY1305_SHA256

Common Handshake Failures

  • Certificate verification failed -- the server's certificate is expired, self-signed, or issued for a different domain.
  • No shared cipher suite -- the client and server do not support any common cipher suites. Often caused by outdated clients or overly restrictive server configurations.
  • Protocol version mismatch -- the server requires TLS 1.2+ but the client only supports TLS 1.0/1.1 (or vice versa).
  • SNI mismatch -- the server cannot identify which certificate to present because the client did not send the SNI extension or sent the wrong hostname.
  • Firewall or middleware interference -- deep packet inspection devices, corporate proxies, or misconfigured firewalls can interfere with the TLS handshake.
