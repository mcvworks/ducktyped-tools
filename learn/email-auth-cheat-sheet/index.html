Email Authentication Cheat Sheet: SPF, DKIM, DMARC

Last updated: April 5, 2026

Everything you need to configure SPF, DKIM, and DMARC correctly — all the tags, mechanisms, policy options, and copy-paste record examples in one place. All three records live in DNS as TXT records; verify them after publishing with the DNS Record Checker.

How the Three Work Together

  • SPF answers: "Is this server allowed to send mail for this domain?"
  • DKIM answers: "Was this message signed by the domain, and has it been altered in transit?"
  • DMARC answers: "What should receivers do when SPF or DKIM fails, and who gets the reports?"

SPF alone is not enough — it breaks on forwarding. DKIM alone is not enough — it doesn't cover the envelope-from. DMARC glues the two together and adds reporting. Modern mailbox providers (Gmail, Outlook, Yahoo) require all three for bulk senders.

SPF — Sender Policy Framework

Record Location

TXT record at the apex (or subdomain) you send from: example.com. Only one SPF record per name.

Basic Syntax

v=spf1 <mechanisms> <all-qualifier>

Mechanisms

  • ip4:192.0.2.1 — authorize a specific IPv4 address or CIDR range (ip4:192.0.2.0/24).
  • ip6:2001:db8::1 — authorize an IPv6 address or range.
  • a — authorize the A/AAAA records of the sending domain.
  • a:mail.example.com — authorize a specific hostname's A records.
  • mx — authorize the domain's MX record hosts.
  • mx:example.com — authorize another domain's MX hosts.
  • include:_spf.google.com — delegate to another domain's SPF record (recursive).
  • exists:example.com — pass if any A record exists for the given name.
  • redirect=example.com — replace this SPF with another domain's SPF.

All Qualifiers

  • +all — never use. Authorizes every server on the internet.
  • ~all — softfail. Receivers may accept but flag the message. Safe starting point.
  • -all — hardfail. Receivers should reject. Use once you're confident.
  • ?all — neutral. Same as having no SPF at all. Pointless.

Examples

# Google Workspace only
v=spf1 include:_spf.google.com ~all

# Google Workspace + SendGrid + Mailgun
v=spf1 include:_spf.google.com include:sendgrid.net include:mailgun.org ~all

# Microsoft 365 + custom server
v=spf1 ip4:203.0.113.10 include:spf.protection.outlook.com -all

# Reject all mail (parked domain)
v=spf1 -all

SPF Gotchas

  • 10-lookup limit — SPF allows a maximum of 10 DNS lookups during evaluation (each include, a, mx, exists, redirect counts). Exceeding it causes a permerror. Use ip4:/ip6: to flatten if you hit the limit.
  • Only one SPF record per domain — multiple records cause permerror. Merge them.
  • SPF breaks on forwarding — messages forwarded to another address will fail SPF at the second hop. This is why DKIM exists.
  • Max 512 characters per TXT string — split long records into multiple quoted strings that DNS concatenates.

DKIM — DomainKeys Identified Mail

Record Location

TXT record at <selector>._domainkey.example.com. A selector is a short label you choose (e.g., s1, google, mail) that lets you rotate keys without downtime.

Basic Syntax

v=DKIM1; k=rsa; p=<base64 public key>

Tags

  • v=DKIM1 — version (required, always DKIM1).
  • k=rsa — key type. RSA is standard; some providers support ed25519.
  • p=<base64> — the public key. Empty p= marks the key as revoked.
  • h=sha256 — allowed hash algorithms (optional, default is all).
  • s=email — service type (optional).
  • t=y — testing mode flag (recommended during initial setup).
  • t=s — prevents the key being used for subdomains.
  • n=notes — arbitrary notes for administrators.

Example

# Record name: s1._domainkey.example.com
v=DKIM1; k=rsa; p=MIGfMA0GCSqGSIb3DQEBAQUAA4GNADCBiQKBgQC7...IDAQAB

DKIM Gotchas

  • 2048-bit RSA keys exceed 255 characters — split into multiple quoted strings: "v=DKIM1; k=rsa; " "p=MIGfMA0G..."
  • Key length — 1024-bit is deprecated but still widely accepted; 2048-bit is the current standard.
  • Selector matches the header — the s= tag in the message's DKIM-Signature header must match the selector in DNS.
  • Relaxed vs simple canonicalization — set by the sender. Most senders use relaxed/relaxed which tolerates minor whitespace changes.
  • Multiple selectors are fine — useful for key rotation and for authorizing multiple services.

DMARC — Domain-based Message Authentication

Record Location

TXT record at _dmarc.example.com. Exactly one DMARC record per domain.

Basic Syntax

v=DMARC1; p=<policy>; rua=mailto:reports@example.com

Required Tags

  • v=DMARC1 — version (required, always DMARC1, must be first).
  • p=none — policy for the domain itself (required).

Policies

  • p=none — monitor only. Receivers do not change handling based on DMARC. Start here.
  • p=quarantine — failing messages should go to spam/junk.
  • p=reject — failing messages should be rejected outright. Goal state.

Optional Tags

  • sp=none|quarantine|reject — policy for subdomains (defaults to p value).
  • pct=25 — percentage of messages to apply the policy to (0–100). Useful for gradual rollout.
  • rua=mailto:aggregate@example.com — aggregate (daily) reports destination.
  • ruf=mailto:forensic@example.com — forensic (per-failure) reports destination. Rarely used; privacy concerns.
  • adkim=r|s — DKIM alignment: relaxed (default) or strict.
  • aspf=r|s — SPF alignment: relaxed (default) or strict.
  • fo=0|1|d|s — forensic report options: 0 (both fail), 1 (either fails), d (DKIM fails), s (SPF fails).
  • ri=86400 — report interval in seconds (default 86400 = daily).
  • rf=afrf — report format (only afrf is standard).

Examples

# Monitoring only — the starting point
v=DMARC1; p=none; rua=mailto:dmarc@example.com

# Partial quarantine rollout (25%)
v=DMARC1; p=quarantine; pct=25; rua=mailto:dmarc@example.com

# Full quarantine, relaxed alignment
v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com

# Strict reject (goal state)
v=DMARC1; p=reject; sp=reject; adkim=s; aspf=s; rua=mailto:dmarc@example.com; ruf=mailto:forensic@example.com

Recommended Rollout

  1. Week 1: publish p=none with rua. Collect reports.
  2. Week 2–3: identify legitimate senders failing SPF/DKIM. Fix them (add to SPF, set up DKIM).
  3. Week 4: move to p=quarantine; pct=25.
  4. Week 5–6: increase pct to 50, then 100.
  5. Week 7+: move to p=reject.

DMARC Alignment Explained

For DMARC to pass, at least one of SPF or DKIM must align with the From header domain:

  • SPF alignment — the Return-Path domain matches the From domain.
  • DKIM alignment — the d= tag in the DKIM signature matches the From domain.
  • Relaxed alignment (default) — allows subdomain matches (mail.example.com aligns with example.com).
  • Strict alignment — requires exact match.

Quick Verification

  • Query TXT records with the DNS Record Checker to confirm your SPF, DKIM, and DMARC records are published.
  • Send a test message to a mailbox you control and inspect the headers with the Email Header Analyzer. Look for Authentication-Results lines showing spf=pass, dkim=pass, and dmarc=pass.
  • If something fails, see Email Not Delivering: diagnostic guide.
