What Is DKIM (DomainKeys Identified Mail)?

Last updated: March 8, 2026

DKIM is an email authentication method that uses cryptographic signatures to verify that an email was sent by an authorized server and that the message has not been modified in transit. It works by signing outgoing messages with a private key and publishing the corresponding public key in DNS.

How DKIM Works

DKIM operates on a simple principle: the sending server signs the email, and the receiving server verifies the signature. The process has two phases:

Signing (Sender Side)

  1. The sending mail server selects specific email headers (such as From, To, Subject, Date) and the message body.
  2. It creates a hash (a fixed-length digest) of the selected headers and body content.
  3. The hash is encrypted using the domain's private key, producing a digital signature.
  4. The signature, along with metadata about the signing process, is added to the email as a DKIM-Signature header.

Verification (Receiver Side)

  1. The receiving server reads the DKIM-Signature header to identify the signing domain (d=) and selector (s=).
  2. It constructs a DNS query for selector._domainkey.domain.com to retrieve the public key.
  3. Using the public key, it decrypts the signature to obtain the original hash.
  4. It independently computes a hash of the same headers and body.
  5. If the two hashes match, the signature is valid -- the email is authenticated and unmodified.

The DKIM-Signature Header

A DKIM-Signature header looks like this:

DKIM-Signature: v=1; a=rsa-sha256; d=example.com; s=selector1;
    c=relaxed/relaxed; q=dns/txt; h=from:to:subject:date:message-id;
    bh=abcdef123456...=; b=ghijkl789012...=

Key fields:

  • v=1 -- DKIM version (always 1).
  • a=rsa-sha256 -- the signing algorithm. RSA-SHA256 is the standard; Ed25519 is an emerging alternative.
  • d=example.com -- the signing domain. This is the domain claiming responsibility for the message.
  • s=selector1 -- the selector used to locate the public key in DNS.
  • c=relaxed/relaxed -- canonicalization algorithm for headers/body. "Relaxed" is tolerant of minor formatting changes; "simple" requires exact matches.
  • h=from:to:subject:date:message-id -- the list of headers included in the signature.
  • bh=... -- the hash of the message body.
  • b=... -- the actual signature (encrypted hash of the headers).

DKIM Selectors and DNS Records

A selector is a label that identifies which DKIM key to use. The public key is published as a DNS TXT record at:

selector._domainkey.example.com  TXT  "v=DKIM1; k=rsa; p=MIGfMA0GCS..."

Selectors serve several purposes:

  • Key rotation -- you can publish a new key with a new selector while the old one remains active, allowing a gradual transition.
  • Multiple services -- different email services (e.g., Google Workspace, SendGrid, Mailchimp) each use their own selector, so they can sign with different keys without conflicting.
  • Key management -- selectors let you identify which system signed a particular message.

The DNS record fields:

  • v=DKIM1 -- DKIM version identifier.
  • k=rsa -- key type (RSA is standard; Ed25519 is the alternative).
  • p=... -- the public key in Base64 encoding. An empty p= value means the key has been revoked.

Common DKIM Issues

Signature Broken by Mailing Lists

Mailing lists (like Google Groups or Mailman) often modify messages by adding footers, changing the Subject line, or rewriting the From header. Any modification to signed content invalidates the DKIM signature. This is one of the most common causes of DKIM failures and is why DMARC policies should account for mailing list behavior.

Missing or Incorrect DNS Record

If the public key DNS record does not exist at the expected location, or if it contains an incorrect or malformed key, DKIM verification fails. Always verify that the DNS record matches the selector and domain used by your mail server.

Key Rotation Without DNS Update

When rotating DKIM keys, the new private key must be deployed on the mail server and the corresponding new public key must be published in DNS before the old key is removed. If the old DNS record is deleted before all in-flight messages are delivered, some messages signed with the old key will fail verification.

RSA Key Size Too Small

DKIM keys should be at least 1024 bits, and 2048 bits is recommended. Some older configurations still use 512-bit keys, which are considered cryptographically weak and may be rejected by receiving servers. Note that 2048-bit keys may need to be split across multiple DNS TXT strings due to the 255-character limit per DNS string.

DKIM and Email Authentication

DKIM works alongside SPF and DMARC to form a comprehensive email authentication framework:

  • SPF verifies the sending server's IP address is authorized.
  • DKIM verifies the message integrity and authenticity via cryptographic signatures.
  • DMARC ties SPF and DKIM together with domain alignment rules and specifies what to do when authentication fails.

DKIM is particularly valuable because it survives email forwarding -- unlike SPF, which breaks when a message is forwarded through an intermediate server. The signature travels with the message regardless of which servers handle it, as long as the message content is not modified.
