Base32 Encoding Explained

Last updated: June 11, 2026

Understand how Base32 represents binary data with just 32 characters, how it differs from Base64, what RFC 4648 specifies, and why TOTP/2FA secrets and DNS-based systems depend on it.

What Is Base32?

Base32 is a binary-to-text encoding that represents arbitrary bytes using only 32 ASCII characters: the uppercase letters A–Z and the digits 2–7. Because 32 = 25, each output character carries exactly 5 bits of the original data.

The encoder works on the raw bit stream. It concatenates the input bytes into one long sequence of bits, slices that sequence into 5-bit groups, and maps each group (a number from 0 to 31) to a character in the alphabet. Index 0 is A, index 25 is Z, index 26 is 2, and index 31 is 7. If the final group has fewer than 5 bits, it is padded with zero bits, and the encoded output is then padded with = characters until its length is a multiple of 8.

Why such a restricted alphabet? Because it deliberately excludes everything that causes trouble in the real world: lowercase letters (so case changes are harmless), the digits 0, 1, and 8 (easily confused with O, I/l, and B), and all punctuation. The result is an encoding that survives case-folding systems, handwriting, and being read out loud over the phone.

Base32 vs Base64

Base64 is the better-known sibling. It uses 64 characters (A–Z, a–z, 0–9, +, /), so each character carries 6 bits instead of 5. Here is the same string in both encodings:

Input:   Hello, World!          (13 bytes)
Base64:  SGVsbG8sIFdvcmxkIQ==   (20 chars, case-sensitive)
Base32:  JBSWY3DPFQQFO33SNRSCC=== (24 chars, case-insensitive)

The practical differences come down to three things:

  • Alphabet. Base64 mixes upper and lower case and includes the symbols + and / (or - and _ in the URL-safe variant). Base32 uses uppercase letters and six digits only — no symbols, no lowercase, no look-alike characters.
  • Size. Base64 inflates data by roughly 33% (4 output chars per 3 input bytes). Base32 inflates it by 60% (8 output chars per 5 input bytes). If raw size is the only concern, Base64 wins.
  • Case-insensitivity. This is Base32's killer feature. JBSWY3DP and jbswy3dp decode to the same bytes — decoders simply uppercase the input first. Base64 has no such tolerance: SGVsbG8= and sgvsbg8= are entirely different values, and a single case-folding proxy, file system, or careless copy-paste corrupts the data permanently.

Padding works the same way in both: = characters fill the output to a block boundary (4 characters for Base64, 8 for Base32). Base32 needs more of it — the valid pad lengths are 0, 1, 3, 4, or 6 = signs. Many real-world systems (TOTP secrets in particular) drop the padding entirely, and most decoders accept unpadded input, but strict RFC 4648 decoders do not, which is a common source of "invalid input" errors.

RFC 4648 and the base32hex Variant

Both Base32 and Base64 are formally specified in RFC 4648 ("The Base16, Base32, and Base64 Data Encodings"). The RFC actually defines two 32-character encodings:

  • base32 — the standard alphabet A–Z, 2–7 described above.
  • base32hex — an "extended hex" alphabet: 0–9 followed by A–V.

The two are not interchangeable — the same bytes produce completely different strings:

Input:      foobar
base32:     MZXW6YTBOI======
base32hex:  CPNMUOJ1E8======
Base64:     Zm9vYmFy

Why does base32hex exist? Because it preserves sort order. In base32hex, the character that represents value 0 (0) sorts before the character for value 1 (1), and so on through V for 31. That means encoded strings compare in exactly the same order as the raw bytes they encode. Standard base32 does not have this property (its 2, representing value 26, sorts before A, representing value 0). DNSSEC's NSEC3 records use base32hex precisely because DNS needs hashed names in canonical sorted order.

If a decode produces garbage even though the string "looks like Base32," check whether the source system used the hex variant — or a third-party alphabet such as Crockford Base32, a popular non-RFC variant used for human-readable IDs (ULIDs) that excludes I, L, O, and U.

Why TOTP and 2FA Secrets Use Base32

If you have ever set up two-factor authentication manually, the secret key you typed into your authenticator app — something like JBSW Y3DP EHPK 3PXP — was Base32. The otpauth:// URI embedded in the QR code carries the same value:

otpauth://totp/Example:alice@example.com?secret=JBSWY3DPEHPK3PXP&issuer=Example

The TOTP shared secret is raw random bytes used as an HMAC key, and it has to survive the most hostile transport channel of all: a human. Base32 is ideal for that job because:

  • Mistyping case is impossible — the alphabet has no lowercase letters, and decoders accept either case anyway.
  • There are no ambiguous glyphs. A user squinting at a tiny phone screen never has to decide between 0 and O or 1 and l.
  • The output is plain alphanumeric text, so it can be grouped in blocks of four, printed on recovery sheets, and read aloud to support staff without escaping issues.

Note the convention: authenticator secrets are almost always shown without padding, and most TOTP libraries also ignore spaces and case when decoding. If you are implementing TOTP yourself, decode leniently (strip whitespace, uppercase, re-add or ignore padding) before handing the bytes to HMAC-SHA1.

DNS-Safe Encoding and Other Case-Insensitive Systems

DNS is the textbook case for Base32. Hostnames are case-insensitive by specification, and resolvers may legally change case in transit (some randomize it as a security measure, known as 0x20 encoding). Encoding binary data into a DNS label with Base64 would silently corrupt it; Base32 is immune. That is why you see it in:

  • DNSSEC NSEC3 — hashed owner names encoded with base32hex, as described above.
  • Tor onion services — v3 .onion addresses are 56 Base32 characters encoding the service's public key.
  • DNS tunneling and verification records — any scheme that smuggles binary data through hostnames.

The same logic applies to other case-mangling environments: Windows and macOS file systems are case-insensitive by default, so cache file names derived from binary hashes are safer in Base32. License keys, gift-card codes, and ticket numbers use Base32 (often the Crockford variant) for the same human-friendly reasons as TOTP secrets.

So when should you choose which? A simple rule: if the value will only ever travel between machines through case-preserving channels (JSON bodies, HTTP headers, databases), use Base64 and save the bytes. If the value will pass through DNS, a file name, or a human — eyes, voice, or keyboard — use Base32.
