What Is HTTP 502 Bad Gateway?

Last updated: March 8, 2026

HTTP 502 Bad Gateway is a server error indicating that a gateway or proxy server received an invalid response from an upstream server. It is one of the most common infrastructure errors on the web, and understanding its mechanics helps diagnose where the problem lies.

Understanding the Gateway Model

Modern web architecture rarely involves a single server. Instead, requests pass through multiple layers:

  1. Client (your browser) sends a request.
  2. Edge/CDN (e.g., Cloudflare, CloudFront) receives the request first.
  3. Reverse proxy/load balancer (e.g., Nginx, HAProxy) routes the request to the appropriate backend.
  4. Application server (e.g., Node.js, Python/Django, PHP-FPM) processes the request and generates a response.

A 502 error occurs at any intermediary layer (the "gateway") when it cannot get a valid response from the next server in the chain (the "upstream"). The error tells you that the gateway is working, but something behind it is not.

Common Causes

Backend Server Crashed or Stopped

The most straightforward cause: the application server has crashed, been stopped, or failed to start. The reverse proxy tries to forward the request but gets a connection refused error. This commonly happens after a failed deployment, an out-of-memory kill, or a process manager (like PM2 or systemd) failing to restart the application.

Backend Server Overloaded

When the application server is overwhelmed with requests, it may close connections prematurely or return malformed responses. The reverse proxy interprets this as an invalid response and returns 502. This often accompanies traffic spikes, resource exhaustion, or database connection pool saturation.

Network Issues Between Gateway and Backend

If the gateway and backend are on different machines (or different availability zones), network issues between them can cause 502s. Firewall rule changes, security group modifications, DNS resolution failures for the upstream hostname, or physical network problems can all prevent the gateway from reaching the backend.

Upstream Timeout (Partial Response)

Sometimes the backend starts sending a response but takes too long to complete it. The gateway may interpret a partial or prematurely closed response as invalid and return 502. This is a subtle distinction from 504 (Gateway Timeout), which occurs when the gateway gets no response at all within the timeout window.

CGI/FastCGI/PHP-FPM Configuration Issues

For PHP applications using Nginx + PHP-FPM, 502 errors are common when PHP-FPM is not running, the socket path is incorrect, the PHP-FPM pool has exhausted its worker processes, or PHP scripts hit the max_execution_time limit.

SSL/TLS Misconfiguration Between Gateway and Backend

If the reverse proxy is configured to connect to the backend over HTTPS but the backend's certificate is invalid, expired, or uses an untrusted CA, the TLS handshake fails and the gateway returns 502. This is common in microservice architectures with mutual TLS (mTLS).

502 vs. Other 5xx Errors

  • 500 Internal Server Error -- the application itself encountered an error (unhandled exception, bug in code). The response comes from the application, not the gateway.
  • 502 Bad Gateway -- the gateway could not get a valid response from the upstream. The problem is in the communication between gateway and backend.
  • 503 Service Unavailable -- the server is temporarily unable to handle requests, often due to maintenance or capacity limits. Usually returned intentionally.
  • 504 Gateway Timeout -- the gateway did not receive any response within its timeout period. The upstream is too slow rather than returning an invalid response.

Diagnosing 502 Errors

  1. Check if the backend is running -- verify the application process is alive using systemctl status, pm2 status, or docker ps.
  2. Check gateway error logs -- Nginx logs (/var/log/nginx/error.log) will show the specific upstream error (connection refused, connection reset, invalid header).
  3. Test the backend directly -- bypass the reverse proxy and send a request directly to the backend server's port to see if it responds.
  4. Check resource usage -- monitor CPU, memory, and disk I/O on the backend server. Out-of-memory conditions are a frequent cause of backend crashes.
  5. Review recent changes -- deployments, configuration changes, and infrastructure updates are the most common triggers.

CDN-Specific 502 Errors

When using a CDN like Cloudflare, a 502 error can originate from Cloudflare itself or from your origin server. Cloudflare distinguishes between these with its error page:

  • Cloudflare 502 (gray header) -- Cloudflare could not reach your origin server at all.
  • Origin 502 (orange header) -- Cloudflare reached your origin, but your origin's reverse proxy returned 502.

Check the HTTP response headers for server: cloudflare and the cf-ray header to identify Cloudflare-related 502s.
