GitHub Webhook Signature Verification

Last updated: July 3, 2026

GitHub signs every webhook it sends with an HMAC-SHA256 of the raw payload, keyed by a secret only you and GitHub know, and delivers it in the X-Hub-Signature-256 header. Verifying it proves the delivery is genuinely from GitHub and was not forged. This guide shows the header format, working verification in Node and Python, why SHA-256 beats the legacy SHA-1 header, and the handful of mistakes behind almost every signature mismatch. For the Stripe equivalent, see Stripe Webhook Signature Verification; for webhooks in general, the Webhooks Explained guide.

The X-Hub-Signature-256 Header

A GitHub webhook delivery carries several relevant headers:

POST /webhooks/github HTTP/1.1
Host: api.yourapp.com
Content-Type: application/json
X-GitHub-Event: push
X-GitHub-Delivery: 72d3162e-cc78-11e3-81ab-4c9367dc0958
X-Hub-Signature-256: sha256=7d38cdd689735b008b3c702edd92eea23791c5f6...
X-Hub-Signature: sha1=... (legacy — ignore this one)

{ "ref": "refs/heads/main", "commits": [ ... ] }
  • X-Hub-Signature-256 — the signature you should verify: sha256= followed by the hex HMAC-SHA256 of the raw body, keyed by your webhook secret.
  • X-Hub-Signature — the same idea with HMAC-SHA1. It exists only for backward compatibility; SHA-1 is weak, so ignore it for new code.
  • X-GitHub-Event — the event type (push, pull_request, issues, and so on), including a ping when the webhook is first created.
  • X-GitHub-Delivery — a unique GUID per delivery. Use it as an idempotency key so a redelivered event is processed only once.

The secret is configured on the webhook itself — in a repository's Settings → Webhooks, at the organization level, or in a GitHub App's settings — and you store the identical value in your app. If no secret is set, GitHub sends no signature header at all, so always configure one.

Verifying the Signature in Node.js

Compute the HMAC over the raw body, rebuild the sha256= string, and compare it in constant time:

const crypto = require('crypto');

function verifyGithubSignature(rawBody, signatureHeader, secret) {
  // signatureHeader looks like: sha256=<hex digest>
  const expected = 'sha256=' + crypto
    .createHmac('sha256', secret)
    .update(rawBody)                 // raw bytes, NOT re-serialized JSON
    .digest('hex');

  const a = Buffer.from(expected);
  const b = Buffer.from(signatureHeader || '');
  // timingSafeEqual throws if lengths differ, so guard first
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

Wired into an Express route, the critical detail is capturing the raw body and only parsing JSON after the signature checks out:

app.post('/webhooks/github',
  express.raw({ type: 'application/json' }),   // req.body is a Buffer
  (req, res) => {
    const sig = req.headers['x-hub-signature-256'];
    if (!verifyGithubSignature(req.body, sig, process.env.GITHUB_WEBHOOK_SECRET)) {
      return res.status(403).send('signature mismatch');   // GitHub's own convention
    }

    const event = req.headers['x-github-event'];
    const payload = JSON.parse(req.body);   // safe to parse now that it is verified
    if (event === 'ping') return res.sendStatus(200);   // acknowledge the setup ping

    handleEvent(event, payload);
    res.sendStatus(200);
  });

Verifying the Signature in Python

The Flask version uses only the standard library plus request.data, which is the raw request body:

import hmac, hashlib
from flask import request, abort

def verify_github_signature(secret: str):
    signature = request.headers.get('X-Hub-Signature-256', '')
    expected = 'sha256=' + hmac.new(
        secret.encode(),
        request.data,          # raw bytes — do NOT use request.json here
        hashlib.sha256,
    ).hexdigest()
    if not hmac.compare_digest(expected, signature):
        abort(403)

To reproduce the exact HMAC-SHA256 computation by hand — handy when your code and GitHub disagree — paste the raw body and secret into the HMAC Generator and compare the hex digest.

Common Causes of a Signature Mismatch

When verification fails, it is almost always one of these:

  • Not hashing the raw body. The number-one cause. If middleware like express.json() parses the request first, you no longer have the exact bytes GitHub signed, and re-serializing changes whitespace and key order. Use express.raw() on the route (or request.data in Flask, await request.body() in FastAPI).
  • Wrong or mistyped secret. The secret in your environment must match the webhook's configured secret exactly — a trailing newline or stray space is enough to break it.
  • Verifying the wrong header. Hashing with SHA-256 but comparing to X-Hub-Signature (SHA-1), or vice versa. Match the algorithm to the header.
  • No secret configured on GitHub. Then there is no X-Hub-Signature-256 header to read, and your code compares against an empty string.
  • Non-constant-time comparison. Using === or == instead of timingSafeEqual / compare_digest leaks timing information and is considered a vulnerability.

The Ping Event and Redelivery

When you first create a webhook, GitHub immediately sends a ping event — respond with a 2xx so the webhook shows as healthy. In production, GitHub retries nothing automatically, but you can redeliver any past event by hand from Settings → Webhooks → Recent Deliveries, which is invaluable for debugging. Because a manual redelivery reuses the original X-GitHub-Delivery GUID, recording processed GUIDs keeps your handler idempotent.

Testing Locally

GitHub can only reach a public URL, so forward deliveries to your machine while developing:

# GitHub CLI: forward a repo's webhook deliveries to localhost
gh webhook forward --repo owner/repo --events push \
  --url http://localhost:3000/webhooks/github

# Or relay through smee.io (the payload is signed with YOUR secret either way)
npx smee-client --url https://smee.io/AbCd1234 \
  --target http://localhost:3000/webhooks/github

For a fully offline loop with no repository at all, generate a GitHub-style payload with the Webhook Payload Builder, sign it with your secret, and POST it at your handler — then confirm the digest against the HMAC Generator. Both tools run entirely in your browser via the Web Crypto API, so nothing leaves your machine.

Related Errors

  • 403 Forbidden -- the status GitHub's own docs return when a signature check fails.
  • 400 Bad Request -- returned when the signature header is missing or malformed.
  • 504 Gateway Timeout -- a slow handler times out and GitHub marks the delivery as failed.
