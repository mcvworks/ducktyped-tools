HTTP Requests Explained

Last updated: June 11, 2026

Understand the anatomy of an HTTP request — method, path, headers, and body — how to pick the right method, which request headers actually matter, the three common body encodings, and how to debug any request with curl.

Anatomy of an HTTP Request

Every HTTP request, whether it comes from a browser, a mobile app, or a script, is plain structured text with three parts: a request line, a block of headers, and an optional body separated from the headers by a blank line. Here is a complete request as it travels over the wire:

POST /api/users?notify=true HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
Accept: application/json
Content-Length: 47

{"name": "Jane Doe", "email": "jane@example.com"}
  • Method (POST) — the verb declaring what kind of operation this is.
  • Path and query string (/api/users?notify=true) — which resource the request targets, plus optional key-value parameters after ?.
  • Protocol version (HTTP/1.1) — HTTP/2 and HTTP/3 encode the same semantics in binary frames, but the method/path/headers/body model is unchanged.
  • Headers — one Name: value pair per line. Header names are case-insensitive; Host is the only mandatory one in HTTP/1.1.
  • Body — the payload. GET, HEAD, and DELETE requests normally have none; POST, PUT, and PATCH usually do.

The server answers with a status line, response headers, and a response body. If a request "doesn't work," the problem is always somewhere in those few lines above — which is why being able to read and reconstruct them is the core HTTP debugging skill.

Choosing the Right Method

Methods carry meaning beyond convention: caches, proxies, and browsers change behavior based on them. Two properties matter most — safety (does the request change anything?) and idempotency (does repeating it produce the same result?).

  • GET — read a resource. Safe and idempotent, freely cacheable and retryable. Never use GET for anything that mutates state; crawlers and prefetchers will trigger it.
  • HEAD — like GET but returns headers only. Useful for checking existence, size (Content-Length), or freshness without downloading the body.
  • POST — create a resource or trigger an action. Not idempotent: submitting twice may create two records, which is why clients should not blindly retry failed POSTs.
  • PUT — replace a resource entirely with the representation you send. Idempotent: PUT-ing the same document five times leaves one identical resource.
  • PATCH — partially update a resource, changing only the fields included in the body.
  • DELETE — remove a resource. Idempotent in effect: the second DELETE may return 404, but the end state is the same.
  • OPTIONS — ask what the server supports. Browsers send OPTIONS automatically as CORS preflight requests, which is why you see them in network logs you never wrote.

Using the wrong method gets you a 405 Method Not Allowed; the response's Allow header lists what the endpoint actually accepts.

Request Headers That Matter

A handful of request headers cause the vast majority of API integration bugs:

  • Content-Type — declares the format of the body you are sending, e.g. application/json or application/x-www-form-urlencoded. If this does not match the actual body encoding, servers respond with 400 Bad Request or 415 Unsupported Media Type — or worse, silently parse an empty object.
  • Accept — declares the format you want back. Accept: application/json asks an endpoint that supports content negotiation to return JSON instead of HTML or XML. A server that cannot satisfy it may return 406 Not Acceptable.
  • Authorization — carries credentials. The two common schemes are Bearer <token> for API tokens and JWTs, and Basic <base64(user:pass)>. A missing or malformed value yields 401 Unauthorized; valid credentials without permission yield 403 Forbidden.
  • User-Agent — identifies the client. Many APIs (GitHub's, for one) reject requests without one, and CDNs apply bot rules based on it. Set a descriptive value like myapp/1.2 (ops@example.com) for server-to-server calls.
  • Host — the domain being requested; mandatory in HTTP/1.1 and how one IP serves many sites. Tools set it automatically, but overriding it is a classic trick for testing a server before DNS points at it.

Body Encodings: JSON vs Form-Urlencoded vs Multipart

The body is just bytes; the Content-Type header tells the server how to decode them. Three encodings cover nearly all API traffic.

application/json

The default for modern APIs. Structured, nestable, and typed:

Content-Type: application/json

{"name": "Jane", "roles": ["admin", "editor"], "active": true}

application/x-www-form-urlencoded

The classic HTML <form> encoding: flat key-value pairs, percent-encoded, joined with &. Still required by many OAuth token endpoints and older APIs:

Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&client_id=abc123&scope=read%20write

Note the encoding rules — spaces become %20 (or +), and reserved characters like & and = inside values must be escaped. The URL Encoder handles this for you.

multipart/form-data

Used for file uploads and for mixing binary data with text fields. The body is split into parts separated by a boundary string declared in the header, and each part carries its own mini-headers:

Content-Type: multipart/form-data; boundary=----X1Y2Z3

------X1Y2Z3
Content-Disposition: form-data; name="caption"

Quarterly report
------X1Y2Z3
Content-Disposition: form-data; name="file"; filename="report.pdf"
Content-Type: application/pdf

%PDF-1.7 ...binary bytes...
------X1Y2Z3--

Rule of thumb: JSON for structured API data, form-urlencoded when the endpoint demands it (OAuth, legacy forms), multipart only when files are involved. And the most common mistake of all: sending a JSON string with a form-urlencoded Content-Type, or vice versa — the server parses garbage and returns a confusing 400.

Debugging with curl Equivalents

When a request fails inside an application, the fastest way to isolate the problem is to reproduce it with curl, removing your code from the equation. The flags map directly onto request anatomy:

# GET with auth and verbose output (-v prints request + response headers)
curl -v 'https://api.example.com/users?page=2' \
  -H 'Authorization: Bearer YOUR_TOKEN' \
  -H 'Accept: application/json'

# POST JSON
curl -X POST 'https://api.example.com/users' \
  -H 'Content-Type: application/json' \
  -d '{"name": "Jane Doe", "email": "jane@example.com"}'

# POST form-urlencoded (--data-urlencode escapes values for you)
curl -X POST 'https://auth.example.com/oauth/token' \
  --data-urlencode 'grant_type=client_credentials' \
  --data-urlencode 'client_id=abc123'

# Upload a file as multipart
curl -X POST 'https://api.example.com/files' \
  -F 'caption=Quarterly report' \
  -F 'file=@report.pdf'

# Headers only — quick status and redirect check
curl -I 'https://example.com/old-page'

The debugging workflow: get the request working in curl first, then make your code produce the identical request. -v shows exactly what curl sent; compare it line by line against what your application sends. Differences in Content-Type, a missing Authorization header, or an unencoded query parameter jump out immediately.

How to Use the Tool

The duckTyped HTTP Request Builder assembles requests visually and writes the code for you:
