Website Not Loading? A Step-by-Step Diagnostic Guide

Last updated: April 5, 2026

When a website won't load, the problem is somewhere in a stack: DNS → network routing → TCP connection → TLS handshake → HTTP response → application. This guide walks you down that stack, one layer at a time, so you can isolate exactly where things are breaking and fix it fast.

First: What Is the Browser Showing You?

The error message in the browser is your biggest clue. Each one points at a specific layer:

  • DNS_PROBE_FINISHED_NXDOMAIN — domain doesn't exist (DNS problem).
  • ERR_NAME_NOT_RESOLVED — DNS resolver couldn't find an answer.
  • ERR_CONNECTION_REFUSED — server is reachable but actively refusing connections.
  • ERR_CONNECTION_TIMED_OUT — server isn't responding at all (firewall or dead host).
  • ERR_SSL_* — TLS handshake failed (certificate or cipher problem).
  • 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout — upstream/backend failures.

If the browser shows a specific error, jump to the matching layer below. If the page just spins forever, start from Step 1 and work down.

Step 1 — Check DNS Resolution

Every request starts with DNS. If the domain can't be resolved to an IP address, nothing else matters. Use the DNS Record Checker to verify:

  • An A record exists and points to your server's IPv4 address.
  • If you serve IPv6, an AAAA record points to the correct IPv6 address.
  • NS records at your registrar point to the nameservers that actually hold your zone.
  • If you use a CDN (Cloudflare, Fastly, CloudFront), the records point to the CDN, not your origin.

If you just made a DNS change, the problem may be propagation delay — old cached records can linger for the length of the previous TTL. Read our DNS propagation guide for how to speed this up.

Step 2 — Test Network Reachability

DNS resolves. Can you actually reach the server?

Traceroute

Use the Traceroute tool to see the path packets take from a public vantage point to your server. If the trace dies partway through (shown as * * *), routing is broken upstream. If it reaches your server's IP but packets get dropped there, your firewall or network is the problem.

Port Scan

Use the Port Scanner to confirm that ports 80 (HTTP) and 443 (HTTPS) are open and listening. Results:

  • Open — the server is listening and accepting connections. Move to the next step.
  • Closed — the server received the packet but nothing is listening on that port. Your web server process (nginx, Apache, Caddy, Node, etc.) is down or bound to the wrong interface.
  • Filtered — a firewall silently dropped the packet. Check iptables, security groups (AWS, GCP, Azure), or your hosting provider's firewall.

Step 3 — Verify SSL/TLS Certificate

If HTTP works but HTTPS doesn't — or the browser shows a security warning — the TLS layer is broken. Use the SSL Certificate Checker to verify:

  • The certificate is not expired (and not yet valid).
  • The certificate chain is complete (missing intermediates are one of the most common causes of "works on Firefox, fails on curl" problems).
  • The hostname matches the certificate's Common Name or a Subject Alternative Name.
  • The certificate was issued by a CA the browser trusts.
  • The server supports a modern TLS version (1.2 or 1.3) and reasonable cipher suites.

If the certificate is expired, our SSL expired fix guide covers renewal. For chain errors, see our TLS handshake guide.

Step 4 — Check HTTP Response

DNS is fine, the port is open, the cert is valid — but the browser shows a 4xx or 5xx error. Now the problem is above the transport layer.

Use the HTTP Request Builder to send a raw request and inspect the full response, including headers. The HTTP Latency tool shows response time from multiple vantage points — useful for detecting regional outages.

Common HTTP errors and where to look:

  • 500 Internal Server Error — application crashed. Check application logs.
  • 502 Bad Gateway — reverse proxy (nginx, ALB, Cloudflare) got a bad response from upstream. The backend is down or misconfigured.
  • 503 Service Unavailable — server is up but refusing to serve (maintenance mode, overloaded, rate-limited).
  • 504 Gateway Timeout — upstream didn't respond in time. Slow database, blocked network call, or deadlocked thread pool.
  • 404 Not Found — the URL is wrong or the route isn't deployed.
  • 403 Forbidden — access control, WAF rule, or file permissions blocking the request.

Step 5 — Check Security Headers and Redirects

If the page loads but something is broken (mixed content warnings, infinite redirects, blocked resources), inspect:

  • Security Headers checker — CSP, HSTS, X-Frame-Options, and other headers that can block legitimate content if misconfigured.
  • Redirect Checker — follow every hop in a redirect chain. Loops and mixed-protocol redirects are common causes of ERR_TOO_MANY_REDIRECTS.

Step 6 — Is It Just You?

Sometimes the site works fine — you just can't reach it. Before blaming the server:

  • Try from a different network (mobile data, VPN, another office).
  • Flush your local DNS cache (ipconfig /flushdns on Windows, sudo dscacheutil -flushcache on macOS, sudo systemd-resolve --flush-caches on Linux).
  • Run the DNS Record Checker from our tool (which queries from a neutral vantage point) and compare to what your local resolver returns. A mismatch means cached stale records on your resolver.
  • Check if your ISP or workplace is blocking the domain.

The Full Diagnostic Checklist

  1. DNS resolves? → DNS Checker
  2. Network reachable? → Traceroute + Port Scanner
  3. TLS working? → SSL Checker
  4. HTTP responds correctly? → HTTP Request Builder + HTTP Latency
  5. No redirect/header issues? → Redirect Checker + Security Headers
  6. Not a local issue? → Test from a second network
