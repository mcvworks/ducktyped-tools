What Is SPF (Sender Policy Framework)?

Last updated: March 8, 2026

SPF is an email authentication protocol that allows domain owners to specify which mail servers are authorized to send email on their behalf. It works by publishing a DNS TXT record that receiving servers check to verify the sender's identity.

How SPF Works

When a mail server receives an incoming email, it extracts the domain from the envelope sender address (the Return-Path or MAIL FROM value) and looks up the SPF record for that domain in DNS. The SPF record contains a list of authorized sending sources -- IP addresses, IP ranges, or references to other domains' SPF records.

The receiving server then compares the connecting server's IP address against the authorized sources listed in the SPF record. Based on the match result, the SPF check returns one of several results:

  • Pass -- the sending server's IP is explicitly authorized.
  • Fail -- the sending server's IP is explicitly not authorized (the record uses -all).
  • SoftFail -- the sending server's IP is not authorized but the domain owner is not making a strong assertion (the record uses ~all).
  • Neutral -- the domain owner makes no assertion about the IP (the record uses ?all).
  • PermError -- the SPF record has a syntax error or exceeds processing limits.
  • TempError -- a temporary DNS error prevented evaluation.

SPF Record Syntax

An SPF record is a DNS TXT record that begins with v=spf1 followed by a series of mechanisms and modifiers. Here is a typical example:

v=spf1 ip4:192.0.2.0/24 include:_spf.google.com include:sendgrid.net -all

This record authorizes:

  • Any server in the 192.0.2.0/24 IP range
  • Any server authorized by Google Workspace's SPF record
  • Any server authorized by SendGrid's SPF record

The -all at the end means all other sources should fail.

Common Mechanisms

  • ip4:address/prefix -- matches an IPv4 address or CIDR range.
  • ip6:address/prefix -- matches an IPv6 address or CIDR range.
  • include:domain -- includes the SPF record of another domain. Counts as one DNS lookup.
  • a -- matches the A record IP(s) of the domain. Counts as one DNS lookup.
  • mx -- matches the IP addresses of the domain's MX servers. Counts as one DNS lookup.
  • all -- matches everything. Used at the end with a qualifier to set the default policy.

Qualifiers

  • + (Pass) -- the default qualifier. +all and all are equivalent.
  • - (Fail) -- hard fail. Use -all to reject unauthorized senders.
  • ~ (SoftFail) -- soft fail. Use ~all during testing or transition periods.
  • ? (Neutral) -- no policy assertion.

The 10-Lookup Limit

The SPF specification (RFC 7208) limits the number of DNS lookups during SPF evaluation to 10. Each include, a, mx, redirect, and exists mechanism counts as one lookup. Nested includes also count -- if your record includes a domain whose SPF record itself includes three other domains, that is four lookups total.

If your SPF record exceeds 10 lookups, evaluation fails with a PermError, which most receiving servers treat similarly to a fail. This is a common problem for organizations that use many third-party email services (marketing platforms, CRM systems, helpdesk tools), each requiring its own include.

Strategies to stay within the limit:

  • Replace include mechanisms with direct ip4 or ip6 entries where possible (these do not count as lookups).
  • Use SPF flattening services that resolve includes into IP addresses at publish time.
  • Consolidate sending services or use subdomains with separate SPF records for different services.

Common SPF Mistakes

Multiple SPF Records

A domain must have exactly one SPF record. If two TXT records both start with v=spf1, SPF evaluation fails with a PermError. When adding a new service, add it to the existing SPF record rather than creating a second one.

Using +all

An SPF record ending with +all authorizes the entire internet to send email as your domain. This completely defeats the purpose of SPF. Always use -all (hard fail) or ~all (soft fail).

Forgetting Subdomains

SPF records are not inherited by subdomains. If you send email from mail.example.com, it needs its own SPF record, separate from example.com. Subdomains without SPF records have no protection against spoofing.

SPF and Email Authentication

SPF is one of three complementary email authentication protocols. It works alongside DKIM (which verifies message integrity using cryptographic signatures) and DMARC (which defines policies for handling authentication failures). Together, these three protocols form a comprehensive email authentication system.

An important limitation of SPF: it authenticates the envelope sender (Return-Path), not the header From address that users see in their email client. This means SPF alone cannot prevent display-name spoofing. DMARC addresses this gap by requiring alignment between the authenticated domain and the visible From domain.
