URL Anatomy Explained

Last updated: June 11, 2026

Break a URL down to its seven components, understand percent-encoding and reserved characters, learn the query-string conventions that trip up parsers, and see how relative references actually resolve.

The Anatomy of a URL

A URL (Uniform Resource Locator) is defined by RFC 3986 as a sequence of up to seven components. Here is a deliberately complete example, broken apart:

https://alice:s3cret@api.example.com:8443/v2/search?q=ducks&limit=10#results

scheme    https
userinfo  alice:s3cret
host      api.example.com
port      8443
path      /v2/search
query     q=ducks&limit=10
fragment  results
  • Scheme — the protocol (https, http, ftp, mailto). Always followed by :, and by // when an authority (host) follows. Case-insensitive; canonical form is lowercase.
  • Userinfo — optional user:password before an @. Effectively deprecated for HTTP (browsers strip or block it) but still meaningful in connection strings like postgres:// URLs, and a favorite tool of phishers (https://google.com@evil.example/ goes to evil.example).
  • Host — a domain name or IP address. Case-insensitive. IPv6 addresses are bracketed: https://[2001:db8::1]:8080/.
  • Port — optional; defaults come from the scheme (80 for http, 443 for https). https://example.com/ and https://example.com:443/ are the same origin.
  • Path — slash-separated segments identifying the resource. Case-sensitive, unlike the host.
  • Query — everything between ? and the fragment; by convention key=value pairs joined with &, though RFC 3986 imposes no structure at all.
  • Fragment — everything after #. Resolved entirely client-side: the browser never sends it to the server, which is why server logs cannot show it and why single-page-app routers historically lived there.

Percent-Encoding and Reserved Characters

URLs may only contain a limited ASCII repertoire, so everything else must be percent-encoded: the byte is replaced by % plus its two-digit hexadecimal value. RFC 3986 splits characters into three groups:

  • Unreserved — A–Z a–z 0–9 - . _ ~. Always safe; never need encoding.
  • Reserved — : / ? # [ ] @ ! $ & ' ( ) * + , ; =. These are the syntax of the URL. They must be encoded whenever they appear as data in a component where they have meaning — an & inside a query value, a / inside a path segment, a # anywhere it is not the fragment delimiter.
  • Everything else — spaces, quotes, angle brackets, control characters, and all non-ASCII. Always encoded; non-ASCII text is first serialized as UTF-8, then each byte is encoded.
Raw value:   café & crème
Encoded:     caf%C3%A9%20%26%20cr%C3%A8me

In context:  /search?q=caf%C3%A9%20%26%20cr%C3%A8me
             (the %26 keeps the & from splitting the parameter)

The critical rule: encode per component, then assemble — never encode an already-assembled URL, or you will turn your delimiters into data. In JavaScript that is the difference between encodeURIComponent() (encodes &, =, / — use on values) and encodeURI() (preserves delimiters — rarely what you want). The duckTyped URL Encoder exposes both modes; the URL Encoding guide covers them in depth.

Query-String Parsing Gotchas

The query string looks trivial — split on &, then on = — but three conventions cause endless bugs.

Plus signs

Under the application/x-www-form-urlencoded rules HTML forms use, a space becomes + in the query string. But that convention applies only there: in a path, + is a literal plus. The mismatch bites in both directions:

?q=duck+types
decodeURIComponent("duck+types")        → "duck+types"   (wrong, + kept)
new URLSearchParams("q=duck+types").get("q") → "duck types"  (correct)

?email=a+b@example.com   → many servers read "a b@example.com"
?email=a%2Bb@example.com → reads "a+b@example.com" as intended

Duplicate keys

Nothing in any RFC says what ?tag=red&tag=blue means. Frameworks disagree: some return the first value, some the last, some a list. If two layers of your stack disagree (say, a CDN cache key uses the first value while the app reads the last), you have a cache-poisoning vector known as HTTP parameter pollution.

Arrays and structure

Because the query string has no native array type, ecosystems invented their own conventions, and they do not interoperate:

?tag=red&tag=blue        repeat the key      (most APIs, URLSearchParams.getAll)
?tag[]=red&tag[]=blue    bracket suffix      (PHP, Rails, qs)
?tag=red,blue            delimited value     (many REST APIs)

Also remember: ?flag (no =), ?flag= (empty value), and a missing parameter are three distinct states that many parsers collapse into one. Paste a real query string into the Query String Parser to see exactly what keys and values it contains.

Relative URL Resolution

Most links in the wild are not absolute. RFC 3986 defines exactly how a relative reference combines with a base URL, and the rules surprise people. Given the base https://example.com/docs/guide/intro.html:

page.html              → https://example.com/docs/guide/page.html
./page.html            → https://example.com/docs/guide/page.html
../api/v2              → https://example.com/docs/api/v2
/api/v2                → https://example.com/api/v2
//cdn.example.net/x.js → https://cdn.example.net/x.js
?page=2                → https://example.com/docs/guide/intro.html?page=2
#top                   → https://example.com/docs/guide/intro.html#top

Three rules explain almost every surprise:

  • The base directory is everything up to the last slash. intro.html is dropped before joining. A base of /docs/guide (no trailing slash) therefore resolves page.html to /docs/page.html, not /docs/guide/page.html — the classic broken-stylesheet bug after removing a trailing slash.
  • A leading slash means site root, replacing the entire base path.
  • A leading double slash is protocol-relative: it replaces the host too, keeping only the scheme. //evil.example/ in a redirect parameter is a full cross-origin URL — a frequent open-redirect bypass.

Common URL Parsing Bugs

When validating or parsing URLs in real code, watch for these recurring failures:

  • Validating with regex instead of a parser. Hand-rolled patterns miss userinfo tricks (https://trusted.com@evil.com/), backslash tolerance (browsers treat https:\\evil.com like //evil.com), and unusual-but-valid forms. Parse first with a real parser (new URL(), urllib.parse), then inspect the components.
  • Double encoding and double decoding. Encoding an already-encoded value turns %20 into %2520; decoding twice turns %2541 into A. Filters that decode a different number of times than the backend are a standard path-traversal bypass.
  • Comparing URLs as strings. HTTPS://EXAMPLE.COM:443/a/../b and https://example.com/b are the same resource. Normalize (lowercase scheme and host, drop default ports, resolve dot segments, decode unreserved characters) before comparing.
  • Expecting the fragment server-side. Everything after # never leaves the browser. If a redirect target or token lives in the fragment, the server cannot log or validate it.
  • Forgetting that parsers disagree. The WHATWG URL standard (browsers, Node.js) and RFC 3986 libraries differ on edge cases like whitespace, backslashes, and multiple @ signs. Server-side request forgery (SSRF) bugs often live precisely in the gap between the parser that validates and the client that fetches.

How to Use the Tool

The duckTyped URL Parser takes the guesswork out of all of the above:

  1. Paste any URL into the input and press Enter or click Parse URL.
  2. Read the component table — protocol, hostname, port (or default), pathname, search, hash, origin, username, and password, each with a one-click copy button.

Parsing happens entirely in your browser using the same WHATWG URL engine browsers use for navigation — nothing is sent to a server.

Related Errors

  • HTTP 400 Bad Request — malformed URLs and bad percent-encoding are common causes.

  • HTTP 414 URI Too Long — runaway query strings hit server URL length limits.
