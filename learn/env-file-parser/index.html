.env Files Explained

Last updated: June 11, 2026

Master .env file syntax: quoting and escaping rules, multiline values, how variable expansion differs between dotenv, Docker Compose, and the shell, which value wins when they conflict, and how to keep secrets out of git.

What Is a .env File?

A .env file is a plain-text file of KEY=value lines that supplies environment variables to an application at startup. It exists to solve one problem: configuration — especially secrets like API keys and database credentials — should live in the environment, not in source code. That principle comes from the twelve-factor app methodology, and the .env file is its most popular implementation: each developer and each deployment keeps its own local file, while the code reads process.env.DATABASE_URL (or os.environ, $_ENV, etc.) without caring where the value came from.

A typical file looks like this:

# Database
DATABASE_URL=postgres://app:s3cret@localhost:5432/myapp

# Third-party services
STRIPE_API_KEY="sk_test_your_secret_key_here"
SMTP_HOST=smtp.example.com
SMTP_PORT=587

# Feature flags
DEBUG=true

The catch: there is no official .env specification. The format originated in Ruby's dotenv gem and was reimplemented by Node's dotenv, Python's python-dotenv, PHP's vlucas/phpdotenv, Docker Compose, Vite, and dozens of others — each with slightly different rules. The basics below are safe everywhere; the differences are where bugs live.

Syntax Basics

The portable core of the format:

  • One KEY=value pair per line. Keys are conventionally UPPER_SNAKE_CASE, must not contain spaces, and should start with a letter or underscore.
  • No spaces around the =. This is the single most common .env mistake. Shell syntax forbids it, and dotenv parsers either reject the line or create a key with a trailing space.
  • Lines starting with # are comments. Most parsers also allow inline comments after an unquoted value (PORT=587 # smtp), which means an unquoted value containing # gets silently truncated.
  • Blank lines are ignored. An empty value (EMPTY_VAR=) sets the variable to an empty string — which is different from the variable being unset.

Right vs wrong, side by side:

# Wrong                          # Right
KEY = value                      KEY=value
PASSWORD=p@ss word               PASSWORD="p@ss word"
SECRET=abc#123                   SECRET="abc#123"
export NODE_ENV=production       NODE_ENV=production
MY-KEY=value                     MY_KEY=value

The export prefix deserves a note: it makes the file source-able by a shell, and some parsers tolerate it, but Docker Compose and several strict parsers do not. Leave it out unless you specifically source the file.

Quoting and Escaping Rules

Quotes are where parsers diverge most, but the dominant convention (Node dotenv, python-dotenv, Compose) mirrors the shell:

  • Unquoted values are trimmed of surrounding whitespace and end at an inline #. Fine for hostnames, ports, and booleans.
  • Double quotes ("...") preserve spaces and #, and expand escape sequences: \n becomes a real newline, \" a literal quote. In parsers that support expansion, $VAR is also substituted inside double quotes.
  • Single quotes ('...') are fully literal: no escapes, no expansion. Use them when the value itself contains $, backslashes, or anything else you want untouched.
MESSAGE="line one\nline two"   # value contains a real newline
REGEX='^\d+$'                  # value is exactly ^\d+$  (no escape processing)
LITERAL='$HOME is not expanded'
PASSWORD="p@$$w0rd"            # risky: $$ and $w may be expansion syntax
PASSWORD='p@$$w0rd'            # safe: single quotes keep it literal

Multiline values — private keys are the classic case — are supported by modern parsers in two forms, but support is far from universal:

# Modern dotenv (v15+), python-dotenv: a quoted value may span lines
PRIVATE_KEY="-----BEGIN RSA PRIVATE KEY-----
MIIEpAIBAAKCAQEA7...
-----END RSA PRIVATE KEY-----"

# Maximum portability: keep it on one line with \n escapes
PRIVATE_KEY="-----BEGIN RSA PRIVATE KEY-----\nMIIEpAIBAAKCAQEA7...\n-----END RSA PRIVATE KEY-----"

# Often even better: Base64-encode the whole key and decode in app code
PRIVATE_KEY_B64=LS0tLS1CRUdJTiBSU0EgUFJJVkFURSBLRVktLS0tLQ...

Variable Expansion: dotenv vs Docker Compose vs Shell

Can one variable reference another, as in API_URL=https://$HOST/api? This is the sharpest difference between parsers, and the same file can produce three different values in three tools:

HOST=localhost
API_URL=https://$HOST/api
  • Node dotenv — no expansion at all. API_URL is the literal string https://$HOST/api unless you add the separate dotenv-expand package.
  • Docker Compose — expands $VAR and ${VAR} in the .env file and in compose.yaml, including shell-style defaults: ${PORT:-8080} (default if unset or empty), ${PORT-8080} (default only if unset), and ${PORT:?error message} (fail if missing). A literal dollar sign must be doubled: PRICE=$$5.
  • The shell (source .env) — full shell semantics: expansion, command substitution, the lot. Powerful, but it also means an unquoted special character is a syntax error and a malicious file is arbitrary code execution.
  • python-dotenv — expands ${VAR} (interpolation is on by default for the load_dotenv path), but not bare $VAR.

Practical advice: if a file must be shared between tools (very common — the same .env feeding Compose and the app inside the container), avoid expansion syntax entirely, or single-quote any value containing a literal $.

Precedence: The Real Environment Wins

What happens when a variable is defined both in the shell and in the .env file? Almost universally, the real environment beats the file:

$ cat .env
NODE_ENV=development

$ NODE_ENV=production node app.js
# dotenv sees NODE_ENV already set and leaves it alone
# app runs with NODE_ENV=production

Node's dotenv, python-dotenv, and Docker Compose all behave this way by default; most offer an opt-in override flag (dotenv.config({ override: true }), load_dotenv(override=True)) to reverse it. This default is a feature, not a bug: it lets CI pipelines and production platforms inject real values while the .env file serves as the local fallback. Docker Compose adds its own layered precedence on top — from highest to lowest: environment: entries in compose.yaml, shell variables, --env-file/.env, and finally ENV defaults baked into the image. When a container sees a stale value, walk that chain from the top.

Common Mistakes and Security Practices

  • Committing secrets. The cardinal sin. Add .env (and .env.*.local variants) to .gitignore before the first commit, and commit a placeholder .env.example instead. If a real secret ever lands in git, rotate it immediately — deleting the file in a later commit leaves it fully recoverable in history, and bots scrape public repos for exactly this within minutes.
  • Spaces around =. KEY = value silently fails or creates a malformed key in most parsers. If a variable is mysteriously undefined, check this first.
  • A UTF-8 BOM. Some Windows editors prepend an invisible byte-order mark, turning the first key into ﻿DATABASE_URL. Symptom: only the first variable in the file fails to load. Save as "UTF-8 without BOM". Stray CRLF line endings cause a similar invisible-trailing-\r bug.
  • Unquoted special characters. Passwords containing #, $, or spaces get truncated or mangled. Quote any value that is not strictly alphanumeric.
  • One .env for every environment. Use separate files (.env.development, .env.production) or, better, no file at all in production — inject variables through your platform's secret manager (Vault, AWS Secrets Manager, Kubernetes Secrets), which provides access control, auditing, and rotation that a plain file never can.
  • Forgetting frontend exposure rules. Build tools ship prefixed variables (VITE_, NEXT_PUBLIC_, REACT_APP_) to the browser bundle. Anything with such a prefix is public; never put a server secret behind one.
