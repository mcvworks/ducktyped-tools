What Causes HTTP 429 Too Many Requests?

Last updated: March 8, 2026

HTTP 429 Too Many Requests is a rate-limiting response code. It means the server is intentionally rejecting your request because you have exceeded the allowed request rate. This guide explains how rate limiting works and how to handle 429 responses properly.

What Is Rate Limiting?

Rate limiting is a technique servers use to control how many requests a client can make within a given time window. It protects servers from being overwhelmed by excessive traffic -- whether from legitimate high-volume usage, bugs in client code, or deliberate abuse.

Common rate limiting patterns:

  • Fixed window -- allows N requests per time window (e.g., 100 requests per minute). Simple but can allow bursts at window boundaries.
  • Sliding window -- tracks requests over a rolling time period, preventing boundary bursts.
  • Token bucket -- tokens are added to a bucket at a fixed rate. Each request consumes a token. When the bucket is empty, requests are rejected. Allows controlled bursts.
  • Leaky bucket -- requests are processed at a constant rate. Excess requests queue up and are processed later or rejected if the queue is full.

Common Causes of 429 Errors

API Rate Limits

Most APIs impose rate limits to ensure fair usage. For example, an API might allow 60 requests per minute per API key. If your application exceeds this, subsequent requests receive 429 responses until the rate limit window resets. Common APIs with rate limits include GitHub, Twitter/X, Stripe, OpenAI, and virtually every public API.

Aggressive Polling or Scraping

Applications that poll an endpoint too frequently (checking for updates every second instead of every 30 seconds) or scripts that scrape websites at high speed commonly trigger rate limits. Web Application Firewalls (WAFs) and CDNs often implement rate limiting at the edge to block scrapers.

Concurrent Request Bursts

Sending many requests simultaneously (e.g., fetching 100 API pages in parallel) can trigger rate limits even if the total number of requests is within the limit. Some rate limiters count concurrent connections, not just requests per second.

Shared IP Address

If rate limiting is IP-based, you may hit limits because other users sharing your IP address (common with corporate proxies, VPNs, or shared hosting) are also making requests to the same server.

Login/Authentication Brute Force Protection

Many applications rate-limit login attempts to prevent credential stuffing and brute force attacks. After a certain number of failed login attempts, the server returns 429 to slow down the attacker. This is a deliberate security measure.

The Retry-After Header

Well-implemented APIs include a Retry-After response header with 429 responses. This header tells you exactly when you can retry:

HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1709913600

Common rate-limit headers (not standardized, but widely used):

  • Retry-After -- seconds to wait (or an HTTP date) before retrying.
  • X-RateLimit-Limit -- the maximum number of requests allowed in the window.
  • X-RateLimit-Remaining -- how many requests you have left in the current window.
  • X-RateLimit-Reset -- Unix timestamp when the rate limit window resets.

Handling 429 Errors Properly

Exponential Backoff

The standard approach for handling 429 responses is exponential backoff with jitter:

  1. If a Retry-After header is present, wait that many seconds.
  2. Otherwise, wait 1 second, then retry.
  3. If still rate-limited, wait 2 seconds, then 4, then 8, and so on.
  4. Add random jitter (e.g., +/- 20%) to prevent multiple clients from retrying simultaneously.
  5. Set a maximum retry count (e.g., 5 attempts) to avoid infinite loops.

Request Queuing

For applications that need to make many API calls, implement a request queue that sends requests at a controlled rate, staying under the limit. Libraries like bottleneck (Node.js) or ratelimit (Python) handle this automatically.

Caching

Reduce unnecessary API calls by caching responses. If the data does not change frequently, cache it locally and serve from cache instead of making a new API request for every user.

Proactive Rate Tracking

Track X-RateLimit-Remaining headers and slow down requests as you approach the limit, rather than waiting for a 429 response. This provides a smoother experience than hitting the limit and having to back off.

429 vs. Other Error Codes

  • 429 Too Many Requests -- you exceeded the rate limit. Slow down and retry later.
  • 403 Forbidden -- you do not have permission. A rate-limited IP might be temporarily banned and receive 403 instead of 429.
  • 503 Service Unavailable -- the server is overloaded or under maintenance. Similar symptom but different cause than 429.
