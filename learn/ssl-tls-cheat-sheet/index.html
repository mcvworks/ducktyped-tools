SSL/TLS Cheat Sheet

Last updated: June 11, 2026

Quick reference for everything TLS: handshake flows, cipher suite notation, certificate types, file formats, OpenSSL commands, HSTS, and CAA. Bookmark this page for fast lookups when configuring servers or debugging certificate errors.

For a step-by-step walkthrough of the handshake, see the SSL/TLS Handshake Explained guide. To inspect a live certificate, use the SSL Checker.

TLS Handshake: 1.2 vs 1.3

TLS 1.2 Handshake (2 round trips)

Client                                Server
------                                ------
ClientHello          ───────────────▶          (versions, cipher suites,
                                                SNI, random)
                     ◀───────────────  ServerHello
                     ◀───────────────  Certificate
                     ◀───────────────  ServerKeyExchange (ECDHE params)
                     ◀───────────────  ServerHelloDone
ClientKeyExchange    ───────────────▶
ChangeCipherSpec     ───────────────▶
Finished (encrypted) ───────────────▶
                     ◀───────────────  ChangeCipherSpec
                     ◀───────────────  Finished (encrypted)
Application data     ◀──────────────▶  Application data

Two full round trips (2-RTT) before application data flows. The certificate is sent in plaintext.

TLS 1.3 Handshake (1 round trip)

Client                                Server
------                                ------
ClientHello          ───────────────▶          (+ key_share: client guesses
                                                the key exchange group)
                     ◀───────────────  ServerHello (+ key_share)
                     ◀───────────────  {EncryptedExtensions}
                     ◀───────────────  {Certificate}
                     ◀───────────────  {CertificateVerify}
                     ◀───────────────  {Finished}
{Finished}           ───────────────▶
Application data     ◀──────────────▶  Application data

{braces} = encrypted with handshake keys

Key differences in TLS 1.3:

FeatureTLS 1.2TLS 1.3
Round trips to first byte2-RTT1-RTT (0-RTT with resumption)
Key exchangeRSA, DHE, ECDHE(EC)DHE only — forward secrecy mandatory
Certificate visibilitySent in plaintextEncrypted
Cipher modesCBC, GCM, othersAEAD only (GCM, CCM, ChaCha20-Poly1305)
Session resumptionSession IDs / ticketsPSK-based, optional 0-RTT
Renegotiation, compressionAllowedRemoved
Cipher suite countHundreds definedFive

0-RTT caveat: TLS 1.3 early data (0-RTT) is replayable. Only allow it for idempotent requests (GET), never for state-changing operations.

Cipher Suite Notation Explained

A TLS 1.2 cipher suite name encodes four algorithms:

TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
    ─────  ───      ───────────  ──────
      │     │            │          │
      │     │            │          └─ Hash: SHA-384 (PRF / HMAC)
      │     │            └─ Bulk cipher: AES, 256-bit key, GCM mode
      │     └─ Authentication: RSA (certificate key type)
      └─ Key exchange: Elliptic-Curve Diffie-Hellman, Ephemeral
ComponentCommon ValuesWhat It Does
Key exchangeECDHE, DHE, RSAHow the session key is agreed. Ephemeral (E) variants give forward secrecy; plain RSA key exchange does not.
AuthenticationRSA, ECDSAThe certificate's key type, used to prove server identity.
Bulk cipherAES_128_GCM, AES_256_GCM, CHACHA20_POLY1305, AES_128_CBCEncrypts application data. AEAD modes (GCM, Poly1305) are preferred; CBC is legacy.
HashSHA256, SHA384Used in the PRF for key derivation (and HMAC in CBC suites).

TLS 1.3 suites name only the AEAD cipher and hash, because key exchange and authentication are negotiated separately:

TLS_AES_128_GCM_SHA256
TLS_AES_256_GCM_SHA384
TLS_CHACHA20_POLY1305_SHA256
TLS_AES_128_CCM_SHA256
TLS_AES_128_CCM_8_SHA256

Nginx Example

ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305:DHE-RSA-AES128-GCM-SHA256:DHE-RSA-AES256-GCM-SHA384;
ssl_prefer_server_ciphers off;
ssl_session_timeout 1d;
ssl_session_cache shared:SSL:10m;
ssl_session_tickets off;

Avoid: anything with RC4, 3DES, MD5, SHA1 (as MAC), NULL, EXPORT, aNULL, or static RSA/DH key exchange.

Note: all types provide identical encryption strength. Browsers validate hostnames against the SAN list, not the Subject CN — every modern certificate is technically a SAN certificate. Check what's in yours with the SSL Checker.

Certificate File Formats

FormatExtensionsEncodingUsed By
PEM.pem .crt .cer .keyBase64 text with -----BEGIN/END----- markers; multiple blocks per file allowedApache, Nginx, HAProxy, OpenSSL, most Unix tools
DER.der .cerRaw binary ASN.1; one object per fileJava keystores, some Windows contexts
PKCS#12.pfx .p12Password-protected binary container: cert + chain + private keyWindows IIS, code signing, import/export between systems
PKCS#7.p7b .p7cCert + chain only, no private keyWindows, Java Tomcat chain bundles

PEM block markers you'll encounter:

-----BEGIN CERTIFICATE-----            # X.509 certificate
-----BEGIN CERTIFICATE REQUEST-----    # CSR (decode with the CSR Decoder)
-----BEGIN PRIVATE KEY-----            # PKCS#8 private key (unencrypted)
-----BEGIN ENCRYPTED PRIVATE KEY-----  # PKCS#8 private key (encrypted)
-----BEGIN RSA PRIVATE KEY-----        # legacy PKCS#1 RSA key
-----BEGIN EC PRIVATE KEY-----         # legacy SEC1 EC key
-----BEGIN PUBLIC KEY-----             # public key (decode with the Public Key Decoder)

Paste any CSR into the CSR Decoder or any public key into the Public Key Decoder to inspect the contents without OpenSSL.

OpenSSL Command Reference

Generate Keys and CSRs

# Generate a 2048-bit RSA private key
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out key.pem

# Generate an EC P-256 private key (smaller, faster)
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out key.pem

# Create a CSR from an existing key
openssl req -new -key key.pem -out req.csr \
  -subj "/CN=example.com" \
  -addext "subjectAltName=DNS:example.com,DNS:www.example.com"

# Key + CSR in one command
openssl req -new -newkey rsa:2048 -nodes -keyout key.pem -out req.csr

# Self-signed certificate (testing only)
openssl req -x509 -newkey rsa:2048 -nodes -keyout key.pem \
  -out cert.pem -days 365 -subj "/CN=localhost"

Inspect Certificates and CSRs

# Print certificate details
openssl x509 -in cert.pem -noout -text

# Just the expiry dates
openssl x509 -in cert.pem -noout -dates

# Subject, issuer, and SANs
openssl x509 -in cert.pem -noout -subject -issuer -ext subjectAltName

# Inspect a CSR
openssl req -in req.csr -noout -text

# Verify a cert chains to a CA bundle
openssl verify -CAfile chain.pem cert.pem

# Check that key, cert, and CSR match (compare the hashes)
openssl x509 -in cert.pem -noout -pubkey | openssl sha256
openssl pkey -in key.pem -pubout | openssl sha256
openssl req  -in req.csr -noout -pubkey | openssl sha256

Convert Formats

# PEM → DER
openssl x509 -in cert.pem -outform DER -out cert.der

# DER → PEM
openssl x509 -in cert.der -inform DER -out cert.pem

# PEM (cert + key + chain) → PKCS#12
openssl pkcs12 -export -in cert.pem -inkey key.pem \
  -certfile chain.pem -out bundle.pfx

# PKCS#12 → PEM
openssl pkcs12 -in bundle.pfx -out everything.pem -nodes

# PKCS#7 → PEM
openssl pkcs7 -in bundle.p7b -print_certs -out chain.pem

Test Live Connections

# Basic TLS connection test (always send SNI with -servername)
openssl s_client -connect example.com:443 -servername example.com

# Show the full certificate chain
openssl s_client -connect example.com:443 -servername example.com -showcerts

# Force a specific protocol version
openssl s_client -connect example.com:443 -tls1_2
openssl s_client -connect example.com:443 -tls1_3

# Check expiry of a live certificate
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -dates

# Test SMTP with STARTTLS
openssl s_client -connect mail.example.com:587 -starttls smtp

HSTS — HTTP Strict Transport Security

HSTS is a response header that forces browsers to use HTTPS for all future requests to the domain.

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
DirectiveMeaning
max-age=31536000Enforce HTTPS for this many seconds (1 year). Required.
includeSubDomainsApply the policy to every subdomain too.
preloadSignals eligibility for the browser preload list at hstspreload.org — browsers then enforce HTTPS even on the first-ever visit.

Warning: preload is effectively permanent — removal from the list takes months. Confirm every subdomain serves valid HTTPS before submitting. Check your current headers with the Security Headers checker.

CAA Records

A CAA DNS record restricts which Certificate Authorities may issue certificates for your domain. CAs are required to check it before issuance.

; Only Let's Encrypt may issue certs
example.com.  CAA  0 issue "letsencrypt.org"

; Allow a CA to issue wildcards
example.com.  CAA  0 issuewild "letsencrypt.org"

; Forbid all issuance
example.com.  CAA  0 issue ";"

; Get notified of policy violations
example.com.  CAA  0 iodef "mailto:security@example.com"

Full syntax for CAA and every other record type is in the DNS Records Cheat Sheet.

Frequently Asked Questions

Is SSL different from TLS?

SSL (Secure Sockets Layer) is the obsolete predecessor of TLS (Transport Layer Security). Every modern "SSL certificate" actually secures TLS connections — the old name simply stuck. SSL 2.0/3.0 are prohibited by RFC; only TLS 1.2 and 1.3 should be enabled today.

What is forward secrecy?

Forward secrecy means each session uses a unique, ephemeral key (via ECDHE/DHE), so a future compromise of the server's private key cannot decrypt previously recorded traffic. TLS 1.3 makes it mandatory; in TLS 1.2 you get it by preferring ECDHE suites and avoiding plain RSA key exchange.

What is SNI and why does it matter?

Server Name Indication is a ClientHello extension that tells the server which hostname the client wants, so one IP can serve many certificates. Tools that skip SNI (e.g., openssl s_client without -servername) often receive the wrong or default certificate, producing misleading hostname-mismatch errors.

How long can a certificate be valid?

Publicly trusted certificates are capped at 398 days, and the CA/Browser Forum has scheduled further reductions (200 days in 2026, stepping down to 47 days by 2029). Automate renewal — manual processes are the leading cause of expired-certificate outages.

RSA or ECDSA certificates?

ECDSA (P-256) keys are far smaller than RSA-2048 with comparable security, making handshakes faster. All modern browsers support ECDSA; some servers deploy dual certificates and let cipher negotiation pick. For new deployments, ECDSA is a sound default.
