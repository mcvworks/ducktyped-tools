HMAC Explained: Keyed Hashing for Message Authentication

Last updated: June 11, 2026

Understand what HMAC adds on top of a plain hash, how the RFC 2104 construction actually works, which algorithm to choose, and how HMAC powers API request signing, webhook verification, and token integrity.

HMAC vs a Plain Hash

A cryptographic hash like SHA-256 takes any input and produces a fixed-size digest. It proves integrity: change one bit of the input and the digest changes completely. What it does not prove is authenticity. Anyone can compute SHA-256("amount=100"), so an attacker who tampers with a message can simply recompute the hash to match. A bare hash tells you the data is consistent with itself -- not who produced it.

HMAC (Hash-based Message Authentication Code) fixes this by mixing a secret key into the computation. Only parties holding the key can produce a valid code, and only they can verify one. That single change upgrades the guarantee from "this data was not corrupted" to "this data was not corrupted and it came from someone who knows the secret."

SHA-256("amount=100")
  → anyone can compute, anyone can forge

HMAC-SHA256(secret, "amount=100")
  → only key holders can compute or verify

For password storage, file checksums, or deduplication, a plain hash is the right tool -- see the Hashing guide. The moment a message crosses a trust boundary and you need to know who sent it, you need HMAC (or an asymmetric signature).

How the HMAC Construction Works

The obvious approach -- hash(secret + message) -- is broken. Merkle-Damgård hashes such as SHA-256 and SHA-1 suffer from length-extension attacks: given hash(secret + message), an attacker can compute a valid hash(secret + message + padding + extra) without ever knowing the secret, appending data to a "signed" message.

HMAC, defined in RFC 2104, defeats this with a nested, two-pass construction:

HMAC(K, m) = H( (K' ⊕ opad) || H( (K' ⊕ ipad) || m ) )

where:
  H     = the underlying hash (e.g. SHA-256)
  K'    = the key, hashed if longer than the block size,
          then zero-padded to the block size (64 bytes for SHA-256)
  ipad  = the byte 0x36 repeated to the block size
  opad  = the byte 0x5c repeated to the block size
  ||    = concatenation, ⊕ = XOR

The message is hashed once with the inner key (K' ⊕ ipad), then that digest is hashed again with the outer key (K' ⊕ opad). Because the attacker never sees the inner digest and the outer pass re-keys the result, length extension is impossible. The construction is also remarkably robust: HMAC remains secure even against some weaknesses in the underlying hash, which is why HMAC-SHA1 is not broken despite SHA-1's collision attacks.

Key length matters less than you might think -- HMAC handles keys of any length -- but entropy matters a lot. Use a randomly generated key of at least the hash's output size (32 bytes for SHA-256), not a human-chosen passphrase.

Choosing an Algorithm: SHA-256 vs SHA-1 vs MD5

HMAC is a construction, not an algorithm -- you pair it with a hash function, and that choice determines output size and long-term safety:

  • HMAC-SHA256 -- the modern default. 256-bit (32-byte) output, fast on all platforms, universally supported. Use it for anything new. HMAC-SHA384 and HMAC-SHA512 offer larger margins where policy requires them.
  • HMAC-SHA1 -- 160-bit output. SHA-1 collisions do not directly break HMAC-SHA1, so legacy integrations (older webhook APIs, TOTP per RFC 6238) still work safely. But SHA-1 is deprecated, many compliance regimes (PCI DSS, FIPS) restrict it, and there is no reason to choose it for new designs.
  • HMAC-MD5 -- 128-bit output over a thoroughly broken hash. While the HMAC wrapper masks MD5's collision weakness, the safety margin is gone. Treat it as legacy-only and migrate anything still using it.

Rule of thumb: SHA-256 for everything new; SHA-1 and MD5 only when a legacy peer forces your hand.

Use Case: API Request Signing

HMAC is the backbone of keyed API authentication. Instead of sending a bearer secret with every call, the client signs a canonical representation of the request -- method, path, timestamp, and body -- and sends only the signature:

string_to_sign = METHOD + "\n" + PATH + "\n" + TIMESTAMP + "\n" + sha256(BODY)
signature      = hex( HMAC-SHA256(api_secret, string_to_sign) )

GET /v1/orders HTTP/1.1
X-Timestamp: 1781136000
X-Signature: 7f1d6a3e9b...

The server reconstructs the same string and recomputes the HMAC; a mismatch means the request was tampered with or signed by the wrong key. AWS Signature Version 4 is the best-known production example of this pattern. Including the timestamp in the signed string (and rejecting stale ones) blocks replay attacks, since an intercepted request expires within minutes.

Use Case: Webhook Verification and Token Integrity

Webhooks are the most common place developers meet HMAC today. When Stripe, GitHub, or Slack POSTs an event to your endpoint, anyone on the internet could send a request that looks identical -- so the provider includes an HMAC of the payload computed with your shared webhook secret:

X-Hub-Signature-256: sha256=a0b1c2d3...   (GitHub)
Stripe-Signature: t=1781136000,v1=5257a8...  (Stripe, timestamp included)

// Your server:
expected = HMAC-SHA256(webhook_secret, raw_request_body)
if !constant_time_equal(expected, received_signature): reject(401)

Two implementation details matter. Verify against the raw request body bytes, before any JSON parsing or re-serialization changes whitespace or key order. And compare signatures with a constant-time comparison (crypto.timingSafeEqual, hmac.compare_digest) -- an early-exit string comparison leaks timing information an attacker can exploit byte by byte.

Token integrity is the same idea applied to credentials you hand out. A JWT signed with HS256 is exactly an HMAC-SHA256 over the encoded header and payload, and signed session cookies in frameworks like Django and Rails append an HMAC so the server can detect client-side edits. If you can forge the HMAC, you can forge the session -- which is why these secrets deserve the same protection as database passwords.
