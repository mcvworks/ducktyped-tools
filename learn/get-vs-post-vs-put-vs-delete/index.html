HTTP Methods — GET vs POST vs PUT vs PATCH vs DELETE

Last updated: July 2, 2026

Each HTTP method has a semantic meaning in REST APIs. Choosing the right method prevents bugs, enables caching, and makes APIs predictable and discoverable.

To build and test requests, use the HTTP Request Builder. For status code details, see HTTP Status Codes.

Key Definitions

Safe

The method doesn't modify server state — it only reads. GET is the only safe method. A safe request can be repeated unlimited times with no side effects.

Idempotent

Making the same request multiple times has the same effect as making it once. GET, PUT, and DELETE are idempotent. POST is not — each POST creates a new resource. Example: calling DELETE /resource/123 five times always results in the resource being deleted (idempotent); the 2nd–5th calls return 404, which is fine.

Cacheable

Caches (browser, CDN, proxy) can store the response and reuse it. GET is cacheable by default. POST is technically cacheable but rarely cached in practice unless cache headers explicitly say so. PUT, PATCH, DELETE are not cacheable.

Detailed Methods

GET — Retrieve a Resource

Semantic: Read-only, no side effects.

Usage: Fetch a single resource, list resources (with query parameters for filtering), download a file.

Example:

GET /api/users/123
GET /api/users?role=admin&status=active

Response: 200 OK with resource in body, or 404 Not Found.

Note: Query parameters go in the URL, not the body. Avoid GET requests with side effects (e.g., <a href="/api/delete?id=123"> is bad design).

POST — Create a Resource or Trigger an Action

Semantic: Non-idempotent, creates or triggers something.

Usage: Create a new resource, submit a form, trigger a one-time action (send email, generate report), file upload.

Example:

POST /api/users
Content-Type: application/json

{"name":"Alice","email":"alice@example.com"}

Response: 201 Created (with Location header pointing to new resource) or 200 OK.

Important: Each POST creates a new resource (non-idempotent). Calling the same request twice creates two resources. For idempotent creation, use PUT.

PUT — Replace Entire Resource

Semantic: Idempotent complete replacement. The request body defines the full new state.

Usage: Replace a resource with a new version. Create or update idempotently using a client-specified ID.

Example:

PUT /api/users/123
Content-Type: application/json

{"name":"Alice","email":"alice@example.com","role":"admin"}

Key rule: If you omit a field, it's set to null/deleted. The request body is the complete resource state. Don't send it twice — the result is the same.

Response: 200 OK (with updated resource), 201 Created (if the resource didn't exist), or 204 No Content.

PATCH — Partial Update

Semantic: Apply partial changes. Unspecified fields remain unchanged.

Usage: Update one or two fields without replacing the entire resource.

Example:

PATCH /api/users/123
Content-Type: application/json

{"role":"admin"}

Result: Only the role field is updated; other fields stay as they were.

Caveat: PATCH semantics are less standardized (RFC 6902 JSON Patch, RFC 7386 JSON Merge Patch). Check API documentation. Many APIs prefer PUT for simplicity.

Response: 200 OK or 204 No Content.

DELETE — Remove a Resource

Semantic: Idempotent removal.

Usage: Delete a resource.

Example:

DELETE /api/users/123

Idempotent: Calling DELETE /users/123 five times has the same effect as calling it once. First call deletes, 2nd–5th return 404 (acceptable).

Response: 200 OK (with confirmation), 204 No Content (no response body), or 404 Not Found.

Note: Some APIs allow a body on DELETE for specifying which items to delete (e.g., bulk delete). This is non-standard — use POST for bulk operations instead.

Understanding Idempotency

Idempotent means "same result from one or many calls." This is critical for reliability:

  • GET: Reading data multiple times returns the same data (idempotent).
  • PUT: Replacing a resource with the same data multiple times results in the same state (idempotent).
  • DELETE: Deleting a resource multiple times results in deletion (idempotent — 2nd+ calls return 404, which is acceptable).
  • POST: Creating a new resource multiple times creates multiple resources (NOT idempotent).

Why it matters: Networks are unreliable. If a request times out, was it processed? Idempotent methods are safe to retry. Non-idempotent methods (POST) need deduplication or idempotency keys.

Common API Design Mistakes

1. GET with Side Effects

Mistake: <a href="/api/delete?id=123">Delete</a> or GET /api/send-email?to=user@example.com

Problem: Caches, crawlers, and proxies will fetch the URL, triggering the side effect unintentionally.

Solution: Use POST or DELETE for operations that change state.

2. POST for Idempotent Operations

Mistake: POST /api/pay with the same transaction ID multiple times.

Problem: Each POST creates a new payment. Without idempotency keys, retrying failed requests double-charges.

Solution: Use PUT (idempotent) or add deduplication (idempotency keys).

3. PUT vs PATCH Confusion

Mistake: Sending partial data to a PUT endpoint and expecting unmentioned fields to stay unchanged.

Problem: PUT replaces the entire resource — omitted fields are deleted/nulled.

Solution: Send the complete resource to PUT, use PATCH for partial updates, or document your PUT endpoint behavior clearly.

4. DELETE with Request Body

Mistake: DELETE /api/users with body <ids in JSON>

Problem: Most HTTP clients, caches, and proxies don't support bodies on DELETE. The request may be silently truncated or rejected.

Solution: Use POST /api/users/bulk-delete or DELETE /api/users?id=123&id=456 (query params).

Status Codes by Method

GET: 200 (success), 404 (not found), 301/302 (redirect).

POST: 201 (created), 200 (okay), 400 (bad request), 409 (conflict).

PUT: 200 (updated), 201 (created), 204 (no content), 400 (bad request).

PATCH: 200 (updated), 204 (no content), 400 (bad request).

DELETE: 200 (deleted), 204 (no content), 404 (not found).
