Webhooks Explained

Last updated: June 11, 2026

Understand how webhooks deliver events between systems, how to test handlers with capture endpoints and sample payloads, how to verify HMAC signatures from Stripe, GitHub, and Shopify, and how to survive retries with idempotent handlers.

What Is a Webhook?

A webhook is an HTTP request — almost always a POST with a JSON body — that one system sends to another when an event occurs. Instead of your application repeatedly polling an API asking "did anything change?", the provider pushes the event to a URL you register, the moment it happens. A payment succeeds, Stripe calls your endpoint. Code is pushed, GitHub calls your endpoint. An order is created, Shopify calls your endpoint.

This inverts the usual client-server relationship: your application becomes the server, and the third-party provider becomes the client. A typical webhook delivery looks like this on the wire:

POST /webhooks/stripe HTTP/1.1
Host: api.yourapp.com
Content-Type: application/json
Stripe-Signature: t=1718064000,v1=5257a869e7ecebeda32affa62cdca3fa51cad7e77a0e56ff536d0ce8e108d8bd

{
  "id": "evt_1PQrstuv",
  "object": "event",
  "type": "payment_intent.succeeded",
  "data": { "object": { "id": "pi_3PQ...", "amount": 2000, "currency": "usd" } }
}

Your handler is expected to respond quickly with a 2xx status code to acknowledge receipt. Anything else — a timeout, a 4xx, a 5xx — is treated as a failed delivery, and most providers will retry.

How to Test Webhooks

Webhooks are awkward to test because the sender is an external service and the receiver is often code running on your laptop. Three techniques cover almost every situation.

Capture Endpoints

A capture endpoint is a temporary URL that accepts any request and displays exactly what arrived: method, headers, and raw body. Point a provider's webhook configuration at a capture URL, trigger the event, and inspect the delivery. This answers the questions documentation often leaves vague — what the exact header names are, whether the body is JSON or form-encoded, and what the payload structure really looks like in your account.

Inspecting and Replaying Payloads

Once you know the payload shape, you do not need the real provider for every test cycle. Save a captured payload (or generate a realistic sample with the duckTyped Webhook Payload Builder) and replay it against your local handler with curl:

curl -X POST http://localhost:3000/webhooks/github \
  -H 'Content-Type: application/json' \
  -H 'X-GitHub-Event: push' \
  -H 'X-Hub-Signature-256: sha256=<computed-hmac>' \
  -d @sample-push-payload.json

This gives you a fast, repeatable feedback loop: edit the handler, replay the payload, check the result — no waiting for a real event to fire.

Triggering Real Events

Before shipping, always run at least one end-to-end test with the real provider in test mode. Stripe's CLI can trigger events on demand (stripe trigger payment_intent.succeeded), GitHub lets you redeliver any past webhook from the repository settings page, and Shopify lets you send test notifications from the admin. Real deliveries catch the things replays miss: TLS issues, header casing, and signature mismatches.

Verifying Webhook Signatures

A webhook endpoint is a publicly reachable URL that mutates state in your system — anyone who discovers it can POST forged events. The standard defense is an HMAC signature: the provider computes a keyed hash of the request body using a secret only you and the provider know, and sends it in a header. Your handler recomputes the HMAC and compares. Each major provider does this slightly differently:

  • Stripe — header Stripe-Signature, containing a timestamp (t=) and an HMAC-SHA256 (v1=) of "{timestamp}.{body}", hex-encoded. The timestamp lets you reject old deliveries and defeat replay attacks.
  • GitHub — header X-Hub-Signature-256, an HMAC-SHA256 of the raw body, hex-encoded and prefixed with sha256=.
  • Shopify — header X-Shopify-Hmac-Sha256, an HMAC-SHA256 of the raw body, Base64-encoded (not hex).

A GitHub-style verification in Node.js looks like this:

const crypto = require('crypto');

function verifyGithubSignature(rawBody, signatureHeader, secret) {
  const expected = 'sha256=' + crypto
    .createHmac('sha256', secret)
    .update(rawBody)           // raw bytes, NOT re-serialized JSON
    .digest('hex');
  return crypto.timingSafeEqual(
    Buffer.from(expected),
    Buffer.from(signatureHeader)
  );
}

Two mistakes account for nearly every "signature mismatch" bug. First, always hash the raw request body — if your framework parses JSON and you re-serialize it, key ordering and whitespace changes will produce a different digest. Second, use a constant-time comparison (like crypto.timingSafeEqual) instead of === to avoid timing side channels. You can experiment with HMAC computation interactively using the HMAC Generator.

Retries and Idempotency

Webhook delivery runs over the public internet, so failures are normal: your server restarts mid-request, a load balancer times out, a deploy returns 503 for thirty seconds. Providers handle this by retrying failed deliveries, usually with exponential backoff — Stripe retries for up to three days, GitHub redelivers on request, and Shopify retries 19 times over roughly 48 hours before disabling the subscription.

The consequence: the same event can arrive more than once, and your handler must behave correctly when it does. This property is called idempotency. The standard pattern is to record each processed event ID and skip duplicates:

app.post('/webhooks/stripe', async (req, res) => {
  const event = req.body;
  const seen = await db.events.findOne({ id: event.id });
  if (seen) return res.sendStatus(200);   // duplicate — acknowledge, do nothing

  await db.events.insert({ id: event.id });
  await handleEvent(event);               // safe to run exactly once
  res.sendStatus(200);
});

Two more rules keep retry behavior sane. Respond fast: acknowledge with a 200 immediately and do heavy work (emails, PDF generation, downstream API calls) in a background queue, because slow responses get treated as failures and trigger retries. And never rely on delivery order — retries and parallel delivery mean events can arrive out of sequence, so fetch the current state from the provider's API when ordering matters.

Local Development Tunneling

Providers can only deliver webhooks to a public URL, but your handler runs on localhost. Tunneling tools bridge the gap by giving your local port a temporary public address:

# ngrok: expose local port 3000 at a public https URL
ngrok http 3000
# → Forwarding https://a1b2c3.ngrok-free.app -> http://localhost:3000

# cloudflared: same idea, no account required for quick tunnels
cloudflared tunnel --url http://localhost:3000

# Stripe CLI: provider-specific forwarding with signature support
stripe listen --forward-to localhost:3000/webhooks/stripe

Register the tunnel URL as your webhook endpoint in the provider's dashboard, trigger test events, and watch real deliveries hit your local debugger. Note that free tunnel URLs change on every restart, so you will need to update the provider configuration each session — or use a provider CLI like Stripe's, which forwards events without any dashboard changes and prints a signing secret for local verification.

How to Use the Tool

The duckTyped Webhook Payload Builder generates correctly structured sample payloads so you can exercise handlers without waiting for real events:

  1. Pick a service and event — GitHub (push, pull_request, issues, release), Stripe (payment_intent.succeeded, charge.succeeded, invoice.paid, customer.created), Slack, Discord, or a generic payload.
  2. Generate and edit — the tool produces a realistic JSON payload you can tweak to match your test case, then copy.
  3. Sign it — enter your webhook secret and the tool computes an HMAC-SHA256 signature (sha256=...) over the payload, ready to paste into a signature header.

Everything runs entirely in your browser using the Web Crypto API — payloads and secrets are never sent to a server.
