Redirect Status Codes — 301 vs 302 vs 307 vs 308

Last updated: July 2, 2026

Not all redirects are the same. Each status code tells browsers and search engines something different about the permanence and method preservation. Choose the right one to avoid SEO penalties and broken form submissions.

To trace redirect chains before deploying, use the Redirect Checker. For individual status code descriptions, see HTTP Status Codes.

Decision Flowchart

Start: Is this redirect permanent or temporary?

  • Permanent?
    • Does the HTTP method (GET, POST, PUT, DELETE) matter?
      • Yes (API, form, mutation): Use 308 (Permanent Redirect)
      • No (GET request, browsing): Use 301 (Moved Permanently)
  • Temporary?
    • Does the HTTP method matter?
      • Yes (POST, PUT, mutation): Use 307 (Temporary Redirect)
      • No (GET request, browsing): Use 302 (Found)

Why Method Preservation Matters

By HTTP spec, 301 and 302 traditionally downgrade POST requests to GET. This breaks form submissions and API mutations.

Example (301 POST problem):

  1. Client POSTs data to example.com/api/users (create user)
  2. Server responds with 301 Location: /users/v2 (endpoint migrated)
  3. Browser follows with GET to example.com/api/users/v2 (body dropped!)
  4. Server can't create user because data is gone — request fails

Solution: Use 307 (temporary) or 308 (permanent) to guarantee method and body preservation.

Common Mistakes

1. Using 302 for Permanent Moves

If you're moving your site and redirect with 302, search engines won't transfer SEO equity to the new URL. Users' bookmarks will still point to the old domain. Use 301 or 308 instead.

2. Forgetting POST Requests Downgrade on 301/302

If you have an API endpoint or form handler on the old URL and redirect with 301 or 302, POST requests will silently become GET requests. The form data is lost, and mutations fail. Use 308 for permanent, 307 for temporary.

3. Redirect Loops

If A redirects to B and B redirects back to A, the browser hits redirect-loop limits and shows an error. Check your redirects carefully:

  • Old URL should redirect to new, but new URL must NOT redirect back
  • Reverse proxies can create loops if misconfigured (catch-all redirects, middleware order)
  • Use the Redirect Checker to trace chains

4. Redirecting to the Same Host/Port by Accident

Misconfigured redirects can point to themselves. Check your Location header points somewhere different.

When to Use Each Code

301 — Moved Permanently (Classic Permanent Redirect)

Use for permanent URL changes where the HTTP method doesn't matter (mostly GET requests). Examples: site migrations, renaming a page, deprecating an endpoint.

Note: Newer systems should prefer 308 because it handles POST better.

302 — Found (Classic Temporary Redirect)

Use for temporary redirects expected to revert. Examples: maintenance redirects, A/B testing, feature flags, temporary URL aliases.

Caveat: Modern browsers may cache aggressively. For guaranteed non-caching, consider 307.

307 — Temporary Redirect (Modern Temporary, Method-Preserving)

Guarantees the method and body survive the redirect. Use for temporary API reroutes, temporary form handlers, or any mutation that's expected to revert.

308 — Permanent Redirect (Modern Standard)

The modern best practice for all permanent redirects. Unlike 301, it preserves POST/PUT/DELETE. Use this by default for permanent moves unless you have compatibility concerns with very old clients.

Caching Behavior

301 and 308 are cacheable by default — browsers and proxies remember the redirect. This is good for performance but means:

  • Once cached, a user won't check the old URL again
  • Hard-refresh (Ctrl+Shift+R) bypasses the cache
  • CDNs and proxies also cache these redirects — plan accordingly

302 and 307 are NOT cached (unless cache headers say otherwise) — each request checks the server, which is safer for temporary situations.
