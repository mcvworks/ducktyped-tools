SSL Certificate Expired: How to Fix It Fast

Last updated: April 5, 2026

Your visitors are seeing a scary browser warning and your API consumers are getting connection errors. An expired TLS certificate is both very serious (your site is effectively offline over HTTPS) and very easy to fix. This guide shows you exactly how to confirm the problem, renew the certificate, verify the fix, and set up automatic renewal so it never happens again.

What's Happening

Every TLS certificate has a fixed validity period — usually 90 days for Let's Encrypt, or 1 year for most commercial CAs. Once the expiration date passes, browsers treat the certificate as untrusted and show warnings like:

  • Chrome/Edge: "Your connection is not private" with error code NET::ERR_CERT_DATE_INVALID
  • Firefox: "Warning: Potential Security Risk Ahead" (SEC_ERROR_EXPIRED_CERTIFICATE)
  • Safari: "This Connection Is Not Private"
  • curl / command line: SSL certificate problem: certificate has expired

Related error pages: SSL Certificate Expired, NET::ERR_CERT_DATE_INVALID.

Step 1 — Confirm the Certificate Is Actually Expired

Before touching any config, run the SSL Certificate Checker on your domain. It shows the issuer, Common Name, Subject Alternative Names, full certificate chain, expiration date, and TLS configuration. If the tool reports the certificate expired, you have your answer.

If the tool says the certificate is valid but users still see warnings, the problem isn't expiration — it's one of these lookalikes:

  • Wrong hostname — the certificate covers example.com but users are visiting www.example.com (or vice versa).
  • Incomplete chain — your server isn't sending the intermediate certificate. Some browsers tolerate this via AIA fetching, others don't.
  • Client clock is wrong — if a user's computer clock is set incorrectly, valid certificates appear expired on their end only.
  • Certificate not yet valid — a "not yet valid" error means the server clock is behind or the cert's notBefore date is in the future.

Step 2 — Renew the Certificate

How you renew depends on where the certificate came from.

Let's Encrypt (Free, 90-day certificates)

Most modern sites use Let's Encrypt via an ACME client. To renew manually:

# certbot
sudo certbot renew
sudo systemctl reload nginx   # or apache2, caddy, etc.

# acme.sh
acme.sh --renew -d example.com --force
systemctl reload nginx

If the renewal fails, the error in the certbot log is almost always one of: HTTP-01 challenge can't reach port 80 (firewall), DNS-01 challenge can't update DNS, CAA record blocks Let's Encrypt, or the account key is missing. Fix the underlying issue and re-run.

Caddy (automatic)

Caddy renews automatically as long as it's running and can reach the CA. If your Caddy certificate is expired, the daemon is probably not running — check with systemctl status caddy and review logs.

Commercial CA (DigiCert, Sectigo, GoDaddy, GlobalSign, etc.)

  1. Log into your CA's control panel and order a renewal.
  2. Generate a new CSR on your server (or reuse the existing key and CSR — your CA's docs will specify).
  3. Submit the CSR; the CA validates domain ownership and issues the new certificate.
  4. Download the certificate plus the intermediate chain.
  5. Install both on your server in the correct location (e.g., /etc/nginx/ssl/, /etc/letsencrypt/live/example.com/, or your load balancer's cert store).
  6. Reload the web server, load balancer, or CDN.

If you need to inspect a CSR before submitting it, use the CSR Decoder to verify the Common Name, SANs, and organization fields.

CDN or Managed Hosting (Cloudflare, Fastly, Netlify, Vercel, AWS ACM)

Most CDNs and managed hosts handle TLS for you — an expired certificate means either their automation broke or you're running in a mode that requires manual action (e.g., Cloudflare's "Full (Strict)" mode requires a valid cert on your origin and Cloudflare). Check the provider's dashboard and logs.

Step 3 — Verify the Fix

After installing the renewed certificate, always verify before walking away:

  1. Run the SSL Checker again. Confirm the new expiration date, correct hostname, and complete chain.
  2. Open the site in a private/incognito window (to bypass any browser cache of the old cert warning).
  3. If you use a load balancer or multiple servers, check each backend — certificates need to be updated on all of them, not just one.
  4. If you use HSTS with a long max-age, users who visited before expiration may still see errors until the HSTS cache refreshes.

Step 4 — Set Up Automatic Renewal

If you just renewed manually, the single most important thing you can do next is make sure this never happens again.

Automate with ACME

Certbot installs a systemd timer or cron job by default — verify it's actually running:

systemctl list-timers | grep certbot
# or
sudo crontab -l | grep certbot

Run a dry-run to confirm renewal will succeed when the real renewal fires:

sudo certbot renew --dry-run

Add Expiration Monitoring

Even with auto-renewal, monitor expiration externally. Set up alerts at 30, 14, and 7 days before expiration using:

  • Your existing monitoring platform (Datadog, New Relic, Grafana, Uptime Kuma, etc.) — most have built-in TLS expiration checks.
  • A simple cron job that runs openssl s_client or hits your API and posts to Slack if the cert is close to expiring.
  • Free services like Let's Monitor or ssl-checker.io.

Keep CAA Records Sane

A CAA DNS record that doesn't list your CA will silently block every future renewal. Use the DNS Checker to query your CAA record and confirm it includes the CA you actually use. If you're unsure, remove the CAA record entirely — that allows any CA to issue.

Common Root Causes of Expiration

  • Auto-renewal was never set up — someone ran certbot manually once, forgot to enable the timer.
  • Server was down during renewal window — certbot ran but couldn't complete the HTTP-01 challenge.
  • Port 80 firewall rule — HTTP-01 challenges need port 80 open to the internet, even if you redirect all traffic to HTTPS.
  • CAA record was added after initial issuance — locked out your own CA.
  • DNS provider API key expired — DNS-01 challenges can't update records.
  • Disk full — renewal writes to /etc/letsencrypt/ and fails if the disk is out of space.
  • Service account rotated — the ACME client account key was deleted or the email address bounced, so the CA revoked the account.
