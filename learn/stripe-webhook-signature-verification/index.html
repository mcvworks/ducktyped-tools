Stripe Webhook Signature Verification

Last updated: July 2, 2026

Stripe signs every webhook it sends so your endpoint can prove the event really came from Stripe and was not forged or tampered with. This guide breaks down the Stripe-Signature header, shows verification with the official library and by hand, and fixes the error almost everyone hits first: "No signatures found matching the expected signature for payload." For a broader tour of webhooks in general, see the Webhooks Explained guide — this page focuses specifically on Stripe.

What the Stripe-Signature Header Contains

Every Stripe webhook delivery carries a Stripe-Signature header. It is a comma-separated list of key/value pairs — a timestamp and one or more signatures:

Stripe-Signature: t=1718064000,
  v1=5257a869e7ecebeda32affa62cdca3fa51cad7e77a0e56ff536d0ce8e108d8bd
  • t — the Unix timestamp (in seconds) when Stripe generated the signature. This is what makes replay protection possible.
  • v1 — an HMAC-SHA256, hex-encoded, of the signed payload. There can be more than one v1 value during a signing-secret rotation, and you should accept the delivery if any of them matches.
  • v0 — an older scheme you can ignore for normal verification (the Stripe CLI uses it internally).

The crucial detail is what Stripe actually hashes. The signed payload is not just the JSON body — it is the timestamp, a literal period, and the raw body concatenated together:

signed_payload = t + "." + raw_request_body
signature      = HMAC_SHA256(signing_secret, signed_payload)   // hex-encoded

The signing_secret is the endpoint's secret that starts with whsec_. Get this one wrong, or hash the wrong bytes, and verification fails — the two most common causes are covered below.

Verifying With the Official Library (Recommended)

Unless you have a specific reason not to, use Stripe's SDK. constructEvent parses the header, recomputes the HMAC, does a constant-time comparison, and checks the timestamp tolerance — then returns a typed, trusted event or throws. In Node with Express:

const stripe = require('stripe')(process.env.STRIPE_SECRET_KEY);
const endpointSecret = process.env.STRIPE_WEBHOOK_SECRET;   // the whsec_... value

// express.raw hands your handler the untouched request body (a Buffer)
app.post('/webhooks/stripe',
  express.raw({ type: 'application/json' }),
  (req, res) => {
    const sig = req.headers['stripe-signature'];
    let event;
    try {
      event = stripe.webhooks.constructEvent(req.body, sig, endpointSecret);
    } catch (err) {
      // Verification failed — do NOT trust the payload. Reject it.
      return res.status(400).send('Webhook signature verification failed');
    }

    // From here, `event` is authenticated and safe to act on.
    handleEvent(event);
    res.sendStatus(200);
  });

The Python equivalent is stripe.Webhook.construct_event(payload, sig_header, secret), which raises stripe.error.SignatureVerificationError on failure. In both languages, pass the raw body — request.data in Flask, not request.json.

Verifying by Hand

Sometimes you cannot use the SDK — a lightweight edge function, a language without an official library, or you just want to understand exactly what happens. Here is the full check in plain Node crypto:

const crypto = require('crypto');

function verifyStripeSignature(rawBody, sigHeader, secret, toleranceSec) {
  toleranceSec = toleranceSec || 300;

  // 1. Pull "t" and "v1" out of the header
  const parts = Object.fromEntries(
    sigHeader.split(',').map(function (kv) { return kv.split('='); })
  );
  const timestamp = parts.t;
  const signature = parts.v1;

  // 2. Recompute HMAC-SHA256 over "{timestamp}.{rawBody}"
  const signedPayload = timestamp + '.' + rawBody;   // rawBody = exact bytes received
  const expected = crypto
    .createHmac('sha256', secret)
    .update(signedPayload, 'utf8')
    .digest('hex');

  // 3. Constant-time compare (never use ===)
  const ok = crypto.timingSafeEqual(
    Buffer.from(expected),
    Buffer.from(signature)
  );

  // 4. Reject stale deliveries to defeat replay attacks
  const age = Math.floor(Date.now() / 1000) - Number(timestamp);
  return ok && age <= toleranceSec;
}

And the same thing in Python with only the standard library:

import hmac, hashlib, time

def verify_stripe_signature(raw_body: bytes, sig_header: str, secret: str, tolerance=300):
    parts = dict(p.split('=', 1) for p in sig_header.split(','))
    signed_payload = parts['t'].encode() + b'.' + raw_body   # bytes, not str
    expected = hmac.new(secret.encode(), signed_payload, hashlib.sha256).hexdigest()

    fresh = abs(time.time() - int(parts['t'])) <= tolerance
    return fresh and hmac.compare_digest(expected, parts['v1'])

You can reproduce exactly this HMAC-SHA256 computation interactively — paste a signed payload and secret — with the HMAC Generator to confirm your code and Stripe agree byte for byte.

Fixing "No signatures found matching the expected signature for payload"

This is the single most common Stripe webhook error, and it nearly always comes down to one of three causes.

1. You are not hashing the raw body

This accounts for the large majority of cases. If a body-parsing middleware reads the request and hands you a parsed object, the raw bytes are gone. Re-serializing that object produces different whitespace and key ordering, so your HMAC can never match Stripe's. In Express, the fix is to use express.raw() on the webhook route only:

// WRONG — express.json() consumes the stream and reparses it:
app.use(express.json());
app.post('/webhooks/stripe', (req, res) => {
  // req.body is a JS object now; the exact bytes Stripe signed are lost.
});

// RIGHT — capture the raw Buffer just for this route:
app.post('/webhooks/stripe',
  express.raw({ type: 'application/json' }),   // req.body is a Buffer
  handler);

Other frameworks have the same trap: use request.data (not request.json) in Flask, await request.body() in FastAPI, and disable automatic body parsing on the route in Next.js API routes.

2. Wrong signing secret

The secret must be the one for this specific endpoint. Common mix-ups:

  • Using your API secret key (sk_...) instead of the webhook signing secret (whsec_...). They are different values.
  • Using the Dashboard endpoint secret while testing through the Stripe CLI, which prints its own separate whsec_ when you run stripe listen.
  • Mixing test-mode and live-mode secrets — each mode has its own.
  • Having several endpoints and pasting the wrong one. Each endpoint you create in the Dashboard has a distinct secret.

3. Timestamp outside the tolerance zone

If verification instead fails with "Timestamp outside the tolerance zone," the delivery's t= value is too far from your server's clock. Either you are replaying an old captured request, or your server clock has drifted — make sure NTP is running. During legitimate testing you can widen the tolerance, but do not disable the timestamp check in production, since it is what stops replay attacks.

Testing Verification Locally

The Stripe CLI is the fastest way to exercise a real signature path without deploying. It forwards live events to localhost and prints a signing secret scoped to that session:

# Forward events to your local server; note the printed whsec_ secret:
stripe listen --forward-to localhost:3000/webhooks/stripe
# > Ready! Your webhook signing secret is whsec_1a2b3c...   (use THIS secret locally)

# In another terminal, fire a real test event through the pipe:
stripe trigger payment_intent.succeeded

For fully offline experimentation — no Stripe account needed — build and sign a sample payload with the Webhook Payload Builder, then confirm your handler's HMAC math against the HMAC Generator. Both run entirely in your browser using the Web Crypto API, so payloads and secrets never leave your machine.
