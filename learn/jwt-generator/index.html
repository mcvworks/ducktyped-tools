Generating JSON Web Tokens Safely

Last updated: June 11, 2026

Learn what goes into a well-formed JWT: the three-part structure, how to choose between HS256, RS256, and ES256, which standard claims to include, and how to pick an expiration strategy that limits the damage of a leaked token.

What Generating a JWT Actually Means

A JSON Web Token (JWT) is a signed, Base64url-encoded credential defined in RFC 7519. Generating one is not just "creating a string" -- it is making a cryptographic promise. The issuer asserts a set of claims (who the user is, what they may do, how long the token is valid) and signs them so that any verifier can detect tampering.

Every generated token has three dot-separated parts: header.payload.signature. The header declares the signing algorithm, the payload carries the claims, and the signature binds them together. A minimal generation flow looks like this:

// 1. Header
{ "alg": "HS256", "typ": "JWT" }

// 2. Payload
{ "sub": "user_1024", "iat": 1781136000, "exp": 1781139600 }

// 3. Sign
signature = HMAC-SHA256(
  base64url(header) + "." + base64url(payload),
  secret
)

token = base64url(header) + "." + base64url(payload) + "." + base64url(signature)

Two details trip people up. First, the encoding is Base64url, not plain Base64 -- + becomes -, / becomes _, and padding = characters are stripped. Second, the payload is encoded, not encrypted: anyone holding the token can read every claim. Never put passwords or other secrets in a JWT you generate.

Choosing a Signing Algorithm

The alg header is the most consequential decision you make when generating a token. The three production-grade families differ in who can sign and who can verify.

HS256 (HMAC with SHA-256)

A symmetric algorithm: the same shared secret both signs and verifies. It is fast and simple, which makes it the right default when a single service issues and verifies its own tokens. The trade-off is that every verifier must hold the secret -- and anyone holding the secret can mint valid tokens. Use a secret of at least 32 random bytes; a short, guessable secret can be brute-forced offline from a single captured token.

RS256 (RSA with SHA-256)

An asymmetric algorithm: a private key signs, a public key verifies. This is the standard choice for distributed systems and third-party identity providers (it is what most OIDC providers issue). Microservices can verify tokens with the published public key but can never forge them. RSA keys should be 2048 bits or larger; signing is slower than HMAC and tokens are bigger.

ES256 (ECDSA with P-256 and SHA-256)

Also asymmetric, but built on elliptic curves. A 256-bit ECDSA key gives security comparable to a 3072-bit RSA key, with much smaller signatures and faster signing. ES256 is the best choice for high-volume token issuance when all your verifiers support it.

Whichever you choose, hard-code the expected algorithm on the verification side. Never let the token's own header decide how it is verified -- that is the root of the well-known alg: "none" forgery attack.

Standard Claims to Include

RFC 7519 registers a set of claim names that every JWT library understands. When generating tokens, include at least these:

  • sub (Subject) -- who the token is about, usually a stable user ID such as "user_1024". Avoid emails, which can change.
  • iat (Issued At) -- Unix timestamp of creation. Lets verifiers reject suspiciously old tokens and supports "invalidate everything issued before X" logic.
  • exp (Expiration) -- Unix timestamp after which the token must be rejected. Every token you generate should have one.
  • aud (Audience) -- which API or service the token is for, e.g. "api.example.com". Stops a token minted for one API from being replayed against another.
  • iss (Issuer) -- who minted the token, e.g. "auth.example.com".
  • jti (JWT ID) -- a unique random ID per token, useful for revocation lists and replay detection.

A realistic payload for an API access token:

{
  "iss": "auth.example.com",
  "sub": "user_1024",
  "aud": "api.example.com",
  "iat": 1781136000,
  "exp": 1781137800,
  "jti": "f3b1c2a8-9d4e-4f6a-b1c0-7e2d5a9c3f10",
  "role": "editor"
}

Custom claims like role are fine -- just keep the payload small, since the token travels on every request, and remember it is readable by anyone who holds it.

Expiration Strategy

A signed JWT cannot be recalled once issued; it stays valid until exp. That makes expiration your primary damage-control mechanism:

  • Keep access tokens short-lived -- 5 to 60 minutes is typical. A leaked 15-minute token is a nuisance; a leaked 30-day token is a breach.
  • Use refresh tokens for long sessions -- issue a separate, longer-lived refresh token (stored in an HTTP-only cookie or secure storage) that exchanges for fresh access tokens. Refresh tokens are stored server-side, so they can be revoked.
  • Allow small clock skew -- verifiers commonly accept 30-60 seconds of leeway on exp and nbf to tolerate clock drift between servers.
  • Set iat honestly -- backdating or omitting it removes your ability to do issued-before cutoffs after a key rotation or incident.

Remember that exp and iat are Unix timestamps in seconds, not milliseconds. Passing a JavaScript Date.now() value without dividing by 1000 creates tokens that "expire" tens of thousands of years from now.

Using the JWT Generator Safely

The duckTyped JWT Generator builds and signs tokens entirely in your browser:

  1. Edit the header -- the default is {"alg":"HS256","typ":"JWT"}. The tool signs with the HMAC family (HS256).
  2. Build the payload -- type JSON directly, or use the one-click buttons to add iss, aud, exp (+1 hour), iat (now), or a random jti.
  3. Enter a secret key and click Generate JWT to produce a properly signed token.

Nothing is sent to a server, so generating test tokens is safe. Still, follow two rules: never paste a production signing secret into any tool, browser-based or not, and treat generated tokens as test artifacts -- production tokens belong on your server, minted from a secret that never leaves your infrastructure. To inspect a token you have generated (or one from your auth provider), decode it with the JWT Decoder and check the claims and expiration status.
