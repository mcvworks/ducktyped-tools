Certificate Signing Requests (CSR) Explained

Last updated: June 11, 2026

Learn what a CSR actually contains, how to generate one with OpenSSL, what the subject fields and key parameters mean, and how to verify everything is correct before you submit it to a Certificate Authority.

What Is a Certificate Signing Request?

A Certificate Signing Request (CSR) is the formal application you send to a Certificate Authority (CA) when you want an SSL/TLS certificate. Defined by PKCS #10 (RFC 2986), a CSR bundles three things into one Base64-encoded block:

  • Your public key -- the key the CA will embed in the issued certificate.
  • Subject information -- the domain name(s) and, for organization-validated certificates, your company details.
  • A self-signature -- the whole request is signed with your private key, proving to the CA that you actually control the key pair you are asking it to certify.

Critically, the private key is never part of the CSR. The key pair is generated on your server, the private half stays there, and only the public half travels inside the request. That is why a CSR is safe to paste into a decoder or email to a CA. In PEM form it looks like this:

-----BEGIN CERTIFICATE REQUEST-----
MIICqzCCAZMCAQAwZjELMAkGA1UEBhMCVVMxEzARBgNVBAgMCkNhbGlmb3JuaWEx
FjAUBgNVBAcMDVNhbiBGcmFuY2lzY28xEjAQBgNVBAoMCUFjbWUgSW5jMRYwFAYD
...
-----END CERTIFICATE REQUEST-----

The CA validates your control of the domain (and identity, for OV/EV certificates), then issues a certificate containing your public key and subject details, signed by the CA's own key. From that point on, browsers trust your server because they trust the CA -- the chain of trust that the SSL/TLS handshake verifies on every connection.

Generating a CSR with OpenSSL

The standard way to create a CSR is OpenSSL. This single command generates a new 2048-bit RSA private key and the CSR together:

openssl req -new -newkey rsa:2048 -nodes \
  -keyout example.com.key \
  -out example.com.csr \
  -subj "/C=US/ST=California/L=San Francisco/O=Acme Inc/CN=example.com" \
  -addext "subjectAltName=DNS:example.com,DNS:www.example.com"

What each part does:

  • -new -newkey rsa:2048 -- create a new request and a fresh 2048-bit RSA key. Use rsa:4096 for a larger key, or -newkey ec -pkeyopt ec_paramgen_curve:P-256 for a smaller, faster ECDSA key.
  • -nodes -- "no DES": leave the private key unencrypted so your web server can read it without a passphrase prompt at startup.
  • -keyout / -out -- where to write the private key and the CSR.
  • -subj -- the subject fields inline; omit it to be prompted interactively.
  • -addext "subjectAltName=..." -- the SAN extension listing every domain the certificate must cover. Do not skip this.

If you already have a private key and only need a new CSR (for example, when renewing), reuse it:

openssl req -new -key example.com.key -out example.com.csr

Afterwards, set restrictive permissions on the key (chmod 600 example.com.key) and never transmit it anywhere. If the key is lost you cannot install the issued certificate; if it leaks, the certificate must be revoked and reissued.

What the CSR Fields Mean

Decoding a CSR reveals a handful of fields, and CAs copy them almost verbatim into the certificate -- so a typo here becomes a typo in your cert:

  • CN (Common Name) -- historically the primary domain, e.g. example.com. Modern browsers ignore the CN for hostname matching and rely solely on SANs, but CAs still expect it to be set, and it should match your first SAN.
  • SANs (Subject Alternative Names) -- the list that actually matters. Every hostname the certificate must secure -- example.com, www.example.com, a wildcard like *.example.com -- must appear here. A missing SAN is the classic cause of "certificate name mismatch" warnings after issuance.
  • O (Organization) -- your legal company name, e.g. Acme Inc. Validated and shown in the certificate for OV/EV issuance; ignored for domain-validated (DV) certificates such as Let's Encrypt.
  • OU, L, ST, C -- organizational unit, locality, state/province, and two-letter country code. OU is deprecated by the CA/Browser Forum and most CAs now strip it; C must be ISO 3166 (e.g. US, not USA).
  • Public key algorithm and size -- RSA 2048 is the minimum CAs accept today; RSA 3072/4096 or ECDSA P-256 offer stronger or faster alternatives. A CSR with a 1024-bit key will be rejected outright.
  • Signature algorithm -- how the request itself is signed, typically sha256WithRSAEncryption or ecdsa-with-SHA256. SHA-1-signed CSRs should be regenerated.

Verifying a CSR Before Submitting to a CA

Submitting a flawed CSR wastes a validation round-trip -- or worse, gets you a certificate with the wrong names that you discover only when browsers start warning. Three checks catch nearly every problem.

1. Decode and read it. Verify the embedded signature and print every field:

openssl req -in example.com.csr -noout -text -verify

Confirm the output says verify OK, the CN and every SAN are spelled correctly, the O field matches your legal name (if you need OV), and the key is at least RSA 2048 or ECDSA P-256. For a quicker look without a terminal, paste the PEM into the duckTyped CSR Decoder -- it parses the ASN.1 structure in your browser and displays the subject, key info, and extensions without sending the request anywhere.

2. Confirm the CSR matches your private key. The issued certificate is useless if it does not pair with the key on your server. Compare public key hashes:

openssl req  -in example.com.csr -noout -pubkey | openssl sha256
openssl pkey -in example.com.key -pubout       | openssl sha256

The two digests must be identical. A mismatch usually means an old CSR was generated from a previous key.

3. Sanity-check the SAN list against reality. List every hostname that will serve the certificate -- apex, www, API subdomains -- and make sure each is present. Remember that a wildcard *.example.com covers one level of subdomain but not the bare apex, so most wildcard CSRs need both *.example.com and example.com as SANs.

From CSR to Installed Certificate

Once the CA validates your request and issues the certificate, the lifecycle continues:

  1. Install the certificate plus the intermediate chain on your server, alongside the original private key. Serving the leaf certificate without intermediates is a leading cause of chain validation errors on some clients.
  2. Test from the outside with the SSL Checker to confirm the chain, names, and expiry dates look right.
  3. Track expiration. Public certificates are now limited to short lifetimes, so renewal -- generating a fresh CSR or letting ACME automation do it -- comes around quickly. An expired certificate takes your site down for most visitors; see the SSL certificate expired guide for diagnosis and fixes.

Automated issuers like Let's Encrypt build and submit the CSR for you via the ACME protocol, but the object exchanged is exactly the same PKCS #10 request described here -- which is why decoding CSRs remains a useful debugging skill even in fully automated setups.
