Public Keys, PEM and DER Explained

Last updated: June 11, 2026

Understand what is actually inside a PEM file: how DER and PEM encodings relate, what the BEGIN/END armor labels mean, how public keys differ from certificates and CSRs, and how to read the decoded fields that matter.

PEM vs DER: Two Encodings, One Structure

Every key, certificate, and certificate signing request in the X.509 ecosystem is defined as an ASN.1 data structure -- a nested tree of sequences, integers, and object identifiers. That structure has to be serialized to bytes somehow, and there are two standard ways to do it:

  • DER (Distinguished Encoding Rules) -- the raw binary serialization. Compact and unambiguous, but it cannot be pasted into a terminal, an email, or a YAML file without being corrupted.
  • PEM (Privacy-Enhanced Mail) -- the same DER bytes encoded in Base64, wrapped at 64 characters per line, and bracketed by header and footer lines. PEM is just a text-safe container for DER.

This is the single most important fact about these formats: a PEM file contains exactly the same information as the corresponding DER file. Strip the header and footer, Base64-decode the middle, and you have DER. A typical PEM public key looks like this:

-----BEGIN PUBLIC KEY-----
MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE2adMrdG7aUfZH57aeKFFM01dPnkE
C4EGVcjCARIbF8oolIr0zfxuEk2NXIV+B1BjCJSXmDuZLkVmrmnKPvWP2Q==
-----END PUBLIC KEY-----

The -----BEGIN ...----- and -----END ...----- lines are called PEM armor. The label between the dashes tells you (and your tooling) what the Base64 payload contains. Common labels:

  • PUBLIC KEY -- a SubjectPublicKeyInfo (SPKI) structure: an algorithm identifier plus the key material. This is the modern, algorithm-agnostic format.
  • RSA PUBLIC KEY -- a legacy PKCS#1 structure containing only the RSA modulus and exponent, with no algorithm wrapper.
  • CERTIFICATE -- a full X.509 certificate.
  • CERTIFICATE REQUEST -- a PKCS#10 CSR.
  • PRIVATE KEY / EC PRIVATE KEY / RSA PRIVATE KEY -- private key material. Never paste these into anything you do not control.

Because the armor is plain text, you can concatenate multiple PEM blocks in one file -- which is exactly how certificate chain files (fullchain.pem) work.

Public Keys vs Certificates vs CSRs

These three artifacts are constantly confused because they all travel as PEM blocks and all contain a public key. They serve very different purposes:

  • Public key -- raw cryptographic material: an RSA modulus and exponent, or an elliptic curve point. It says nothing about who owns it. Anyone can generate one in milliseconds.
  • Certificate -- a public key plus identity: a subject (such as CN=example.com), an issuer, validity dates, extensions like Subject Alternative Names, and a digital signature from a certificate authority binding all of it together. The CA signature is what lets a browser trust that the key really belongs to that domain.
  • CSR (Certificate Signing Request) -- the in-between artifact. You generate a key pair, embed the public key and your requested subject details into a CSR, self-sign it with your private key to prove possession, and send it to a CA. The CA verifies your control of the domain and returns a signed certificate. CSRs are covered in depth in our CSR Decoder guide.

The lifecycle is: key pair → CSR → certificate. The public key inside all three is byte-for-byte identical, which is also how you verify that a certificate matches a key: compare the hashes of their public keys. Where the certificate fits into an actual connection is covered in our SSL/TLS handshake guide.

Reading the Decoded Fields

When you decode a public key, a handful of fields tell you almost everything you need to know:

  • Algorithm -- identified by an OID (object identifier) in the ASN.1 structure. 1.2.840.113549.1.1.1 means RSA, 1.2.840.10045.2.1 means an EC public key, and 1.3.101.112 means Ed25519.
  • Key size -- for RSA, the bit length of the modulus (2048, 3072, 4096). For EC keys, size is implied by the curve.
  • Curve -- EC keys carry a second OID naming the curve: 1.2.840.10045.3.1.7 is P-256 (also called prime256v1 or secp256r1), 1.3.132.0.34 is P-384, and 1.3.132.0.35 is P-521.
  • Exponent -- RSA keys almost always use the public exponent 65537 (0x010001). Anything unusual here is a red flag.
  • Fingerprint -- a hash (usually SHA-256) of the DER bytes. Fingerprints give you a short, comparable identifier for a key: if two fingerprints match, the keys are identical. This is the standard way to confirm a certificate, CSR, and private key all belong together, and it is what SSH shows you on first connection.

A decoded RSA SPKI structure looks like this -- an outer sequence holding an algorithm identifier and a bit string containing the actual key:

SEQUENCE
  SEQUENCE
    OBJECT IDENTIFIER  1.2.840.113549.1.1.1 (rsaEncryption)
    NULL
  BIT STRING
    SEQUENCE
      INTEGER (257 bytes)   <- 2048-bit modulus
      INTEGER 65537         <- public exponent

Inspecting Keys with OpenSSL

OpenSSL is the reference tool for working with these formats. The commands you will use most often:

# Inspect any public key (RSA, EC, Ed25519)
openssl pkey -pubin -text -noout -in pubkey.pem

# RSA-specific: print modulus, exponent, key size
openssl rsa -pubin -text -noout -in pubkey.pem

# EC-specific: print curve name and point
openssl ec -pubin -text -noout -in pubkey.pem

# Inspect a certificate or CSR
openssl x509 -text -noout -in cert.pem
openssl req -text -noout -in request.csr

Converting between PEM and DER is a single flag:

# PEM to DER
openssl pkey -pubin -in pubkey.pem -outform DER -out pubkey.der

# DER to PEM
openssl pkey -pubin -inform DER -in pubkey.der -out pubkey.pem

And to verify that a certificate, CSR, and private key all share the same public key, hash the SPKI of each and compare:

openssl x509 -in cert.pem  -pubkey -noout | openssl pkey -pubin -outform DER | openssl dgst -sha256
openssl req  -in req.csr   -pubkey -noout | openssl pkey -pubin -outform DER | openssl dgst -sha256
openssl pkey -in priv.key  -pubout         | openssl pkey -pubin -outform DER | openssl dgst -sha256

Three identical digests means the three files belong to the same key pair -- the fastest way to rule out a mismatched key when a server refuses to start or a CA rejects your request.

When Key Size Matters

Key size determines how expensive a brute-force or factoring attack would be, but the numbers are not directly comparable across algorithms:

  • RSA 2048 -- roughly 112 bits of security. Still the most widely deployed size and acceptable for typical TLS certificates (which rotate every 90 days to a year), but standards bodies recommend moving beyond it for keys that must stay secure long-term.
  • RSA 3072 / 4096 -- roughly 128 / ~140+ bits of security. Appropriate for long-lived keys such as root CAs, code signing, and document signing. The cost is slower handshakes and signatures -- RSA operations scale poorly with key size.
  • EC P-256 -- about 128 bits of security from a 256-bit key. Equivalent strength to RSA 3072 at a fraction of the size and CPU cost, which is why most modern TLS deployments use ECDSA P-256. P-384 steps up to 192-bit security.
  • RSA 1024 -- considered breakable by well-resourced attackers. If a decoder reports a 1024-bit key anywhere in production, replace it immediately.

Practical guidance: for web TLS, prefer EC P-256 (or P-384) unless you must support very old clients; if you stay on RSA, use 2048 as the floor and 3072+ for anything long-lived. Bigger is not automatically better -- RSA 4096 roughly quadruples handshake CPU versus 2048 for a security margin most sites do not need.
