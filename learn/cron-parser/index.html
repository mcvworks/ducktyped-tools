Cron Expressions Explained

Last updated: June 11, 2026

Learn how to read and write cron expressions: the five fields, ranges, steps and lists, special strings like @daily and @reboot, 5-field vs 6-field dialects, timezone and DST pitfalls, and a library of real-world schedules.

What Is a Cron Expression?

A cron expression is a compact string that describes a recurring schedule. It originated with the Unix cron daemon in the 1970s and is now the lingua franca of scheduling everywhere: crontabs on Linux servers, Kubernetes CronJobs, GitHub Actions schedule: triggers, AWS EventBridge rules, and countless application-level job runners.

The classic format has five space-separated fields, read left to right:

┌───────────── minute        (0–59)
│ ┌─────────── hour          (0–23)
│ │ ┌───────── day of month  (1–31)
│ │ │ ┌─────── month         (1–12 or JAN–DEC)
│ │ │ │ ┌───── day of week   (0–7, 0 and 7 = Sunday, or SUN–SAT)
│ │ │ │ │
0 9 * * 1-5    →  "At 09:00 on every weekday"

Each field accepts a number, a wildcard, or an expression built from ranges, lists, and steps. The job fires whenever the current time matches all fields — with one famous exception covered below.

The Five Fields, One by One

  • Minute (0–59) — the minute within the hour. 0 means on the hour; 30 means half past.
  • Hour (0–23) — 24-hour clock. 0 is midnight, 13 is 1 PM. There is no AM/PM in cron.
  • Day of month (1–31) — the calendar day. 1 is the first of the month. Days that do not exist in a given month (e.g., 31 in April) simply never match, so 0 0 31 * * only fires in 7 months of the year.
  • Month (1–12) — 1 is January. Most implementations also accept three-letter names: JAN, FEB, MAR.
  • Day of week (0–7) — 0 and 7 both mean Sunday, 1 is Monday. Names like MON and FRI are widely supported and far more readable.

The classic trap: when both day-of-month and day-of-week are restricted (neither is *), standard Vixie cron fires when either matches, not both. So 0 0 13 * 5 runs on the 13th of every month and on every Friday — not just on Friday the 13th. Quartz and some modern schedulers handle this differently, which is one more reason to verify expressions with a parser before deploying them.

Ranges, Steps, and Lists

Four operators turn single values into schedules:

  • * (wildcard) — matches every value in the field. * in the hour field means "every hour."
  • - (range) — an inclusive span. 1-5 in day-of-week means Monday through Friday; 9-17 in the hour field means 9 AM through 5 PM.
  • , (list) — discrete values. 0,30 in the minute field means on the hour and at half past. Lists can contain ranges: MON,WED,FRI or 1-3,5.
  • / (step) — every Nth value. */15 in the minute field means minutes 0, 15, 30, 45. Steps combine with ranges: 9-17/2 means 9, 11, 13, 15, 17.

Combining them reads naturally once you know the grammar:

*/10 9-17 * * 1-5    # every 10 minutes, 9 AM–5 PM, weekdays only
0 8,12,18 * * *      # at 08:00, 12:00, and 18:00 every day
30 2 1,15 * *        # at 02:30 on the 1st and 15th of each month

One subtlety with steps: */7 in the minute field fires at 0, 7, 14, 21, 28, 35, 42, 49, 56 — then resets at the top of the next hour, so the gap between :56 and :00 is only 4 minutes. Steps divide the field's range; they are not true "every N minutes forever" intervals.

5-Field vs 6-Field Formats and Special Strings

Not all cron dialects agree on the number of fields:

  • 5 fields — classic Unix/Vixie cron, Kubernetes CronJobs, GitHub Actions: minute hour dom month dow.
  • 6 fields with seconds first — Quartz (Java), Spring's @Scheduled: second minute hour dom month dow. The expression 0 0 9 * * MON-FRI here means 9:00:00 AM on weekdays.
  • 6 fields with a year last — AWS EventBridge: minute hour dom month dow year, and it requires ? in either dom or dow.

Pasting a Quartz expression into a Linux crontab (or vice versa) silently shifts every field one position — a schedule meant for 9 AM daily becomes minute 9 of every hour. Always confirm which dialect your scheduler speaks.

Most crontab implementations also accept special strings in place of the five fields:

@reboot     # once, at daemon/system startup (not time-based)
@hourly     # 0 * * * *
@daily      # 0 0 * * *      (alias: @midnight)
@weekly     # 0 0 * * 0
@monthly    # 0 0 1 * *
@yearly     # 0 0 1 1 *      (alias: @annually)

@reboot is the odd one out: it is an event, not a schedule, and it is handy for starting user-level services on boot without writing a systemd unit. Note that special strings are a crontab feature — Kubernetes supports the time-based ones but most cloud schedulers do not.

Timezone Gotchas: Server TZ, UTC, and DST

Cron expressions contain no timezone information — the scheduler supplies it, and different schedulers supply different defaults:

  • Classic crontab evaluates expressions in the server's local timezone (some crons honor a CRON_TZ= variable per crontab).
  • GitHub Actions, AWS EventBridge (by default), and most CI schedulers run in UTC. A nightly job written as 0 2 * * * fires at 2 AM UTC — which is 7 PM the previous day in Los Angeles.
  • Kubernetes CronJobs historically used the controller's timezone; modern clusters support an explicit timeZone: "Europe/Berlin" field, which you should always set.

Daylight saving time adds two failure modes for jobs scheduled in a local timezone. When clocks spring forward, the hour from 2:00 to 3:00 simply does not exist — a job scheduled at 30 2 * * * is skipped that night (some crons run it late; behavior varies). When clocks fall back, 1:00–2:00 occurs twice, and the same job may run twice. The pragmatic rules:

  • Schedule infrastructure jobs in UTC whenever the audience is machines, not humans.
  • Avoid scheduling anything between 1:00 and 3:00 local time in zones that observe DST.
  • When a job must align with human time (reports at 9 AM in the office's timezone), use a scheduler that accepts an explicit IANA timezone rather than doing offset math yourself.

When debugging "why did this run at the wrong time," converting between the server's epoch timestamps and your wall clock with a timestamp converter usually reveals the offset immediately.

Common Real-World Expressions

*/5 * * * *      # every 5 minutes — health checks, queue polling
0 * * * *        # top of every hour — log rotation, cache refresh
0 0 * * *        # daily at midnight — cleanup jobs, daily rollups
30 3 * * *       # daily at 03:30 — backups, off-peak maintenance
0 9 * * 1-5      # 9 AM weekdays — business-hours reports
0 0 * * 0        # Sunday at midnight — weekly digests
0 0 1 * *        # first of the month — billing, invoice generation
0 0 1 1 *        # January 1st — yearly archival
0 */6 * * *      # every 6 hours — certificate/DNS re-checks
15 4 * * 1       # Monday 04:15 — weekly DB maintenance, offset from
                 # the top of the hour to avoid thundering herds

That last point is a real operational tip: thousands of machines all running 0 0 * * * hit shared services at exactly midnight. Offsetting jobs to odd minutes (17 0 * * *) spreads the load.
