Docker Compose Files Explained

Last updated: June 11, 2026

Understand the structure of a docker-compose.yml file, how the modern Compose Specification replaced the version-keyed schemas, which validation errors trip people up most, and how to debug a failing compose up.

Anatomy of a Compose File

A Compose file is a YAML document that describes a multi-container application declaratively: which containers to run, how they talk to each other, and where their data lives. It has three main top-level sections:

  • services -- the containers themselves. Each key under services is a service name, and each service needs at minimum an image to pull or a build context to build from. Everything else -- ports, environment, volumes, depends_on, restart -- configures how that container runs.
  • networks -- how services communicate. Compose creates a default network automatically and connects every service to it, so services can already reach each other by service name (db:5432, not localhost:5432). You only declare networks explicitly when you need isolation between groups of services.
  • volumes -- named volumes for data that must survive container restarts, such as database files. Named volumes used by a service must also be declared at the top level.

A minimal but complete two-service stack:

services:
  web:
    image: nginx:latest
    ports:
      - "8080:80"
    depends_on:
      - db
  db:
    image: postgres:15
    environment:
      POSTGRES_PASSWORD: secret
    volumes:
      - db_data:/var/lib/postgresql/data

volumes:
  db_data:

Note the structure: web and db are nested under services, ports and volumes are lists (each entry starts with -), environment here is a mapping, and the named volume db_data is declared at the bottom. Most validation errors are violations of exactly this shape.

Compose Spec vs Legacy version Schemas

Older Compose files start with a line like version: "3.8". That number selected one of the legacy schemas: the 2.x series (designed for standalone Compose, with features like depends_on conditions and resource limits) or the 3.x series (designed for Docker Swarm, which dropped some 2.x features and added deploy). Picking a version meant picking which keys were legal, and plenty of confusion came from features existing in 2.4 but not 3.8.

Docker Compose V2 (the docker compose plugin, as opposed to the old docker-compose Python tool) replaced all of that with the unified Compose Specification:

  • The top-level version key is deprecated and ignored. Modern Compose prints a warning ("the attribute version is obsolete") and validates against the spec regardless of what the key says.
  • The spec merges the useful parts of 2.x and 3.x -- depends_on with conditions, deploy resource limits, healthchecks, and profiles all coexist.
  • compose.yaml is the preferred filename, though docker-compose.yml still works.

Practical takeaway: for new files, omit version entirely. If you maintain old files, leaving it in is harmless with Compose V2 but misleading -- it no longer controls anything. Only legacy tooling pinned to the old docker-compose 1.x binary still enforces version-keyed schemas.

Most Common Validation Errors

Almost every "invalid compose file" report falls into one of four buckets:

  • Indentation mistakes. YAML nesting is defined purely by leading spaces. A service property indented at the wrong level silently becomes a top-level key (then fails as "unknown key") or attaches to the wrong service. Pick two spaces per level and never mix widths.
  • Wrong value types. Each key expects a specific type. ports and depends_on (short form) expect lists; environment accepts a list or a mapping, but not a mix. A classic type error: 
    # Wrong: ports given as a mapping
services:
  web:
    image: nginx
    ports: "8080:80"

# Right: ports is a list of strings
services:
  web:
    image: nginx
    ports:
      - "8080:80"
  • Unknown keys. Usually a typo (enviroment, depend_on) or a key at the wrong level -- for example putting volumes: inside ports: because of an indentation slip. Compose reports these as Additional property X is not allowed.
  • Port syntax errors. The short syntax is "HOST:CONTAINER", optionally with an IP ("127.0.0.1:8080:80") or protocol ("53:53/udp"). Reversing host and container ports, omitting quotes, or using a range incorrectly ("8000-8010:8000" maps a range to one port only in newer versions) all produce confusing failures.

YAML Gotchas

Compose problems are often really YAML problems. The recurring traps:

  • Tabs are illegal. YAML forbids tab characters for indentation, full stop. A single tab pasted from a terminal yields found character '\t' that cannot start any token. Configure your editor to insert spaces.
  • Unquoted port mappings. YAML 1.1 parsers treat colon-separated digit groups under 60 as base-60 (sexagesimal) numbers. An unquoted 22:22 can parse as the integer 1342 instead of a port mapping: 
    # Wrong: may parse as the number 1342
ports:
  - 22:22

# Right: always quote port mappings
ports:
  - "22:22"
  • The Norway problem. Unquoted yes, no, on, off, true, false become booleans in YAML 1.1. An environment value of no arrives in your container as False. Quote any environment value that is not obviously a plain string: DEBUG: "no".
  • Version numbers become floats. image_tag: 3.10 parses as the float 3.1. Quote it.
  • Duplicate keys. Defining environment: twice in one service is invalid YAML, but some parsers silently keep only the last occurrence -- your first block of variables vanishes without an error.
  • Variable interpolation. ${DB_PASSWORD} is substituted from the shell environment or a .env file at parse time. An unset variable becomes an empty string with only a warning. Use ${DB_PASSWORD:?error} to make missing variables fail loudly.

Debugging a Failing compose up

When docker compose up fails, work through it in this order:

  1. Validate first: docker compose config parses the file, applies .env interpolation, and prints the fully resolved configuration -- or the exact line of the first error. docker compose config --quiet is a pure pass/fail check for CI.
  2. Read the actual error. A YAML parse error names a line number; a schema error names the offending key and service. Fix the first error and re-run -- later errors are often cascade effects.
  3. Check the logs: docker compose logs -f web shows why a container that started immediately exited. docker compose ps shows restart loops.
  4. Isolate one service: docker compose up web starts a single service (plus its depends_on chain) so you can find which container is at fault.
  5. Check port conflicts. bind: address already in use means another process owns the host port -- find it with ss -tlnp | grep 8080 or change the host side of the mapping.
  6. Verify interpolation: compare docker compose config output against what you expected -- empty strings where secrets should be mean an unset variable or a .env file in the wrong directory.
  7. Rebuild when in doubt: docker compose up --build --force-recreate rules out stale images and containers holding old configuration.
