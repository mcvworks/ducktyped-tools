422 Unprocessable Entity

Last updated: March 8, 2026

A 422 error means the request was parsed successfully but failed semantic validation. The data structure is correct, but the content violates business rules or validation constraints.

You might see this error as:

  • HTTP 422
  • 422 Unprocessable Entity
  • 422 error
  • Validation failed
  • Unprocessable entity
  • 422 API validation error
  • 422 vs 400

What Does This Error Mean?

HTTP 422 is used when a request body is syntactically valid (parseable JSON, correct content type) but semantically incorrect — the server understands what you are trying to do but cannot process it because the data violates its rules.

This is commonly returned by REST APIs for validation errors: missing required fields, values outside allowed ranges, invalid enum values, or violated business logic constraints.

Common Causes

  • Missing required fields — a required JSON field was omitted from the request body.
  • Invalid field value — a field value is outside the allowed range or does not match the expected format.
  • Wrong data type — sending a string where a number is expected, or an object where an array is expected.
  • Business rule violation — e.g., setting a ship date before the order date, or a quantity below 1.
  • Foreign key constraint — referencing an ID that does not exist in a related resource.
  • Duplicate value in a unique field — though 409 may be more appropriate here.

How to Fix It

1. Read the Response Body

Well-designed APIs include validation error details in the 422 response body. A typical response might look like:

{
  "errors": [
    { "field": "email", "message": "is required" },
    { "field": "age", "message": "must be a positive integer" }
  ]
}

Fix each reported validation issue in your request.

2. Check Required Fields

Compare your request body against the API documentation. Ensure all required fields are present and spelled correctly (field names are usually case-sensitive).

3. Verify Data Types and Formats

Ensure dates are in the expected format (ISO 8601 vs. Unix timestamp), numbers are not wrapped in strings, and arrays are not objects.

4. Review API Documentation

Check the specific validation rules for each field: minimum/maximum values, allowed enum values, regex patterns, and relationship constraints.

Frequently Asked Questions

When should an API return 422 vs. 400?

Use 400 for syntactic problems (malformed JSON, invalid HTTP headers, unparseable request). Use 422 for semantic problems (valid JSON but failing business validation). In practice, many APIs return 400 for both — but 422 provides more precise semantics for validation failures.

Does 422 indicate the server made an error?

No. Like all 4xx errors, 422 indicates the problem is on the client side. The client sent data that the server cannot process. Fix the request to comply with the server's validation rules.

Related Errors

  • 400 Bad Request — syntactically malformed request.
  • 409 Conflict — request conflicts with existing resource state.
  • 403 Forbidden — access denied.
