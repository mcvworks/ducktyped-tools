412 Precondition Failed

Last updated: March 8, 2026

One or more precondition headers evaluated to false on the server

You might see this error as:

  • HTTP 412
  • 412 Precondition Failed
  • 412 error
  • Precondition failed
  • If-Match failed
  • ETag mismatch

What Does This Error Mean?

A 412 Precondition Failed response indicates that one or more conditions specified in the request headers (If-Match, If-Unmodified-Since, If-None-Match) evaluated to false on the server. This mechanism prevents lost updates in concurrent editing scenarios by ensuring the resource has not been modified since the client last retrieved it. The client must fetch the latest version before retrying.

Common Causes

  • ETag mismatch on conditional update — The client sent an If-Match header with an ETag that no longer matches the current version of the resource, indicating another client has modified it since.
  • Resource modified since last retrieval — The If-Unmodified-Since header timestamp is earlier than the resource's last modification time, meaning the resource has changed since the client's cached copy.
  • Concurrent editing conflict — Two clients attempted to update the same resource simultaneously. The second client's request fails because the precondition based on the original version no longer holds.
  • Stale client cache — The client is using outdated ETags or timestamps from a stale cache entry to construct conditional requests.

How to Fix It

1. Fetch the latest version and retry

GET the resource again to obtain the current ETag and Last-Modified values, then retry the conditional request with the updated precondition headers.

# 1. Get current ETag
curl -I https://api.example.com/resource/123
# 2. Use the new ETag in your update
curl -X PUT -H 'If-Match: "new-etag-value"' -d '{...}' https://api.example.com/resource/123

2. Implement optimistic concurrency in your client

Build retry logic that catches 412 errors, re-fetches the resource, merges changes if possible, and resubmits with the updated precondition headers.

3. Remove conditional headers if not needed

If you do not need optimistic concurrency control, remove the If-Match or If-Unmodified-Since headers from your request. Be aware this may cause lost updates.

Frequently Asked Questions

What is the purpose of precondition headers?

Precondition headers implement optimistic concurrency control. They prevent the 'lost update' problem where two clients read a resource, both modify it, and the second write silently overwrites the first.

Is 412 the same as 409 Conflict?

No. A 412 specifically means a precondition header failed. A 409 indicates a more general conflict with the current state of the resource. Both relate to concurrent modifications but have different semantics.
