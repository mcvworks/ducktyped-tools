425 Too Early

Last updated: March 8, 2026

The server is unwilling to process a request that might be replayed

You might see this error as:

  • HTTP 425
  • 425 Too Early
  • 425 error
  • Too early
  • TLS early data rejected

What Does This Error Mean?

A 425 Too Early response indicates that the server is unwilling to process the request because it was sent as TLS 1.3 early data (0-RTT) and the server cannot guarantee it was not replayed. Early data allows clients to send requests before the TLS handshake is complete, reducing latency, but it creates a replay attack risk for non-idempotent requests.

Common Causes

  • Request sent as TLS 1.3 early data — The client sent the request in the TLS 1.3 0-RTT early data phase, and the server's policy does not allow processing this type of request as early data.
  • Non-idempotent request in early data — The server rejects non-idempotent requests (POST, PUT, DELETE) sent as early data because they could cause unintended side effects if replayed by a network attacker.
  • Server-side early data policy — The server is configured to reject all or certain types of early data requests as a security measure against replay attacks.

How to Fix It

1. Retry after the TLS handshake completes

The client should retry the request after the full TLS handshake is complete. Most HTTP libraries handle this automatically when they receive a 425.

2. Disable 0-RTT early data in the client

If 425 errors are frequent, configure the TLS client to not send early data. This adds a round trip of latency but eliminates replay risks.

# OpenSSL: disable early data
SSL_CTX_set_max_early_data(ctx, 0);

3. Configure server early data policy

On the server, configure which request types are safe to process as early data. GET requests for static resources are generally safe; POST requests are not.

Frequently Asked Questions

What is TLS 1.3 early data (0-RTT)?

TLS 1.3 allows clients to send data during the first round trip of a resumed connection, before the handshake completes. This reduces latency by one round trip but creates a window where the data could be replayed.

Is 425 an error I need to fix?

Usually not. HTTP clients should automatically retry the request after the handshake completes. If you are seeing 425 in logs, it is the server correctly protecting against potential replay attacks.
