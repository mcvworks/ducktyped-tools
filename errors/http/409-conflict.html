409 Conflict

Last updated: March 8, 2026

A 409 error means the request conflicts with the current state of the resource. The request is valid, but applying it would create an inconsistency on the server.

You might see this error as:

  • HTTP 409
  • 409 Conflict
  • 409 error
  • Resource conflict
  • Edit conflict
  • 409 API error

What Does This Error Mean?

HTTP 409 indicates a state conflict. The server understood your request and you are authorized to make it, but completing it would break the integrity of the server's data. This is common in REST APIs where concurrency and data consistency must be managed.

Common Causes

  • Duplicate resource creation — trying to create a user, record, or resource with a unique identifier that already exists.
  • Optimistic locking conflict — submitting an update based on an old version of a resource that has since been changed by someone else.
  • ETag mismatch — sending a PUT with an If-Match header whose ETag no longer matches the resource.
  • Duplicate form submission — submitting the same request twice (e.g., double-clicking a submit button).
  • Business logic conflict — e.g., trying to cancel an order that is already shipped.
  • Git merge conflicts — some Git hosting APIs return 409 for push conflicts.

How to Fix It

For Users

1. Refresh and Retry

The resource may have changed since you loaded the page. Refresh to get the latest state, then retry your action.

2. Check for Duplicates

If creating a resource (account, file, entry), check whether it already exists before submitting again.

For Developers and API Consumers

3. Fetch Current State Before Updating

Before a PUT or PATCH, GET the current state of the resource. Apply your changes to the latest version to avoid version conflicts.

4. Implement Idempotent Operations

Use PUT with a client-generated ID for resource creation where possible. A PUT to an existing resource is idempotent — creating no conflict — whereas POST may create duplicates.

5. Handle 409 in Your Client Code

On receiving 409, your client should fetch the latest resource state and present the conflict to the user for manual resolution, or automatically merge non-conflicting changes.

Frequently Asked Questions

Is 409 the correct code for duplicate email registration?

Yes. If a user attempts to register with an email that is already taken, returning 409 is semantically correct. Some APIs return 422 for this case, but 409 more accurately represents a conflict with existing state.

What is optimistic locking and how does 409 relate to it?

Optimistic locking is a concurrency technique where a record includes a version number. When updating, the client sends the version it read. If another client updated the record in the meantime, the version numbers do not match and the server returns 409 to prevent overwriting the newer data.

Related Errors

  • 422 Unprocessable Entity — semantic validation failure.
  • 410 Gone — resource permanently removed.
