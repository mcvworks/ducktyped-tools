400 Bad Request

Last updated: March 8, 2026

A 400 error means the server received a request it could not understand. The problem is with the request itself — malformed syntax, invalid data, or an oversized payload.

You might see this error as:

  • HTTP 400
  • 400 Bad Request
  • Error 400
  • 400 error
  • Bad request error
  • The request could not be understood
  • 400 Bad Request nginx
  • 400 Bad Request Apache

What Does This Error Mean?

HTTP 400 is a client-side error. The server received your request and understood it was an HTTP request, but the content was malformed or invalid in a way that prevented the server from processing it. This is different from 404 Not Found — with 400, the server found nothing wrong with the endpoint, but the request data itself was unacceptable.

Common Causes

  • Oversized cookies — cookie header exceeds the server's size limit (often 4KB or 8KB).
  • Corrupted or malformed URL — special characters not properly URL-encoded, double slashes, or invalid query strings.
  • Invalid HTTP headers — headers with illegal characters or malformed values.
  • Corrupted browser cache — stale cached data being sent as part of the request.
  • API request errors — sending invalid JSON, missing required fields, or wrong content type.
  • Oversized request body — file upload or POST body exceeding the server's maximum allowed size.
  • Double URL encoding — encoding a URL that is already encoded, creating invalid sequences.

How to Fix It

1. Clear Browser Cache and Cookies

Press Ctrl+Shift+Delete (Windows) or Cmd+Shift+Delete (macOS). Select "Cookies and site data" and "Cached images and files." Reload the page.

2. Check the URL

Look for special characters that need URL encoding (spaces should be %20, for example). Remove any duplicate slashes or illegal characters.

3. Try in Incognito Mode

Open the page in incognito. If it works, the issue is with cached data or cookies in your normal browser session.

4. Reduce Cookie Size (for Developers)

If users are reporting 400 errors on your site, check cookie sizes. Nginx defaults to an 8KB limit for request headers. Consider clearing old cookies or using server-side session storage instead of large client-side cookies.

5. Fix API Requests (for Developers)

Check that your request body is valid JSON, includes the correct Content-Type header, and all required fields are present. Compare against API documentation carefully.

6. Check Server Logs

Server logs (nginx error.log, Apache error.log) typically include the specific reason for a 400 rejection, such as "request line too large" or "invalid header."

Frequently Asked Questions

Is a 400 error always the client's fault?

Not always. While 400 technically indicates a client-side problem, a server can also return 400 due to a bug in its own request parsing logic. If many users report 400 errors on a specific action, check the server side.

400 vs. 422 — what is the difference?

A 422 Unprocessable Entity is more specific — the request is syntactically valid but semantically incorrect (e.g., the JSON is valid but fails business validation). A 400 is more general and usually indicates the request itself was malformed before the server could even validate its content.

Can ad blockers or proxies cause 400 errors?

Yes. Some proxies modify headers in ways that make them invalid. Ad blockers can occasionally interfere with cookies or request headers. Test in a clean browser session if you suspect this.

Related Errors

  • 401 Unauthorized — authentication credentials missing or invalid.
  • 403 Forbidden — server understood the request but refuses to authorize it.
  • 422 Unprocessable Entity — request is valid but semantically incorrect.
  • 413 Payload Too Large — request body exceeds server limit.
