DNS YXDOMAIN

Last updated: July 1, 2026

DNS response code 6 — a name exists when it should not. Seen in dynamic DNS updates with failed prerequisites and in DNAME/CNAME expansion overflows.

You might see this error as:

  • YXDOMAIN
  • RCODE 6
  • Name Exists when it should not
  • nsupdate YXDOMAIN
  • dynamic update prerequisite failed

What Does This Error Mean?

YXDOMAIN is one of the rarer DNS response codes, defined for dynamic updates (RFC 2136): an update said 'this name must not exist' as a prerequisite, but it does — so the server rejects the change. You will meet it in nsupdate scripts, DHCP servers doing dynamic DNS registration (especially Windows/Active Directory), and — in a second, unrelated meaning from RFC 6672 — when DNAME redirection produces a name longer than DNS allows. Understanding which of the two situations you are in is the whole diagnosis.

Common Causes

  • Dynamic update prerequisite failed — The update used an NXDOMAIN prerequisite ('add this only if the name does not exist'), but a record already exists at that name — often left behind by an earlier registration.
  • DHCP name collisions in Active Directory — Two machines claiming the same hostname, or a machine re-imaged with a new identity, collide with the existing DNS record owned by the old registration. The DHCP server's update is answered with YXDOMAIN.
  • Stale records that were never scavenged — Without DNS scavenging (or with it misconfigured), records from long-gone hosts persist and block re-registration of their names.
  • DNAME expansion exceeded the name-length limit — Per RFC 6672, when substituting a DNAME target produces a domain name longer than 255 octets, the server responds with YXDOMAIN. This is a zone-design problem, not an update conflict.

How to Fix It

1. Inspect what exists at the conflicting name

Look at the current records before fighting the prerequisite — the conflict is usually a stale A or CNAME record.

dig +noall +answer conflicting-host.example.com ANY
dig +noall +answer conflicting-host.example.com A CNAME TXT

2. Delete the stale record, then re-run the update

Remove the existing record explicitly in the same nsupdate session (or via your DNS console), then add the new one.

nsupdate -k /etc/rndc.key <<'EOF'
server ns1.example.com
zone example.com
update delete conflicting-host.example.com A
update add conflicting-host.example.com 300 A 192.0.2.10
send
EOF

3. Enable scavenging / fix ownership in AD environments

In Windows DNS, enable aging and scavenging so stale dynamic records expire, and check the record's security tab — a record owned by another computer account blocks updates from the new machine. Deleting the stale record and re-registering (ipconfig /registerdns) resolves the immediate conflict.

4. Shorten names involved in DNAME redirection

If YXDOMAIN comes from DNAME expansion, the combined substituted name exceeds 255 bytes. Flatten deep label hierarchies or move the DNAME higher in the tree so expanded names stay legal.

Frequently Asked Questions

How is YXDOMAIN different from NXDOMAIN?

They are opposites. NXDOMAIN: you asked for a name and it does not exist. YXDOMAIN: you required (in an update prerequisite) that a name not exist — and it does. YXDOMAIN appears in update responses, not ordinary lookups.

Why does my DHCP server log YXDOMAIN errors?

The DHCP server tried to register a client's hostname in DNS, but a record for that name already exists and is owned by someone else (a previous lease, an old machine account). Clean up the stale record or enable scavenging so it expires.

Can ordinary users ever see YXDOMAIN in a browser?

Practically never. Browsers do plain lookups, which return NOERROR, NXDOMAIN, or SERVFAIL. YXDOMAIN is confined to dynamic-update responses and the rare DNAME overflow case — it is an operator-facing error.
