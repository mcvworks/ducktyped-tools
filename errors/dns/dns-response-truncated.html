DNS Response Truncated

Last updated: July 1, 2026

A DNS answer was too large for UDP and was cut short (TC flag set) — and the fallback to TCP failed, so clients see incomplete or missing records.

You might see this error as:

  • DNS response truncated
  • ;; Truncated, retrying in TCP mode
  • TC flag DNS
  • reply truncated
  • DNS UDP truncation
  • EDNS buffer size

What Does This Error Mean?

Classic DNS runs over UDP with limited message sizes. When an answer does not fit — big TXT record sets, many A records, DNSSEC signatures — the server sets the TC (truncated) flag, telling the client to retry over TCP port 53. That retry is the fragile part: many firewalls still block TCP 53 under the outdated belief that DNS only needs UDP. The visible symptoms are dig printing ';; Truncated, retrying in TCP mode' followed by a timeout, applications seeing partial record sets, and domains with large responses (often DNSSEC-signed or heavily SPF-decorated) failing while small ones work.

Common Causes

  • TCP port 53 is blocked — The truncated UDP reply is only step one of the protocol; the real answer comes over TCP. A firewall dropping TCP 53 turns every large response into a hard failure.
  • EDNS buffer size mismatch or stripped EDNS — EDNS lets clients accept larger UDP responses (commonly 1232 bytes now). Middleboxes that strip EDNS force servers back to the 512-byte classic limit, truncating answers that would otherwise fit.
  • Oversized record sets — Domains accumulate huge TXT collections (SPF includes, verification tokens) or long CNAME chains. Each addition pushes more responses past UDP limits.
  • Fragmented UDP being dropped — Large UDP responses fragment at the IP layer, and many networks drop fragments. The client sees a timeout rather than a truncation — the modern recommendation is to keep UDP answers under ~1400 bytes and rely on TCP beyond that.

How to Fix It

1. Confirm truncation and test TCP explicitly

Watch for the TC flag, then force TCP. If UDP truncates and TCP times out, a firewall is blocking TCP 53 — that is the fix target.

dig example.com TXT            # look for ';; Truncated'
dig example.com TXT +tcp       # force TCP
dig example.com TXT +bufsize=1232   # modern EDNS size

2. Open TCP port 53 through the firewall

Allow outbound (and for servers, inbound) TCP 53 the same as UDP 53. DNS has required TCP support since the original specification — blocking it breaks large responses and zone transfers.

# example (iptables, server side):
sudo iptables -A INPUT -p tcp --dport 53 -j ACCEPT
sudo iptables -A INPUT -p udp --dport 53 -j ACCEPT

3. Shrink oversized record sets

Flatten SPF includes (each include is a lookup and adds size), delete stale verification TXT records, and split services across subdomains so no single name carries every record.

Frequently Asked Questions

How do I know a response was truncated?

dig prints ';; Truncated, retrying in TCP mode' and the response header shows the tc flag. If the TCP retry succeeds you will just see a normal (larger) answer; if TCP is blocked you will see the truncation message followed by a timeout.

Is it safe to assume DNS only needs UDP?

No — that is the misconception that causes this error. RFC 7766 makes TCP support mandatory for DNS. Zone transfers always used TCP, and any response over the UDP size limit requires it.

What is a good EDNS buffer size?

1232 bytes is the community-agreed default (from DNS Flag Day 2020) — large enough for most answers, small enough to avoid IP fragmentation on typical paths. Servers and resolvers negotiating larger sizes invite fragment drops.
