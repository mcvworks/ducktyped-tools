nodename nor servname provided, or not known

Last updated: July 1, 2026

A macOS and BSD error meaning the system could not resolve a hostname (or service name) — the Mac equivalent of 'unknown host'.

You might see this error as:

  • nodename nor servname provided, or not known
  • ping: cannot resolve: Unknown host
  • ssh: Could not resolve hostname
  • getaddrinfo EAI_NONAME
  • macOS DNS resolution failed

What Does This Error Mean?

This wordy message comes from the BSD getaddrinfo implementation used by macOS. 'Nodename' is the hostname and 'servname' is the service/port; the error fires when neither could be translated — in practice, almost always because the hostname failed to resolve. You will see it from ping, ssh, and many command-line tools on a Mac. The causes are the usual resolution suspects, plus a few macOS-specific ones: the mDNSResponder cache, /etc/hosts formatting, and .local names being handled by Bonjour instead of DNS.

Common Causes

  • The hostname does not resolve — Typo, expired domain, or an internal name that only exists on another network (VPN, office DNS). The Mac's resolver got a definitive 'no such name'.
  • Stale mDNSResponder cache — macOS caches lookups in mDNSResponder. After a domain's records change or a VPN connects, cached negative answers can keep a resolvable name failing.
  • Malformed /etc/hosts entry — A missing newline at the end of /etc/hosts, tabs vs spaces confusion, or a commented-out line means the override you think exists is not being read.
  • .local names going to Bonjour instead of DNS — macOS treats .local as multicast DNS (Bonjour). Corporate domains ending in .local often fail on Macs even though they work fine on Windows and Linux clients.

How to Fix It

1. Flush the macOS DNS cache

The first thing to try after any DNS change — clears cached negative answers held by mDNSResponder.

sudo dscacheutil -flushcache
sudo killall -HUP mDNSResponder

2. Test what macOS actually resolves

dscacheutil queries through the same system path applications use (dig bypasses it), so it reveals what apps really see — including /etc/hosts entries.

dscacheutil -q host -a name example.com
dig +short example.com   # compare: raw DNS answer

3. Check /etc/hosts formatting

Verify the entry exists, is uncommented, uses a valid IP first, and the file ends with a newline.

cat -A /etc/hosts | tail -5   # shows hidden characters
# valid format:
# 192.168.1.50   myserver.example.com myserver

4. Fix SSH host aliases

For ssh specifically, check ~/.ssh/config — an alias with a wrong or missing HostName resolves the alias itself, which does not exist in DNS.

# ~/.ssh/config
Host myserver          # alias you type
    HostName server1.example.com   # name that must resolve
    User deploy

ssh -v myserver 2>&1 | head -5   # shows the name being resolved

Frequently Asked Questions

What do 'nodename' and 'servname' actually mean?

They are the two arguments of the BSD getaddrinfo call: nodename is the hostname, servname is the service name or port. The error text covers both failing, but in practice it is nearly always the hostname that could not be resolved.

Why does the site load in Safari but ping fails with this error?

Safari may be resolving through a different path — cached results, iCloud Private Relay, or DNS-over-HTTPS. Command-line tools use the system resolver directly. Flush the cache and compare 'dscacheutil -q host -a name' with 'dig' to see where they diverge.

Why do .local hostnames fail on macOS?

macOS reserves .local for Bonjour/multicast DNS and does not send those names to your DNS server by default. If your company uses a .local Active Directory domain, add the domain to the resolver search settings or use the fully qualified non-.local name.
