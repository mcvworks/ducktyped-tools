No servers could be reached

Last updated: July 1, 2026

The dig and nslookup error ';; connection timed out; no servers could be reached' — the tool could not contact any DNS server at all.

You might see this error as:

  • connection timed out; no servers could be reached
  • dig no servers could be reached
  • nslookup connection timed out
  • ;; communications error to 127.0.0.53#53: timed out
  • nslookup no response from server

What Does This Error Mean?

This error means dig or nslookup sent queries to every configured DNS server and got zero responses — not even an error response. It says nothing about the domain being queried; the tool never managed to talk to a DNS server. The fault is always in the path between your machine and the resolver: wrong resolver IP, a firewall silently dropping port 53, the resolver process being down, or no network connectivity at all.

Common Causes

  • The configured resolver IP is wrong or dead — resolv.conf (or the dig @server argument) points at an address where no DNS service is listening — a decommissioned internal server, an old router IP, or a mistyped address.
  • A firewall blocks port 53 — Corporate and cloud firewalls often block outbound UDP/TCP 53 to everything except approved internal resolvers, so queries to public resolvers like 8.8.8.8 are silently dropped.
  • The local stub resolver is down — When resolv.conf points at 127.0.0.53 (systemd-resolved) or 127.0.0.1 (dnsmasq/unbound) and that daemon is stopped, every query times out against localhost.
  • No network connectivity — Interface down, DHCP failure, or a broken default route means no packets reach any server — DNS is just the first thing to notice.

How to Fix It

1. Query a public resolver explicitly

This one test splits the problem: if @1.1.1.1 works, your configured resolver is broken; if it also times out, the network path or firewall is at fault.

dig example.com                 # times out
dig @1.1.1.1 example.com        # explicit public resolver
dig @8.8.8.8 example.com +tcp   # try TCP in case UDP is blocked

2. Check what resolver is actually configured

Verify the nameserver lines and whether they point at a local stub that needs to be running.

cat /etc/resolv.conf
resolvectl status   # if it shows 127.0.0.53
sudo systemctl restart systemd-resolved

3. Test raw reachability of port 53

Confirm packets can reach the resolver at all. If ping works but DNS times out, a firewall is dropping port 53 specifically.

ping -c2 1.1.1.1
nc -zvu 1.1.1.1 53   # UDP
nc -zv 1.1.1.1 53    # TCP

4. Check basic connectivity and routes

If nothing is reachable, fix the network first — DNS will follow.

ip addr show
ip route show
ping -c2 $(ip route | awk '/default/ {print $3; exit}')

Frequently Asked Questions

Does this error mean the domain does not exist?

No. The query never reached a DNS server, so nothing was learned about the domain. A nonexistent domain produces an NXDOMAIN answer instead — which requires a server to respond.

Why does dig fail while websites still load?

The browser may use DNS-over-HTTPS (port 443), bypassing the broken port-53 path that dig uses. That combination — browsing works, dig times out — is a strong hint that a firewall is blocking classic DNS.

Why does 'dig +tcp' work when plain dig times out?

Some networks block or mangle UDP port 53 but allow TCP 53. That is a middlebox/firewall issue worth fixing, since normal resolution tries UDP first and will keep timing out.

Related Errors

  • DNS Server Not Responding — the same condition reported by Windows diagnostics.
  • DNS Query Timeout — timeouts on individual queries.
  • DNS REFUSED — when the server responds but declines to answer.
