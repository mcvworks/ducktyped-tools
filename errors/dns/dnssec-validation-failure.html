DNSSEC Validation Failure

Last updated: July 1, 2026

A domain fails to resolve on validating resolvers because its DNSSEC chain of trust is broken — typically expired signatures or a stale DS record.

You might see this error as:

  • DNSSEC validation failure
  • broken trust chain
  • SERVFAIL DNSSEC
  • delv: resolution failed
  • DNSSEC bogus
  • DS record mismatch

What Does This Error Mean?

DNSSEC adds cryptographic signatures to DNS records. When a validating resolver (Cloudflare 1.1.1.1, Google 8.8.8.8, Quad9) finds signatures that are expired, missing, or do not match the DS record published at the parent zone, it deliberately refuses to return the answer — you get SERVFAIL, and delv reports 'broken trust chain'. The domain seems randomly down: it fails on validating resolvers while still resolving on non-validating ones. The break is almost always on the domain owner's side, introduced by a nameserver migration, an expired signing key, or a leftover DS record.

Common Causes

  • Expired RRSIG signatures — Signatures carry validity windows. If automatic re-signing broke (signing daemon down, cron failure), signatures expire and every validating resolver starts rejecting the zone at once.
  • DS record does not match the DNSKEY — After migrating to a new DNS provider, the old DS record at the registrar still points at the previous provider's keys. The new zone's keys fail validation against the stale DS.
  • Zone moved to a provider without DNSSEC, DS left behind — If DNSSEC was not re-enabled after a migration but the DS record was never removed, validators expect signatures that no longer exist — a guaranteed validation failure.
  • Botched key rollover — Rotating KSK/ZSK keys without following the proper timing (publishing new keys before use, waiting out TTLs) leaves a window where cached DS or DNSKEY records do not match.

How to Fix It

1. Confirm DNSSEC is the cause

Query with checking disabled (+cd). If +cd returns records while a normal query gets SERVFAIL, validation is definitively the problem.

dig example.com               # SERVFAIL
dig example.com +cd           # works -> DNSSEC failure
delv example.com A            # shows 'broken trust chain' detail

2. Locate the break in the chain

DNSViz (dnsviz.net) visualizes the full chain and pinpoints the exact failure — expired signature, missing DNSKEY, or DS mismatch. Compare the DS at the parent with the live DNSKEY.

dig DS example.com @a.gtld-servers.net   # what the parent publishes
dig DNSKEY example.com +dnssec            # what the zone serves

3. Re-sign the zone or update the DS record

If signatures expired, fix the signing pipeline and re-sign. If keys changed, generate the new DS from the current KSK and replace the old DS at your registrar.

4. Remove the DS record if the zone is unsigned

If the new DNS provider does not sign the zone, delete the DS record at the registrar. Validation failures stop once the old DS expires from resolver caches (up to the DS TTL).

Frequently Asked Questions

Why does the domain work on some networks but not others?

Only validating resolvers enforce DNSSEC. Cloudflare, Google, and Quad9 validate and return SERVFAIL for a broken chain; many ISP resolvers do not validate and hand out the records anyway. Inconsistent resolution across networks is the classic DNSSEC-failure signature.

How long until fixes take effect?

Resolvers cache DS and DNSKEY records for their TTLs (often 1–24 hours). After correcting the records, expect residual failures until caches expire — flushing Cloudflare and Google's public caches via their purge pages speeds this up.

Is it safer to just turn DNSSEC off?

Removing the DS record does make the outage stop, and an unsigned zone is still fully functional. You lose protection against DNS spoofing, so the better long-term fix is a provider that automates signing and rollovers rather than leaving DNSSEC off permanently.
