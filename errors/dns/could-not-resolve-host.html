Troubleshooting / DNS / Could not resolve host

Could not resolve host

Last updated: July 1, 2026

The error curl, git, and wget print when a hostname cannot be converted to an IP address — curl reports it as exit code 6.

You might see this error as:

  • curl: (6) Could not resolve host
  • Could not resolve host: github.com
  • wget: unable to resolve host address
  • git could not resolve host
  • curl error 6
  • CURLE_COULDNT_RESOLVE_HOST

What Does This Error Mean?

Command-line tools like curl, git, and wget resolve the hostname in a URL before connecting. When that resolution fails, curl exits with code 6 and this message; git prints the same text when fetching or pushing. The cause is either the name itself (typo, deleted domain, internal-only name) or the machine's resolver setup (no DNS configured, VPN required, proxy required). Because the failure happens before any TCP connection, server-side problems can be ruled out immediately.

Common Causes

  • Typo in the URL or git remote — A misspelled hostname is the single most common cause — for git, the remote URL was saved once with a typo and fails on every operation afterwards.
  • The machine's DNS is not working — If every hostname fails (try a second domain), the machine's resolver configuration is broken — not the specific site.
  • The name is internal and needs VPN or a proxy — Corporate GitLab, private registries, and intranet hosts only resolve through the company VPN or an HTTP proxy. Off VPN, resolution fails with this exact error.
  • Stale negative DNS cache — If the domain was queried while its DNS was broken, a local cache (systemd-resolved, macOS mDNSResponder, or a browser) may keep serving the failure after the domain recovered.

How to Fix It

1. Confirm the exact spelling, then test resolution

Check what name is actually being resolved, then look it up directly. For git, print the remote URL — the typo is usually visible.

git remote -v
dig +short github.com
curl -v https://github.com 2>&1 | head -5

2. Test whether all DNS is down or just this name

If a known-good domain also fails, fix the system resolver rather than chasing the specific hostname.

dig example.com
dig @1.1.1.1 example.com   # works -> your resolver is the problem
cat /etc/resolv.conf

3. Set proxy variables if your network requires one

Behind a corporate proxy, curl and git need the proxy address — with it set, the proxy does the DNS resolution instead of your machine.

export https_proxy=http://proxy.company.com:8080
export http_proxy=http://proxy.company.com:8080
# git-specific alternative:
git config --global http.proxy http://proxy.company.com:8080

4. Flush the local DNS cache

After a domain's DNS was fixed, clear cached negative answers.

# Linux (systemd-resolved):
sudo resolvectl flush-caches
# macOS:
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Windows:
ipconfig /flushdns

Frequently Asked Questions

What does curl exit code 6 mean exactly?

Exit code 6 is CURLE_COULDNT_RESOLVE_HOST: the hostname lookup failed before any connection was attempted. It never indicates a server-side problem — the request never left your machine.

Why does git say 'Could not resolve host: github.com' when github.com loads in my browser?

The browser may be using DNS-over-HTTPS or a different network path (VPN split tunneling), while git uses the system resolver. Test with 'dig github.com' — if that fails, fix the system DNS; if it works, check for a proxy requirement or an /etc/hosts override.

Why does it fail only sometimes?

Intermittent failures point to an unreliable resolver (packet loss on UDP port 53, an overloaded router DNS, or a flaky VPN). Switching to a public resolver like 1.1.1.1 or 8.8.8.8 usually stabilizes it.
