Could not resolve host

Last updated: September 23, 2026

curl error 6 means it could not resolve the target hostname. Start with the exact name in the error, then compare the same lookup from your machine and network.

You might see this error as:

  • curl: (6) Could not resolve host
  • Could not resolve host: github.com
  • wget: unable to resolve host address
  • git could not resolve host
  • curl error 6
  • CURLE_COULDNT_RESOLVE_HOST

What Does This Error Mean?

Command-line tools like curl, git, and wget resolve the hostname in a URL before connecting. When that resolution fails, curl exits with code 6 and this message; git prints the same text when fetching or pushing. The cause is either the name itself (typo, deleted domain, internal-only name) or the machine's resolver setup (no DNS configured, VPN required, proxy required). The web request has not reached the target application, but the domain’s authoritative DNS can still be the cause. DNS queries may already have crossed the network; this error does not prove that all network traffic stayed on your machine.

Common Causes

  • Typo in the URL or git remote — A misspelled hostname or wrongly quoted command can make curl try to resolve the wrong name. For Git, inspect the saved remote URL before changing DNS settings.
  • The machine's DNS is not working — If several public hostnames fail, compare resolver results and check the local network or VPN. One failure alone does not identify which DNS server is at fault.
  • The name is internal and needs VPN or a proxy — Corporate GitLab, private registries, and intranet hosts only resolve through the company VPN or an HTTP proxy. Off VPN, resolution fails with this exact error.
  • Stale negative DNS cache — If the domain was queried while its DNS was broken, a local cache (systemd-resolved, macOS mDNSResponder, or a browser) may keep serving the failure after the domain recovered.

How to Fix It

1. Check the hostname and quote the URL

Read the hostname printed after “Could not resolve host.” If it is a stray word from a command, check argument spacing and quoting first. Quote the entire URL so shell characters such as & are not interpreted as commands. curl’s verbose output helps identify the request, but may contain private URLs or headers; redact it before sharing.

curl -v --connect-timeout 10 "https://example.com/"
# For Git, inspect the stored hostname:
git remote -v

2. Compare local and public DNS results

Test a public hostname through your default resolver and an independent one. Different results narrow the investigation to DNS configuration, filtering, or caching; they do not prove which component is broken. For internal company names, use the required VPN and company DNS. A public resolver is not a replacement for private DNS.

nslookup example.com
nslookup example.com 1.1.1.1
# On Linux, inspect resolver configuration:
cat /etc/resolv.conf

3. Check the required VPN and proxy settings

Connect to the required VPN for internal hosts. If your network uses a proxy, use the address supplied by its administrator. curl recognizes per-protocol proxy variables and no_proxy exclusions. A stale proxy setting can change the request path; do not add a proxy just to hide a DNS failure. curl’s proxy-variable reference describes the rules.

# Example only: substitute your organization’s actual proxy
https_proxy="http://proxy.company.example:8080" curl -I "https://example.com/"

4. Flush the local DNS cache

After fixing the underlying DNS issue, clear a cached negative answer if your system runs a caching resolver. Flushing a cache cannot repair a misspelled domain, a missing DNS record, or a disconnected VPN. Run only the command for your operating system; resolvectl requires systemd-resolved.

# Linux (systemd-resolved):
sudo resolvectl flush-caches
# macOS:
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
# Windows:
ipconfig /flushdns

5. Repeat the check where the failing command runs

If curl works on the host but fails in Docker, WSL, or a CI runner, test DNS in that environment too. Its resolver and proxy settings may differ. Replace CONTAINER below with an existing container name; nslookup must already be available inside it.

docker exec CONTAINER cat /etc/resolv.conf
docker exec CONTAINER nslookup example.com

Frequently Asked Questions

What does curl exit code 6 mean exactly?

Exit code 6 is CURLE_COULDNT_RESOLVE_HOST: curl could not resolve the remote hostname. It has not reached the target web application, but DNS traffic may already have left the machine. The cause may be local configuration, the network, or the domain’s DNS.

Why does git say 'Could not resolve host: github.com' when github.com loads in my browser?

The browser can use a different resolver or proxy path from Git. Compare the hostname in git remote -v with the browser URL, then test resolution from the same terminal, container, or VPN context where Git fails. Browser access alone does not prove that Git’s network path works.

Why does it fail only sometimes?

Intermittent failures can come from a resolver, network connectivity, caching, or a VPN. Compare results across resolvers and times before changing settings. Keep internal company hostnames on the company’s DNS; public resolvers cannot resolve private zones.

How is curl error 6 different from errors 5 and 7?

Error 5 means the proxy hostname could not be resolved. Error 6 concerns the target hostname. Error 7 means curl could not connect to the host or proxy after reaching the connection stage. Diagnose the stage named by the error instead of changing unrelated credentials or TLS settings.

Related Errors

  • getaddrinfo ENOTFOUND — the same failure in Node.js.
  • Temporary failure in name resolution — the Linux system-level variant.
  • NXDOMAIN — what the DNS server answers for nonexistent names.
  • Git repository not found — The host is reachable but the repository URL or access rights need checking.
