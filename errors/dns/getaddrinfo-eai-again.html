Troubleshooting / DNS / getaddrinfo EAI_AGAIN

getaddrinfo EAI_AGAIN

Last updated: July 1, 2026

A temporary DNS resolution failure in Node.js and other applications — the resolver could not get an answer in time, often inside Docker containers or CI environments.

You might see this error as:

  • getaddrinfo EAI_AGAIN
  • Error: getaddrinfo EAI_AGAIN
  • EAI_AGAIN docker
  • npm ERR! errno EAI_AGAIN
  • request to https://registry.npmjs.org failed EAI_AGAIN

What Does This Error Mean?

EAI_AGAIN is the resolver's way of saying 'try again later': the DNS lookup did not definitively fail, but no answer arrived in time. Unlike ENOTFOUND (the name does not exist), EAI_AGAIN is an infrastructure problem — the DNS server is slow, unreachable, or overloaded. It is especially common inside Docker builds and containers, where DNS requests pass through Docker's embedded resolver at 127.0.0.11 and then to whatever upstream the host provides.

Common Causes

  • Upstream DNS server is slow or unreachable — The configured resolver did not respond within the timeout. The name may be perfectly valid — the path to the resolver is the problem.
  • Docker's embedded DNS cannot reach its upstream — Containers resolve via 127.0.0.11, which forwards to the host's resolvers. VPN software, firewalls, or a host resolv.conf pointing at an unreachable server make every container lookup time out.
  • Kubernetes ndots expansion multiplies queries — The default ndots:5 setting makes the resolver try several search-domain suffixes before the real name, multiplying DNS traffic. Under load, some of those lookups time out and surface as EAI_AGAIN.
  • Rate limiting or packet loss on port 53 — Public resolvers rate-limit heavy clients, and lossy networks drop UDP DNS packets. High-volume services that resolve on every request are most exposed.

How to Fix It

1. Test resolution directly against a known resolver

Distinguish 'my resolver is broken' from 'the network is down' by querying a public resolver explicitly.

dig example.com            # uses configured resolver
dig @1.1.1.1 example.com   # bypasses it
# in a container:
docker run --rm alpine nslookup example.com

2. Configure Docker's DNS explicitly

Point the Docker daemon at reliable resolvers so containers stop depending on a fragile host configuration. Restart Docker afterwards.

# /etc/docker/daemon.json
{
  "dns": ["1.1.1.1", "8.8.8.8"]
}

sudo systemctl restart docker

3. Retry with backoff for transient failures

Because EAI_AGAIN is by definition temporary, network code that talks to external APIs should treat it as retryable rather than fatal.

async function fetchWithRetry(url, tries = 3) {
  for (let i = 0; i < tries; i++) {
    try { return await fetch(url); }
    catch (e) {
      if (e.cause?.code !== 'EAI_AGAIN' || i === tries - 1) throw e;
      await new Promise(r => setTimeout(r, 500 * 2 ** i));
    }
  }
}

4. Reduce ndots or use fully-qualified names in Kubernetes

Appending a trailing dot ('api.example.com.') or lowering ndots stops the resolver from trying cluster search domains for external names.

# pod spec:
dnsConfig:
  options:
    - name: ndots
      value: "2"

Frequently Asked Questions

What is the difference between EAI_AGAIN and ENOTFOUND?

ENOTFOUND is a definitive answer: the name does not exist. EAI_AGAIN means no definitive answer arrived — the resolver timed out or was unreachable. ENOTFOUND points at the hostname; EAI_AGAIN points at DNS infrastructure.

Why does 'npm install' fail with EAI_AGAIN inside docker build?

During builds, BuildKit containers use the host's DNS configuration. If the host resolv.conf points at a VPN-only or systemd-resolved stub address the build network cannot reach, registry lookups time out. Setting explicit DNS servers in /etc/docker/daemon.json fixes it.

Can EAI_AGAIN be permanent?

If the configured resolver is permanently unreachable, every lookup returns EAI_AGAIN forever. 'Temporary' describes the protocol semantics, not a guarantee it will heal — check the resolver path if the error persists for more than a minute.
