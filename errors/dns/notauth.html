DNS NOTAUTH

Last updated: July 1, 2026

DNS response code 9 — the server is not authoritative for the zone, or the request was not properly authorized. Common in zone transfers and dynamic updates.

You might see this error as:

  • NOTAUTH
  • RCODE 9
  • Not Authoritative
  • nsupdate NOTAUTH
  • zone transfer NOTAUTH
  • TSIG BADKEY
  • lame delegation

What Does This Error Mean?

NOTAUTH means the DNS server you contacted told you 'that zone is not mine' — you sent a zone transfer request, dynamic update, or SOA query for a zone the server is not authoritative for. It also doubles as an authorization failure when TSIG-signed requests carry a bad or unknown key. NOTAUTH is an operator error class: something is pointed at the wrong server (a lame delegation, an update aimed at a resolver), or the server that should host the zone failed to load it.

Common Causes

  • Update or transfer sent to the wrong server — nsupdate must target the zone's primary authoritative server, and AXFR/IXFR must target a server that actually hosts the zone. Sending either to a recursive resolver or an unrelated nameserver yields NOTAUTH.
  • The zone failed to load on the server — A syntax error in the zone file or configuration means the server that is supposed to be authoritative silently is not — it answers NOTAUTH (or SERVFAIL) for its own zone.
  • Lame delegation — The parent zone's NS records point at a server that does not host the zone (decommissioned secondary, provider change not cleaned up). Resolvers following the delegation get NOTAUTH.
  • TSIG key problems — Signed updates or transfers with a key the server does not recognize (name mismatch, wrong secret, clock skew beyond the TSIG fudge window) are rejected with NOTAUTH and a TSIG error such as BADKEY or BADTIME.

How to Fix It

1. Confirm which servers are really authoritative

Ask the parent for the delegation, then ask each listed server directly for the SOA. Every authoritative server should answer with the aa flag set.

dig NS example.com +short
dig @ns1.example.com example.com SOA +norecurse
# look for 'flags: qr aa' in the response

2. Point updates at the primary server

Find the primary from the SOA MNAME field and direct nsupdate there explicitly.

dig example.com SOA +short   # first field = primary (MNAME)
nsupdate -k key.conf <<'EOF'
server primary.example.com
zone example.com
update add test.example.com 300 A 192.0.2.1
send
EOF

3. Check the zone loads on the server

On the server itself, validate configuration and zone file, then reload and watch the logs.

named-checkconf
named-checkzone example.com /etc/bind/zones/example.com.db
sudo rndc reload example.com
sudo journalctl -u named -n 20

4. Verify TSIG keys and clocks match

The key name and secret must match exactly on both ends, and both machines need accurate time — TSIG allows only a small clock skew (default 300 seconds).

# test a signed transfer:
dig @ns1.example.com example.com AXFR -y hmac-sha256:keyname:BASE64SECRET
timedatectl   # confirm NTP-synced time on both hosts

Frequently Asked Questions

What is a lame delegation?

A delegation is 'lame' when the parent zone lists a nameserver that does not actually answer authoritatively for the child zone. Queries to it return NOTAUTH or REFUSED, causing slow or failed resolution. Fix it by updating the NS records at the registrar to match servers that really host the zone.

Why does my secondary server return NOTAUTH for its own zone?

The zone transfer from the primary never succeeded, so the secondary has no zone data. Check allow-transfer settings on the primary, TSIG keys on both sides, and the secondary's logs for transfer failures.

NOTAUTH vs REFUSED — which is which?

NOTAUTH: 'this zone is not mine (or your signature is not valid)'. REFUSED: 'I could answer, but policy says no' — like recursion denied to outside clients. Both indicate you are talking to the wrong server or without the right authorization, but REFUSED is a deliberate policy response.

Related Errors

  • DNS REFUSED — policy-based rejection of queries or transfers.
  • DNS YXDOMAIN — dynamic-update prerequisite conflicts.
  • DNS SERVFAIL — what unloaded zones often produce for resolvers.
