SMTP 503 — Bad Sequence of Commands

Last updated: March 8, 2026

SMTP commands were sent in an incorrect order

You might see this error as:

  • SMTP 503
  • 503 Bad sequence of commands
  • 503 Need MAIL before RCPT
  • 503 Sender already specified

What Does This Error Mean?

SMTP 503 is a permanent error indicating that the client sent a valid SMTP command at the wrong point in the SMTP conversation. SMTP requires commands to follow a specific sequence: greeting, EHLO/HELO, optional STARTTLS and AUTH, then MAIL FROM, RCPT TO, DATA, and QUIT. Sending a command out of this expected order causes the server to reject it with a 503 response.

Common Causes

  • MAIL FROM sent before EHLO — The client attempted to send a MAIL FROM command before completing the initial EHLO or HELO handshake. The server requires the greeting exchange before accepting any mail transaction commands.
  • DATA sent before RCPT TO — The client attempted to send the message body (DATA command) without first specifying at least one recipient with RCPT TO. The server cannot accept message data without knowing the recipient.
  • Duplicate MAIL FROM without RSET — The client sent a second MAIL FROM command without first resetting the transaction with RSET. A new mail transaction requires either RSET to cancel the previous one or completion of the previous transaction.
  • AUTH attempted after MAIL FROM — The client tried to authenticate after already beginning a mail transaction. Authentication must occur before the MAIL FROM command, typically right after EHLO.
  • STARTTLS sent after mail transaction started — The client attempted to upgrade to TLS after already starting a mail transaction. STARTTLS must be issued immediately after the EHLO response and before any authentication or mail commands.

How to Fix It

1. Follow the correct SMTP command sequence

Ensure your SMTP client sends commands in the proper order.

# Correct SMTP sequence
EHLO client.example.com
STARTTLS                        # optional, before AUTH
EHLO client.example.com         # re-issue after STARTTLS
AUTH LOGIN                      # optional, before MAIL FROM
MAIL FROM:<sender@example.com>
RCPT TO:<recipient@example.com>
DATA
...message content...
.
QUIT

2. Reset the transaction when needed

If you need to start a new mail transaction in the same session, use the RSET command to reset the server state.

# Reset and start new transaction
RSET
MAIL FROM:<newsender@example.com>
RCPT TO:<newrecipient@example.com>

3. Re-issue EHLO after STARTTLS

After a successful STARTTLS upgrade, the SMTP session is reset. You must send EHLO again before proceeding with AUTH or MAIL commands.

Frequently Asked Questions

Why do I need to send EHLO again after STARTTLS?

STARTTLS upgrades the connection to TLS, which effectively resets the SMTP session. The server may advertise different capabilities over the encrypted connection (such as AUTH mechanisms), so a new EHLO exchange is required.

Can pipelining cause 503 errors?

Pipelining allows a client to send multiple commands without waiting for individual responses, but the commands must still be in the correct logical order. If commands are pipelined in the wrong sequence, the server will respond with 503 for the out-of-order commands.

Is SMTP 503 always a client-side problem?

Almost always, yes. The error means your client sent a valid command at the wrong time. Rarely, a buggy server may incorrectly track session state and return 503 for correctly sequenced commands.
