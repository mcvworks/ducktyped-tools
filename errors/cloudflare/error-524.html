Cloudflare Error 524 — A Timeout Occurred

Last updated: July 3, 2026

Cloudflare connected to the origin and delivered the request, but the origin did not complete an HTTP response within 100 seconds — long jobs and slow queries are the usual story.

You might see this error as:

  • Cloudflare Error 524
  • a timeout occurred cloudflare
  • error 524
  • cloudflare 100 second timeout
  • http 524

What Does This Error Mean?

A 524 means everything network-level worked — connection, request delivery — and then the origin took longer than Cloudflare's proxy read window (100 seconds on free/pro/business plans) to return a response. It is the signature error of long-running synchronous work behind Cloudflare: report generation, big exports, admin bulk actions, slow database queries. The options are the classic three: make the endpoint faster, move the work out of the request/response cycle, or take that route out from behind Cloudflare's proxy.

Common Causes

  • Endpoints that legitimately run long — Report/exports/imports executing inside one HTTP request — anything that can exceed 100 seconds under real data volumes.
  • Slow database queries or external calls — An unindexed query or a hanging third-party API pushes an ordinarily fast endpoint past the window under certain inputs.
  • Origin worker starvation — The response would be fast, but the request waits in a saturated worker queue longer than the window — a capacity symptom rather than an endpoint bug.

📡 Them or you? Before changing anything, check live Cloudflare status on DTMonitor — during a provider incident this error shows up on perfectly healthy setups, and the fix is to wait.

How to Fix It

1. Time the slow endpoint directly at the origin

Measure without Cloudflare to see the true duration and find the budget you must get under.

time curl -sk https://ORIGIN_IP/admin/export -H 'Host: example.com' -o /dev/null

2. Move long work to background jobs

The robust fix: the request enqueues the work and returns immediately; the client polls or gets notified. HTTP requests measured in minutes are fragile everywhere, not just behind Cloudflare.

# pattern:
# POST /exports        -> 202 Accepted, {"job":"abc123"}
# GET  /exports/abc123 -> {"status":"running|done","url":...}

3. Fix the query/dependency behind unexpected slowness

For endpoints that should be fast: EXPLAIN the queries, add timeouts to outbound API calls, and check worker saturation during 524 bursts.

4. Take unavoidable long routes out of the proxy

Serve them from a grey-clouded (DNS-only) subdomain so Cloudflare's window does not apply — accepting that this exposes the origin IP for that hostname. Enterprise plans can raise the timeout instead.

# dashboard: DNS record e.g. jobs.example.com -> grey cloud (DNS only)
# then run the slow endpoints on jobs.example.com

Frequently Asked Questions

Can I raise the 100-second limit?

Only on Enterprise plans (proxy_read_timeout is configurable there). On free/pro/business the window is fixed — the practical answers are background jobs or a DNS-only route for the slow endpoints.

Why do I get 524 on WebSocket or long-poll endpoints?

The 100-second rule applies to the initial HTTP response. Established WebSockets are exempt, but a server that takes too long to complete the upgrade handshake, or long-polling that holds the first response beyond the window, will trip 524. Send headers/heartbeats early, or move the endpoint off-proxy.

Is 524 the same as 504 Gateway Timeout?

Conceptually yes — a proxy giving up on a slow upstream. 504 is the standard code any proxy uses; 524 is Cloudflare's specific 'origin exceeded my response window' page, which tells you exactly which layer timed out and what the budget was.

Related Errors

  • 504 Gateway Timeout — the generic upstream timeout.
  • Nginx Upstream Timed Out — the same pattern at the origin's own proxy.
  • Cloudflare Error 522 — timeouts at the connection stage.
