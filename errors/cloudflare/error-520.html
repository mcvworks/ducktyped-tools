Cloudflare Error 520 — Web Server Returns an Unknown Error

Last updated: July 3, 2026

Cloudflare reached the origin server, but the response was empty, malformed, or cut off — something Cloudflare could not interpret as valid HTTP.

You might see this error as:

  • Cloudflare Error 520
  • web server returns an unknown error
  • error 520
  • cloudflare 520 origin error
  • http 520

What Does This Error Mean?

Error 520 is Cloudflare's catch-all for 'the origin answered, but not with usable HTTP': an empty response, a reset connection after the request was sent, or headers too large to process. Unlike 521 (refused) or 522 (silence), the TCP connection worked — the origin then misbehaved. That makes it an origin-side bug hunt: application crashes mid-request, a web server resetting connections under load, or a response exceeding Cloudflare's header limits.

Common Causes

  • Application crashing mid-response — The origin process segfaults or is killed while writing the response — Cloudflare sees a connection that opens, receives the request, and dies.
  • Oversized response headers — Responses with very large header blocks (runaway cookies, debug headers — beyond roughly 16KB) exceed what Cloudflare accepts and are treated as invalid.
  • Connection resets from the origin stack — Aggressive keepalive timeouts, TCP resets from an overloaded server or an intermediate firewall, or a web server restart during the request.
  • Non-HTTP service answering the port — The origin IP/port in Cloudflare DNS points at something that is not speaking HTTP where Cloudflare expects it.

How to Fix It

1. Correlate with origin logs at the exact timestamps

520s always have an origin-side story. Check the web server error log and the app's crash logs around the Ray ID's time (shown on the error page).

sudo tail -100 /var/log/nginx/error.log
sudo journalctl -u myapp --since '15 minutes ago'
dmesg | grep -iE 'segfault|oom' | tail

2. Test the origin directly, bypassing Cloudflare

Request the origin IP with the right Host header. If this also fails or returns garbage, the origin is confirmed as the problem.

curl -v --resolve example.com:443:ORIGIN_IP https://example.com/ -o /dev/null
# or temporarily grey-cloud the DNS record in the Cloudflare dashboard
# (proxy off) and retest through the domain

3. Check response header size on the failing routes

Hunt for endpoints setting enormous cookies or debug headers.

curl -s -D - -o /dev/null https://ORIGIN_IP/failing-path -H 'Host: example.com' -k | wc -c

4. Stabilize keepalive between origin and Cloudflare

Make the origin's keepalive timeout comfortably longer than a few seconds so it does not reset connections Cloudflare is reusing.

# nginx:
keepalive_timeout 90s;
# apache:
KeepAlive On
KeepAliveTimeout 90

Frequently Asked Questions

I am just a visitor — can I do anything about a 520?

Very little: refresh after a minute, and try another network to rule out a local edge case. The failure is between Cloudflare and the website's own server, so the fix belongs to the site owner. The Ray ID on the error page helps the owner find your exact request in their logs.

What is a Ray ID and why does every Cloudflare error show one?

A unique identifier for the request that failed. Site owners can search it in the Cloudflare dashboard (and correlate the timestamp with origin logs) to find precisely what happened to that one request — always include it in support reports.

How is 520 different from 502 Bad Gateway?

502 is the standard 'upstream sent an invalid response' code and can come from any proxy in the chain, including your own nginx. 520 is Cloudflare-specific and means Cloudflare itself received the unusable response from your origin. If your origin runs a reverse proxy too, a backend failure can surface as either — the origin logs disambiguate.

Related Errors

  • 502 Bad Gateway — the generic upstream-response failure.
  • Cloudflare Error 521 — the origin refused the connection.
  • Cloudflare Error 522 — the origin never answered at all.
