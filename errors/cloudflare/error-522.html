Cloudflare Error 522 — Connection Timed Out

Last updated: July 3, 2026

Cloudflare's attempt to open a TCP connection to the origin produced no answer at all within the timeout — packets are being dropped, or the origin is too overloaded to accept.

You might see this error as:

  • Cloudflare Error 522
  • connection timed out cloudflare
  • error 522
  • cloudflare 522 fix
  • http 522

What Does This Error Mean?

Where 521 is an active refusal, 522 is silence: Cloudflare sent connection packets to the origin and nothing came back in time (Cloudflare tries for roughly 15 seconds). Silence on the network means dropped packets — a firewall discarding (not rejecting) Cloudflare's ranges, an origin so overloaded its connection queue is full, an origin IP in Cloudflare DNS that no longer belongs to your server, or a broken network path. The most common single cause in practice: security tooling silently dropping Cloudflare's IP ranges.

Common Causes

  • Firewall silently dropping Cloudflare traffic — DROP rules (vs REJECT) at the host or hosting-provider layer discard the packets — from Cloudflare's view the origin simply never answers.
  • Origin overloaded — Connection backlog full, CPU pinned, or out of workers — the machine is technically reachable but cannot complete a TCP handshake in time.
  • Stale origin IP in Cloudflare DNS — The server moved (new host, new IP after resize) but the Cloudflare DNS record still points at the old address — connection attempts go to a machine that is no longer yours.
  • Network path problems — Routing failures between Cloudflare's edge and the origin's network — rarer, and usually visible to the hosting provider.

How to Fix It

1. Verify the origin IP Cloudflare uses is correct

Compare the DNS record in the Cloudflare dashboard against the server's real address — after any migration this is suspect number one.

# on the origin:
curl -s ifconfig.me
# compare with the A/AAAA record content in Cloudflare DNS (dashboard),
# NOT with public dig — proxied records resolve to Cloudflare IPs publicly

2. Test reachability from outside

If a third machine can connect but Cloudflare cannot, something filters by source — allowlist Cloudflare's ranges through every firewall layer.

nc -zv ORIGIN_IP 443
curl -vk https://ORIGIN_IP/ -H 'Host: example.com' -m 10 -o /dev/null
# allowlist (iptables example):
for ip in $(curl -s https://www.cloudflare.com/ips-v4); do sudo iptables -A INPUT -p tcp -s $ip --dport 443 -j ACCEPT; done

3. Check origin load during the incidents

Intermittent 522s that track traffic peaks point at capacity, not filtering.

uptime && free -m
ss -s                     # socket overview; watch synrecv counts
sudo ss -tlnp state syn-recv | wc -l

4. Keep keepalive on and generous

Origins that disable HTTP keepalive force constant new connections from Cloudflare, amplifying handshake pressure and 522 risk under load.

# nginx:
keepalive_timeout 90s;
keepalive_requests 1000;

Frequently Asked Questions

522 comes and goes every few minutes — what does that pattern mean?

Intermittence points at load (backlog fills during bursts) or a flapping network path, rather than a hard misconfiguration. Correlate the times with traffic and server metrics; if load is flat, ask the host about packet loss toward Cloudflare's ranges.

How do I find my real origin IP if DNS shows Cloudflare addresses?

Proxied (orange-cloud) records intentionally resolve to Cloudflare IPs publicly. The origin value is only visible in the Cloudflare DNS dashboard — or on the server itself ('curl ifconfig.me'). Verify those two match; public dig cannot tell you.

DROP vs REJECT — why does it change the error code?

REJECT sends back 'connection refused', which Cloudflare reports as 521. DROP discards packets silently, so Cloudflare waits and times out — 522. Same firewall, different verb, different error page; useful forensics when deciding where to look.
