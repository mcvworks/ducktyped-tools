Cloudflare Error 1016 — Origin DNS Error

Last updated: July 3, 2026

Cloudflare could not resolve the origin's address: the DNS record behind the proxy points at a hostname that does not resolve — a broken CNAME target is the classic cause.

You might see this error as:

  • Cloudflare Error 1016
  • origin dns error
  • error 1016 cloudflare

What Does This Error Mean?

Before connecting anywhere, Cloudflare must turn your DNS configuration into an origin IP. Error 1016 means that step failed: a proxied CNAME points at a hostname that returns NXDOMAIN (deleted Heroku/hosting endpoint, decommissioned load balancer, typo), or a Load Balancer references origins that no longer resolve. Unlike the 52x family — where an address existed but misbehaved — 1016 means there was never an address to try. It is purely an owner-side configuration problem.

Common Causes

  • CNAME target no longer exists — The record points at something like old-app.herokuapp.com or an ELB hostname that was deleted — the target now returns NXDOMAIN.
  • Typo in the target hostname — A misspelled CNAME content resolves nowhere from day one, or after an edit.
  • Cloudflare Load Balancer with dead origins — Pools referencing origin hostnames that stopped resolving; the balancer has no address to hand to the proxy.
  • Deleted A/AAAA record with a dangling reference — Internal record shuffles that leave the proxied name pointing at another record that was removed.

How to Fix It

1. Resolve the CNAME target independently

Take the record's content from the Cloudflare dashboard and test it from anywhere — if it does not resolve publicly, that is the whole bug.

dig +short your-app.hosting-provider.com
# empty/NXDOMAIN -> fix or replace the target

2. Point the record at something that exists

Update the CNAME to the hosting provider's current endpoint (they change after replatforming), or replace it with an A record to the server's IP.

3. Audit Load Balancer pools if you use them

Traffic → Load Balancing: every origin's hostname must resolve; health checks flag dead ones once the names work again.

4. After hosting migrations, sweep all proxied records

List every orange-cloud record and verify each target still resolves — migrations tend to orphan more than one.

# quick audit loop for CNAME targets you exported:
while read host; do printf '%-40s %s\n' "$host" "$(dig +short "$host" | head -1)"; done < targets.txt

Frequently Asked Questions

Visitors are reporting 1016 — is there anything they can do?

No — 1016 is entirely a site-configuration failure; no retry, VPN, or cache flush on the visitor's side changes it. The useful visitor action is telling the owner, ideally with the Ray ID.

How is 1016 different from 523 (origin unreachable)?

523: Cloudflare had an IP but could not route to it. 1016: Cloudflare could not even obtain an IP — name resolution of the origin failed. 523 sends you to check the IP's validity; 1016 sends you to check the record's target hostname.

Why did this appear right after we moved hosting?

Replatforming changes provider endpoints (herokuapp.com → new platform hostnames, new load balancer names). Any proxied CNAME still pointing at the old endpoint breaks the moment the provider deletes it — sometimes weeks after the migration, which hides the connection.
