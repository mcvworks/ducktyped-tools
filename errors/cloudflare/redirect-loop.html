Cloudflare Redirect Loop (ERR_TOO_MANY_REDIRECTS)

Last updated: July 3, 2026

The browser reports ERR_TOO_MANY_REDIRECTS on a site behind Cloudflare — almost always Flexible SSL mode fighting an origin that redirects HTTP to HTTPS.

You might see this error as:

  • cloudflare too many redirects
  • ERR_TOO_MANY_REDIRECTS cloudflare
  • flexible ssl redirect loop
  • cloudflare redirect loop wordpress
  • redirected you too many times cloudflare

What Does This Error Mean?

The classic Cloudflare loop has a precise mechanism: in Flexible SSL mode, visitors connect to Cloudflare over HTTPS, but Cloudflare fetches from the origin over plain HTTP. If the origin is configured to redirect HTTP to HTTPS (as every security guide recommends), it answers Cloudflare's HTTP fetch with a redirect to https://… — which the visitor is already on, so the browser re-requests, Cloudflare fetches over HTTP again, and the loop spins until the browser gives up. The durable fix is ending the protocol mismatch: a certificate on the origin and Full (strict) mode.

Common Causes

  • Flexible SSL + origin HTTPS redirect — The defining combination: Cloudflare talks HTTP to the origin, the origin insists on HTTPS, each answers the other forever.
  • Double redirect logic — Cloudflare's 'Always Use HTTPS' plus an origin/.htaccess redirect that checks the wrong signal (ignoring X-Forwarded-Proto) — each layer 'fixes' the scheme in turn.
  • Application-level scheme detection behind the proxy — Frameworks (WordPress siteurl, Laravel, Django SECURE_PROXY_SSL_HEADER) seeing HTTP from the proxy and forcing their canonical HTTPS URL in responses.
  • Conflicting page rules or redirect rules — A Cloudflare redirect rule and an origin rule bouncing between www/apex or trailing-slash variants.

How to Fix It

1. See the loop explicitly

Watch the redirect chain — the repeating Location target names the fight.

curl -sIL -o /dev/null -w '%{http_code} %{url_effective}\n' https://example.com --max-redirs 5
# or step by step:
curl -sI https://example.com | grep -iE 'HTTP/|location'

2. Switch to Full (strict) with an origin certificate

Ends the mismatch: Cloudflare fetches over HTTPS, the origin's redirect never fires. The free Origin CA certificate makes this a minutes-long change.

# dashboard: SSL/TLS -> Overview -> Full (strict)
# origin (nginx) with the Origin CA cert installed:
ssl_certificate     /etc/ssl/cf-origin/example.com.pem;
ssl_certificate_key /etc/ssl/cf-origin/example.com.key;

3. If you must stay on Flexible temporarily, stop the origin redirect

Remove the HTTP→HTTPS redirect at the origin (or condition it on the forwarded protocol) so the fetch succeeds. Recognize this leaves the Cloudflare-to-origin leg unencrypted.

# nginx: respect the original visitor scheme
if ($http_x_forwarded_proto = 'http') {
    return 301 https://$host$request_uri;
}
# (redirect only when the VISITOR used http — not when Cloudflare fetches)

4. Let one layer own the HTTPS redirect

Enable 'Always Use HTTPS' in Cloudflare and remove origin-side blanket redirects (or vice versa) — one owner, no ping-pong. For WordPress, also set siteurl/home to https and trust the proxy header.

# wp-config.php behind Cloudflare:
if (isset($_SERVER['HTTP_X_FORWARDED_PROTO']) && $_SERVER['HTTP_X_FORWARDED_PROTO'] === 'https') {
    $_SERVER['HTTPS'] = 'on';
}

Frequently Asked Questions

Why does the loop only affect some pages or only after login?

Application-level redirects (canonical URLs, auth flows) are route-specific. The protocol mismatch is global, but only the routes that enforce a scheme — login pages, admin areas, canonical redirects — actually bounce. Same fix: end the mismatch with Full (strict) and trust X-Forwarded-Proto.

Is clearing cookies the fix, like generic redirect-loop advice says?

For the Cloudflare/Flexible loop, no — no cookie is involved, and the loop reproduces in a fresh browser. Cookie-clearing fixes a different family of loops (stale session state). If curl -sIL shows the http↔https ping-pong, it is the protocol loop and configuration is the only fix.

Why does everyone say to avoid Flexible mode?

Because it encrypts only the visitor-to-Cloudflare half, silently leaving Cloudflare-to-origin traffic as plain HTTP — and it manufactures exactly this loop when origins enforce HTTPS. It exists for origins that cannot get any certificate; with free Origin CA certificates, that excuse rarely applies anymore.
