Cloudflare Error 521 — Web Server Is Down

Last updated: July 3, 2026

Cloudflare tried to connect to the origin server and the connection was actively refused — nothing is accepting connections on the origin's port.

You might see this error as:

  • Cloudflare Error 521
  • web server is down
  • error 521
  • cloudflare 521 fix
  • http 521

What Does This Error Mean?

A 521 is a refused TCP connection: Cloudflare reached the origin machine, and the machine said 'nothing is listening here'. Two causes cover nearly every case — the web server really is down (crashed, stopped, not listening on the HTTPS port), or a firewall on the origin is rejecting Cloudflare's IP ranges specifically. The second is sneakier: once a site moves behind Cloudflare, ALL traffic arrives from Cloudflare's published IP blocks, and security tools that rate-limit or block 'suspiciously busy' ranges end up refusing exactly the traffic that matters.

Common Causes

  • The origin web server is not running — Crashed, failed to restart after a deploy or reboot, or listening only on port 80 while Cloudflare connects to 443 (default in Full SSL modes).
  • Firewall rejecting Cloudflare's IP ranges — iptables/ufw rules, hosting-panel security, or DDoS appliances refusing connections from Cloudflare's ranges — often after automated tools flagged the concentrated traffic.
  • Wrong port expectations — The origin serves HTTPS on a nonstandard port or only plain HTTP, while the Cloudflare SSL mode dictates a 443 connection.

How to Fix It

1. Check the web server is up and listening

On the origin, confirm the service and its ports.

sudo systemctl status nginx    # or apache2/caddy/myapp
sudo ss -tlnp | grep -E ':443 |:80 '
sudo systemctl restart nginx

2. Test a direct connection from outside

From any machine (not the origin itself), try the origin IP. Refused here = server/port problem; works here but 521 through Cloudflare = firewall blocking Cloudflare specifically.

curl -vk https://ORIGIN_IP/ -H 'Host: example.com' -o /dev/null
nc -zv ORIGIN_IP 443

3. Allowlist Cloudflare's IP ranges

Fetch the published ranges and permit them through every firewall layer (host + hosting provider).

# current ranges:
curl -s https://www.cloudflare.com/ips-v4
curl -s https://www.cloudflare.com/ips-v6
# ufw example:
for ip in $(curl -s https://www.cloudflare.com/ips-v4); do sudo ufw allow from $ip to any port 443 proto tcp; done

4. Align the SSL mode with what the origin serves

If the origin only speaks HTTP on 80 (temporarily), Cloudflare's SSL mode must not demand 443 — though the real fix is putting a certificate on the origin and using Full (strict).

Frequently Asked Questions

The server looks fine when I SSH in — why does Cloudflare say it is down?

Because 'up' for Cloudflare means 'accepts TCP connections from Cloudflare's IPs on the right port'. A running machine with a stopped web server, a 443 listener bound only to localhost, or a firewall dropping Cloudflare's ranges all look identical from the edge: refused. The direct-connection test from a third machine separates the cases.

Why would a firewall block Cloudflare of all things?

Behind Cloudflare, the origin sees the entire internet funneled through a few hundred Cloudflare IPs. Naive rate-limiters and brute-force blockers (fail2ban on raw IPs, hosting 'attack protection') interpret that concentration as an attack and ban the ranges — taking the site down for everyone. Allowlist the published ranges and rate-limit on the real client IP (CF-Connecting-IP header) instead.

Is 521 my host's fault or Cloudflare's?

Practically always the origin side (server or firewall). Cloudflare-side incidents exist but are rare and visible on cloudflarestatus.com — check it in ten seconds, then spend your time on the origin.
