Cloudflare Error 1015 — You Are Being Rate Limited

Last updated: July 3, 2026

The request tripped a Rate Limiting rule configured by the site's owner — too many requests from your IP inside the rule's time window.

You might see this error as:

  • Cloudflare Error 1015
  • you are being rate limited
  • error 1015
  • cloudflare rate limited how long

What Does This Error Mean?

Error 1015 means a Cloudflare Rate Limiting rule matched: the visitor's IP exceeded the owner-configured request threshold for some path within a time window, and the rule's action (block for N seconds, usually) kicked in. For visitors, it is self-resolving — wait out the window. For owners, recurring 1015 reports from legitimate users mean the rule's threshold, window, or scope needs tuning: counting static assets toward API limits, thresholds sized for single users but hit by offices behind one NAT IP, or overly long ban durations.

Common Causes

  • Genuinely rapid requests — Refresh storms, aggressive scripts/scrapers, or an API client without backoff exceeding the configured requests-per-window.
  • Shared IP aggregation — Offices, campuses, and CGNAT put many users behind one IP — their combined traffic trips per-IP thresholds that a single user never would.
  • Rules scoped too broadly — A limit meant for a login endpoint applied to paths that load dozens of subresources per page-view — every normal visit counts many times.
  • Client bugs — Retry loops without backoff, polling intervals in milliseconds instead of seconds, or SPA bugs re-firing requests.

How to Fix It

1. Visitors: wait out the window

Blocks are time-boxed (commonly 10 seconds to an hour, per the rule). Stop the requests, wait, retry gently. If you run a script, add rate limiting and exponential backoff on 429/1015.

2. API clients: honor limits proactively

Space requests and back off on rejection.

# simple client-side pacing:
for url in $(cat urls.txt); do
  curl -s "$url" -o /dev/null
  sleep 1   # stay under the site's threshold
done

3. Owners: check which rule fires and on what

Security → Events shows matched rate-limiting rules, paths, and source IPs. Verify the rule counts only what it should (exclude static assets; scope to the sensitive path).

# typical sane shapes:
#  login:  5 requests / 1 min / per IP  -> block 10 min
#  api:    100 requests / 1 min / per IP -> managed challenge
#  never:  sitewide low threshold counting all assets

4. Owners: key limits smarter than raw IP where possible

For APIs with auth, rate-limit by API key/session (Advanced Rate Limiting) so one office NAT does not consume everyone's budget; use challenge actions rather than long hard blocks for borderline traffic.

Frequently Asked Questions

How long does the 1015 block last?

Whatever the owner's rule says — the mitigation timeout is part of the rule (10 seconds to hours). There is no universal number; if it clears after a short wait, the rule is short. Persistent blocks across hours mean either a long timeout or you keep re-tripping it.

Is 1015 the same as HTTP 429?

Same idea — 'too many requests' — different layer. 429 is the standard status any server can send; 1015 is Cloudflare's rate-limiting error page (delivered with a 429 status under the hood). Client handling should be identical: back off and retry later.

Our whole office gets 1015 on a site we use — what should we tell them?

That you are many users behind one IP (give them the IP), that a per-IP threshold aggregates all of you, and roughly how many people share it. Owners can raise thresholds for your address, key limits by session, or switch the action to a challenge — the report is genuinely useful to them.
