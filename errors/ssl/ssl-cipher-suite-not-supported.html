SSL Cipher Suite Not Supported

Last updated: March 8, 2026

No common cipher suite between client and server

You might see this error as:

  • SSL cipher suite not supported
  • No shared cipher
  • No common cipher suite
  • Cipher suite mismatch
  • ssl_error_no_cypher_overlap

What Does This Error Mean?

SSL Cipher Suite Not Supported occurs when the TLS client and server cannot agree on a cipher suite during the handshake. The client sends a list of cipher suites it supports, and the server selects one from that list. If the server does not support any of the client's offered cipher suites, the handshake fails. This typically happens when one side supports only modern ciphers and the other only supports deprecated ones, or when restrictive security policies eliminate all overlapping cipher suites.

Common Causes

  • Server only supports deprecated ciphers — The server is configured with only older cipher suites (such as RC4, DES, or export-grade ciphers) that modern browsers have removed. Current browsers only support AEAD cipher suites like AES-GCM and ChaCha20-Poly1305.
  • Overly restrictive server cipher configuration — The server administrator configured a very narrow set of cipher suites that does not overlap with what the client supports. For example, allowing only TLS 1.3 cipher suites while the client only supports TLS 1.2.
  • Client is too old to support modern ciphers — An older client (legacy browser, embedded device, or old application) does not support modern cipher suites like ECDHE with AES-GCM, and the server has correctly disabled the older insecure ciphers.
  • Security appliance stripping cipher suites — A network security appliance or TLS inspection proxy is modifying the ClientHello and removing cipher suites from the client's list, resulting in no common ciphers with the server.

How to Fix It

1. Configure recommended cipher suites on the server

Use a modern cipher suite configuration that balances security and compatibility.

# Nginx — modern configuration
ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305';
ssl_prefer_server_ciphers on;

# Apache
SSLCipherSuite ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384
SSLHonorCipherOrder on

2. Check supported cipher suites

Test which cipher suites the server supports and compare with the client's capabilities.

# List server's supported ciphers
nmap --script ssl-enum-ciphers -p 443 example.com

# Test specific cipher
openssl s_client -connect example.com:443 -cipher ECDHE-RSA-AES128-GCM-SHA256

3. Update the client

If the client is outdated, update the browser, operating system, or application to a version that supports modern cipher suites. Ensure the TLS library (OpenSSL, NSS, etc.) is current.

4. Use Mozilla SSL Configuration Generator

Use Mozilla's SSL Configuration Generator (ssl-config.mozilla.org) to generate a recommended cipher configuration for your specific server software and desired compatibility level.

Frequently Asked Questions

What cipher suites should I support?

At minimum, support ECDHE key exchange with AES-128-GCM and AES-256-GCM cipher suites. Adding ChaCha20-Poly1305 provides a good alternative for clients without AES hardware acceleration. For TLS 1.3, the cipher suites are fixed and negotiated automatically.

Should I enable CBC cipher suites for compatibility?

CBC cipher suites (like AES-CBC with HMAC-SHA) are less secure than GCM due to padding oracle vulnerabilities. Enable them only if you need to support very old clients. Prefer GCM and ChaCha20 ciphers for all modern clients.

Does TLS 1.3 have cipher suite negotiation issues?

TLS 1.3 simplified cipher suite negotiation significantly. It only supports five cipher suites, all of which use AEAD encryption. Cipher suite mismatches are rare with TLS 1.3 — they are primarily a TLS 1.2 and older issue.
