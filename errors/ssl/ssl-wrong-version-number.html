SSL Wrong Version Number

Last updated: March 8, 2026

Unexpected SSL/TLS version number in the server response

You might see this error as:

  • SSL wrong version number
  • wrong version number SSL
  • SSL routines:ssl3_get_record:wrong version number
  • SSL23_GET_SERVER_HELLO:wrong version number

What Does This Error Mean?

SSL Wrong Version Number occurs when the client receives a response that does not conform to the expected TLS protocol format. This typically means the client is trying to establish a TLS connection but the server is responding with non-TLS data. The most common cause is connecting to a plain HTTP port with HTTPS, or connecting to a service that does not use TLS at all. The client interprets the first bytes of the non-TLS response as a version number, finds it invalid, and reports this error.

Common Causes

  • Connecting HTTPS to an HTTP-only port — The client is attempting a TLS handshake on a port that only serves plain HTTP. The server responds with an HTTP response, which the TLS client cannot parse as a valid TLS record.
  • Wrong port number — The connection is directed to a port running a non-TLS service (such as an SMTP server on port 25 or an HTTP server on port 8080) while the client expects TLS.
  • STARTTLS required but not used — The service requires a plain-text connection first, followed by a STARTTLS upgrade. The client is attempting direct TLS instead of the STARTTLS protocol upgrade sequence.
  • Load balancer or reverse proxy misconfiguration — A load balancer terminates TLS but forwards plain HTTP to a backend that the client is trying to reach with TLS, or the load balancer is forwarding raw TCP to a non-TLS backend.
  • Server TLS configuration is broken — The server's TLS configuration is invalid or the TLS library is corrupted, causing the server to respond with garbage data instead of a proper TLS ServerHello.

How to Fix It

1. Verify the correct port and protocol

Ensure you are connecting to the right port with the correct protocol. Common TLS ports differ from plain-text ports.

# Common port mappings
# HTTPS: 443 (TLS) vs HTTP: 80 (plain)
# SMTPS: 465 (TLS) vs SMTP: 25/587 (STARTTLS)
# IMAPS: 993 (TLS) vs IMAP: 143 (STARTTLS)
# POP3S: 995 (TLS) vs POP3: 110 (STARTTLS)

2. Test the connection with OpenSSL

Use OpenSSL to determine whether the port supports direct TLS or requires STARTTLS.

# Test direct TLS
openssl s_client -connect example.com:443

# Test STARTTLS for SMTP
openssl s_client -connect example.com:587 -starttls smtp

# Test STARTTLS for IMAP
openssl s_client -connect example.com:143 -starttls imap

3. Use STARTTLS when required

If the service requires STARTTLS, configure your client to use the plain-text port with STARTTLS upgrade instead of connecting with direct TLS on the secure port.

4. Check load balancer configuration

If using a load balancer, ensure TLS termination is configured correctly and that backend connections use the expected protocol (TLS or plain HTTP).

Frequently Asked Questions

What does 'wrong version number' actually mean?

When the TLS client reads the server's response, it expects the first byte to be a TLS content type (such as 0x16 for handshake) followed by a version number (such as 0x0301 for TLS 1.0). If the server sends plain HTTP, the client reads the 'H' from 'HTTP' as the content type and the following bytes as a version number, which does not match any valid TLS version.

Can this error occur with a valid TLS server?

Rarely. If the server's TLS library is severely broken or if a network device is corrupting the TLS records in transit, the version number in the TLS record layer may be garbled, causing this error even though the server intends to speak TLS.
