PostgreSQL Password Authentication Failed

Last updated: July 1, 2026

PostgreSQL error 28P01 — 'FATAL: password authentication failed for user'. The server rejected the supplied password for that role.

You might see this error as:

  • FATAL: password authentication failed for user
  • psql password authentication failed
  • 28P01
  • password authentication failed for user "postgres"
  • pg password auth failed scram

What Does This Error Mean?

PostgreSQL matched your connection to a pg_hba.conf rule that requires a password, and the password check failed. Beyond a simply wrong password, there are two PostgreSQL-specific traps: the role may have no password set at all (common for the default postgres role, which normally authenticates via OS 'peer' auth), and password hashes may be stored in md5 while the server now demands scram-sha-256 — a frequent aftermath of upgrading to PostgreSQL 14+, where scram became the default.

Common Causes

  • Wrong password (or wrong role/database) — The obvious case — including passwords from a stale .pgpass file or PGPASSWORD variable overriding what you type.
  • The role has no password set — The postgres superuser is often passwordless, intended for local peer authentication only. Any TCP connection asking for a password must fail until one is set.
  • md5 hash vs scram-sha-256 mismatch — Passwords hashed under md5 cannot satisfy a scram-sha-256 rule in pg_hba.conf. After upgrades that switch password_encryption, old passwords must be re-set to be re-hashed.
  • Connecting to a different cluster than you think — Multiple PostgreSQL versions installed side by side listen on 5432 and 5433. Your password may be perfectly valid — on the other cluster.

How to Fix It

1. Reset the password using local peer authentication

Peer auth (local Unix socket as the postgres OS user) works without any password and lets you set a new one.

sudo -u postgres psql
ALTER USER myuser WITH PASSWORD 'new-password';
-- for the superuser itself:
ALTER USER postgres WITH PASSWORD 'new-password';

2. Check which pg_hba.conf rule applies

Rules are evaluated top-down; the first match wins. Confirm the method (peer, md5, scram-sha-256) for your connection type, and reload after edits.

sudo -u postgres psql -c 'SHOW hba_file;'
sudo cat /etc/postgresql/16/main/pg_hba.conf | grep -v '^#'
-- after changes:
sudo systemctl reload postgresql

3. Fix md5/scram mismatches by re-setting passwords

Confirm how the password is stored, set the desired encryption, and re-run ALTER USER so the hash is regenerated in the new format.

SELECT rolname, substring(rolpassword,1,10) FROM pg_authid WHERE rolname='myuser';
-- 'md5...' vs 'SCRAM-SHA-256$...'
SET password_encryption = 'scram-sha-256';
ALTER USER myuser WITH PASSWORD 'same-or-new-password';

4. Rule out stale credentials sources and wrong ports

Check the environment and pgpass file, and confirm the port you reach is the cluster you administer.

echo $PGPASSWORD
cat ~/.pgpass
pg_lsclusters   # Debian/Ubuntu: list clusters and ports
psql -h 127.0.0.1 -p 5432 -U myuser -d postgres

Frequently Asked Questions

How is this different from 'Peer authentication failed'?

Peer authentication compares your OS username with the database role — no password involved. It fails when the names differ (fix: connect as the matching OS user or switch that rule to scram). Password authentication failed means a password rule matched and the password was wrong.

Why did authentication break after upgrading PostgreSQL?

Newer versions default password_encryption to scram-sha-256 and ship pg_hba.conf rules demanding scram. Roles whose passwords were stored as md5 hashes can no longer authenticate — re-set each affected password so it is stored as scram, or temporarily set the hba method to md5.

How do I use .pgpass correctly?

Create ~/.pgpass with lines of hostname:port:database:username:password, and chmod 600 the file — PostgreSQL ignores it with looser permissions. Wildcards (*) are allowed in any field.
