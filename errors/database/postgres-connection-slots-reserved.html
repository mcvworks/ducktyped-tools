PostgreSQL Remaining Connection Slots Are Reserved

Last updated: July 1, 2026

PostgreSQL error 53300 — 'FATAL: remaining connection slots are reserved for non-replication superuser connections'. The cluster hit max_connections.

You might see this error as:

  • remaining connection slots are reserved
  • FATAL: sorry, too many clients already
  • 53300 postgres
  • connection slots are reserved for non-replication superuser
  • postgres max_connections exceeded

What Does This Error Mean?

PostgreSQL keeps a fixed number of connection slots (max_connections, default 100) and reserves a few of them (superuser_reserved_connections, default 3) for superusers, so an admin can always get in. This error means ordinary connections have consumed everything except that reserve. The cause is rarely genuine demand — it is usually connection leakage: application pools sized too large across too many instances, sessions stuck 'idle in transaction', or serverless functions each opening their own connections.

Common Causes

  • Application connection pools oversubscribe the cluster — Ten app instances each with a pool of 20 is 200 connections against a default limit of 100. Autoscaling multiplies the problem exactly when load spikes.
  • Connections stuck 'idle in transaction' — Code that opens a transaction and stalls (waiting on an external call, or leaking connections without commit/rollback) holds slots indefinitely while doing nothing.
  • Serverless / per-request connections — Lambda-style functions and scripts that open a fresh connection per invocation, without an external pooler, exhaust slots almost immediately under concurrency.
  • max_connections simply too low for legitimate load — Less common — but real for monoliths with many workers. Raising the limit costs memory per slot, so it is a deliberate trade-off, not a free fix.

How to Fix It

1. See who is using the slots right now

Connect as a superuser (the reserve exists for exactly this) and inspect pg_stat_activity, grouped by state and application.

SELECT state, application_name, count(*)
FROM pg_stat_activity
GROUP BY 1, 2 ORDER BY 3 DESC;

-- terminate abandoned idle-in-transaction sessions:
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND state_change < now() - interval '10 minutes';

2. Put pgbouncer in front of the cluster

A transaction-mode pooler multiplexes thousands of client connections onto a few dozen server connections — the standard fix for many app instances or serverless clients.

# pgbouncer.ini (essentials)
[databases]
appdb = host=127.0.0.1 port=5432 dbname=appdb

[pgbouncer]
pool_mode = transaction
max_client_conn = 2000
default_pool_size = 20

3. Set idle_in_transaction_session_timeout

Make PostgreSQL kill sessions that sit in an open transaction too long, so leaks self-heal.

ALTER SYSTEM SET idle_in_transaction_session_timeout = '5min';
SELECT pg_reload_conf();

4. Right-size pools and, if needed, max_connections

Total pool sizes across all instances should stay under max_connections minus the reserve. If you raise max_connections, remember each slot costs server memory (work_mem multiplied under load).

SHOW max_connections;
ALTER SYSTEM SET max_connections = 200;   -- requires restart
-- sum of all app pools should be < 200 - superuser_reserved_connections

Frequently Asked Questions

Why not just set max_connections to 5000?

Each connection is a full backend process with memory overhead, and hundreds of active backends thrash CPU and lock contention. PostgreSQL performs best with a modest number of busy connections — a pooler in transaction mode gives you high client concurrency without that cost.

What do pgbouncer's pool modes mean?

Session mode ties one server connection to one client for its lifetime (safest, least sharing). Transaction mode lends a server connection only for each transaction (the usual choice; prepared statements and session state need care). Statement mode shares per statement (most aggressive, most restrictions).

Why can superusers still connect during the outage?

That is superuser_reserved_connections doing its job: a few slots only superusers may use, kept so an administrator can always get in to diagnose and kill sessions exactly when the pool is exhausted.
