Redis OOM Command Not Allowed

Last updated: July 1, 2026

The Redis error 'OOM command not allowed when used memory is greater than maxmemory' — the memory limit is reached and the eviction policy refuses to free space.

You might see this error as:

  • OOM command not allowed when used memory > 'maxmemory'
  • redis OOM
  • redis maxmemory reached
  • ReplyError: OOM command not allowed

What Does This Error Mean?

Redis enforces maxmemory strictly: when used memory reaches the limit and the eviction policy is noeviction (the default), every command that would allocate more memory is rejected with this OOM error, while reads keep working. Whether this is a misconfiguration depends on the workload — a cache should almost certainly evict old keys instead of erroring, while a queue or primary datastore must not silently drop data, so it errors by design and needs either more memory or less data.

Common Causes

  • maxmemory reached with policy noeviction — The default policy never removes keys automatically. Once the limit is hit, all writes fail until something is deleted or the limit is raised.
  • Keys without TTL accumulating forever — Cache-style data written without expirations never leaves. Sessions, rate-limit counters, and job results quietly grow until the ceiling is hit.
  • A few very large keys — Multi-hundred-megabyte hashes, lists, or sets (often unbounded queues or aggregation structures) consume the budget alone.
  • Memory fragmentation — used_memory_rss can substantially exceed logical used_memory after heavy churn; the allocator holds pages Redis cannot reuse, effectively shrinking headroom.

How to Fix It

1. Check current memory state and policy

Establish the numbers first: limit, usage, policy, fragmentation.

redis-cli INFO memory | grep -E 'used_memory_human|used_memory_peak_human|maxmemory_human|maxmemory_policy|mem_fragmentation_ratio'

2. Set an eviction policy appropriate to the workload

For caches, allkeys-lru (or allkeys-lfu) evicts the least-used keys automatically. volatile-* variants only evict keys that have TTLs.

redis-cli CONFIG SET maxmemory-policy allkeys-lru
# persist in redis.conf:
# maxmemory 2gb
# maxmemory-policy allkeys-lru

3. Find and fix the biggest keys

Locate what is actually eating memory, then cap, trim, or expire it.

redis-cli --bigkeys
redis-cli MEMORY USAGE some:large:key
# trim an unbounded list-queue:
redis-cli LTRIM jobs:done 0 9999

4. Add TTLs to cache-like data

Expire everything that can be regenerated, so steady-state memory is bounded.

SET session:abc123 '{...}' EX 86400
EXPIRE cache:user:42 3600
# audit keys without TTL (sample):
redis-cli --scan --pattern 'cache:*' | head -20 | xargs -I{} redis-cli TTL {}

5. Raise maxmemory or scale only after the above

If the working set is legitimately large, raise maxmemory within the host's RAM budget (leave room for fork-based saves), or shard/cluster the dataset.

Frequently Asked Questions

Which eviction policy should I use?

Pure cache: allkeys-lru (or allkeys-lfu on Redis 4+, which tracks frequency instead of recency). Mixed usage where some keys must never disappear: volatile-lru with TTLs on evictable keys only. Queues/primary data: keep noeviction and size memory properly — silent eviction of a queue is worse than an error.

Reads still work during OOM — why do some read commands fail too?

Commands are classified by whether they may increase memory. Some ostensibly read-like operations (SORT with STORE, commands that create temporary structures) allocate and are therefore rejected. Plain GET/HGET/LRANGE keep working.

What does a high mem_fragmentation_ratio mean?

used_memory_rss divided by used_memory. Around 1.0–1.5 is normal; well above that after heavy delete churn means the allocator holds unreturned pages. Redis 4+ can fix it live with activedefrag yes; otherwise a restart compacts memory.
