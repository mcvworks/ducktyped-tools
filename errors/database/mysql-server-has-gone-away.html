MySQL Server Has Gone Away

Last updated: July 1, 2026

MySQL error 2006 — the connection to the server was lost mid-use, typically because an idle connection timed out or a packet exceeded max_allowed_packet.

You might see this error as:

  • MySQL server has gone away
  • MySQL error 2006
  • ERROR 2006 (HY000)
  • Lost connection to MySQL server
  • OperationalError: (2006, ...)
  • PDOStatement MySQL server has gone away

What Does This Error Mean?

Error 2006 means the client tried to use a connection that the server no longer considers open. Two causes dominate: the server closed an idle connection after wait_timeout seconds (and the application later tried to reuse it), or the client sent a packet — a huge INSERT, a BLOB, a long dump statement — larger than max_allowed_packet, which makes the server cut the connection. Less often, the server actually restarted (crash, OOM kill, deploy) between queries.

Common Causes

  • Idle connection exceeded wait_timeout — MySQL closes connections idle longer than wait_timeout (default 28800s, but often lowered to minutes in production). Applications with long-lived pooled connections hit this after quiet periods.
  • Packet larger than max_allowed_packet — A single statement or row bigger than max_allowed_packet (often left at 16MB or 64MB) causes the server to drop the connection immediately — classic when inserting BLOBs or importing dumps.
  • The server restarted or was OOM-killed — If MySQL crashed or the kernel killed it under memory pressure, every existing connection dies. Check uptime — a suspiciously young server confirms it.
  • A proxy or load balancer cut the idle connection — ProxySQL, HAProxy, cloud NAT gateways, and managed-database proxies enforce their own idle timeouts, often shorter than MySQL's, silently killing connections in between.

How to Fix It

1. Raise max_allowed_packet for large statements

Set it on the server (and for mysqldump imports, on the client too). This is the fix when the error correlates with specific large writes.

-- check current value:
SHOW VARIABLES LIKE 'max_allowed_packet';

# /etc/mysql/my.cnf
[mysqld]
max_allowed_packet = 256M

# for imports:
mysql --max_allowed_packet=256M dbname < dump.sql

2. Validate pooled connections before use

Configure the connection pool to test or recycle connections older than the server's wait_timeout, so the app never picks up a dead one.

-- see server timeouts:
SHOW VARIABLES LIKE 'wait_timeout';

# examples:
# SQLAlchemy: create_engine(url, pool_pre_ping=True, pool_recycle=3600)
# HikariCP:  maxLifetime=1800000
# Node mysql2: pool { enableKeepAlive: true }

3. Check whether the server actually restarted

Rule out crashes: compare uptime with when errors started, and look for OOM kills or crash-recovery messages.

mysqladmin status          # shows uptime
sudo journalctl -u mysql -n 50
dmesg | grep -i 'killed process'

4. Align proxy idle timeouts with the pool

Make every hop's idle timeout longer than the application pool's recycle time, or enable TCP keepalives, so intermediaries stop cutting live connections.

Frequently Asked Questions

What is the difference between error 2006 and 2013 ('Lost connection during query')?

2006 (gone away) usually strikes when reusing a connection that was already dead — before or between queries. 2013 hits in the middle of a running query, pointing at query timeouts, network drops, or the server dying under that specific query's load.

Why does importing a SQL dump trigger this?

Dumps contain multi-row INSERT statements that can exceed max_allowed_packet. Note the client and server each enforce their own limit — raise it on both sides for the import.

Should I just set wait_timeout very high?

It reduces the symptom but keeps dead-connection risk (server restarts, network blips). The robust fix is pool-side: pre-ping or recycle connections, so the app always validates before use.
