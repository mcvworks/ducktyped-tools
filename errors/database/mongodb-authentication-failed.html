MongoDB Authentication Failed

Last updated: July 1, 2026

MongoDB error code 18 — 'Authentication failed' (Atlas reports 'bad auth'). The credentials, authentication database, or mechanism did not match.

You might see this error as:

  • MongoServerError: Authentication failed
  • MongoDB code 18
  • bad auth : authentication failed
  • MongoError: Authentication failed
  • pymongo.errors.OperationFailure: Authentication failed

What Does This Error Mean?

MongoDB rejected the login. Beyond a wrong password, MongoDB has a trap the other databases lack: users live in a specific database (their authentication database), and the client must authenticate against that database — the authSource. A user created in admin but authenticated against myapp fails with code 18 despite a perfect password. The second trap is the connection string: special characters in passwords must be URL-encoded, and an un-encoded @ or : silently breaks the URI parsing.

Common Causes

  • Wrong authSource — The user exists in a different database than the one being authenticated against. Users are typically created in admin; without authSource=admin in the URI, drivers default to the target database.
  • Special characters in the password not URL-encoded — Characters like @ : / ? # in a password confuse URI parsing — part of the password gets read as hostname or database, and authentication fails with correct-looking credentials.
  • Wrong username or password — Including case differences — MongoDB usernames are case-sensitive — and copy-paste whitespace.
  • SCRAM mechanism mismatch — Users created with only SCRAM-SHA-256 credentials cannot authenticate through clients forced to SCRAM-SHA-1 (and vice versa), which appears with older drivers or explicit authMechanism settings.

How to Fix It

1. Specify authSource in the connection string

Point authentication at the database where the user actually lives.

mongodb://appuser:secret@db-host:27017/myapp?authSource=admin
# mongosh equivalent:
mongosh -u appuser -p secret --authenticationDatabase admin db-host:27017/myapp

2. URL-encode the password

Percent-encode reserved characters before putting the password in a URI.

# p@ss:word/123  ->  p%40ss%3Aword%2F123
node -e "console.log(encodeURIComponent('p@ss:word/123'))"
mongodb+srv://appuser:p%40ss%3Aword%2F123@cluster0.mongodb.net/myapp

3. Verify the user exists where you think it does

List users per database and check their mechanisms and roles.

use admin
db.getUsers()
// check a specific user incl. mechanisms:
db.getUser('appuser', { showCredentials: false })

4. Recreate or update the user cleanly

When in doubt, reset the password or recreate the user with the needed roles and both SCRAM mechanisms (the default).

use admin
db.changeUserPassword('appuser', 'new-secret')
// or create:
db.createUser({ user: 'appuser', pwd: 'new-secret',
  roles: [{ role: 'readWrite', db: 'myapp' }] })

Frequently Asked Questions

What exactly is authSource?

The database MongoDB checks the credentials against. Every user belongs to one database (shown as the left part of 'db.user' identities). authSource tells the driver where to look — it is unrelated to which database you read and write after login; roles control that.

Why does Atlas say 'bad auth : authentication failed'?

It is the same code-18 failure surfaced by Atlas. Check that the database user (created under Database Access, not your Atlas login) is correct, that the password is URL-encoded in the URI, and that you kept authSource=admin (mongodb+srv URIs from Atlas include the right defaults — regenerating the connection string from the Atlas UI is the fastest fix).

Are Atlas login credentials the same as database users?

No — the Atlas web account and database users are completely separate. Applications authenticate with database users created in the Atlas 'Database Access' section; your Atlas email/password will always fail in a connection string.
