MySQL Incorrect String Value

Last updated: July 1, 2026

MySQL error 1366 — an INSERT or UPDATE contained bytes the column's character set cannot store, most famously emoji into a 'utf8' column.

You might see this error as:

  • Incorrect string value
  • MySQL error 1366
  • ERROR 1366 (HY000)
  • Incorrect string value: '\xF0\x9F...'
  • MySQL emoji error
  • utf8mb4 incorrect string value

What Does This Error Mean?

MySQL's historical 'utf8' charset (utf8mb3) stores at most 3 bytes per character — but emoji and many modern characters need 4 bytes in UTF-8. When such a character reaches a utf8mb3 or latin1 column, MySQL raises error 1366 and shows the offending bytes (\xF0\x9F... is the emoji signature). The complete fix has two halves: the column must be utf8mb4, and the connection charset must also be utf8mb4 — fixing only one leaves the error (or worse, silent '???' mojibake) in place.

Common Causes

  • Column uses utf8mb3 ('utf8') instead of utf8mb4 — Tables created before utf8mb4 became the default (MySQL 8.0) commonly use 3-byte utf8. Any 4-byte character — emoji, many CJK extension characters — fails.
  • Column uses latin1 or another single-byte charset — Legacy latin1 columns reject most non-Western text outright, not just emoji.
  • Connection charset differs from column charset — If the client connection declares latin1 or utf8mb3, MySQL converts incoming data through that charset first — corrupting or rejecting 4-byte characters even when the column itself is utf8mb4.
  • Mixed charsets after partial migrations — Databases converted table-by-table end up with some columns converted and some not; the error then appears 'randomly' depending on which table a write hits.

How to Fix It

1. Convert the affected table to utf8mb4

CONVERT TO changes the table default and re-encodes every string column. Do it in a maintenance window for large tables — it rebuilds the table.

ALTER TABLE messages CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
-- MariaDB / MySQL 5.7: use utf8mb4_unicode_ci

2. Set the connection charset to utf8mb4

Declare utf8mb4 in the client/connector so data reaches the server unmangled.

# connection URLs:
# JDBC:    ...?characterEncoding=UTF-8&connectionCollation=utf8mb4_0900_ai_ci
# Node:    mysql.createPool({ charset: 'utf8mb4' })
# Django:  'OPTIONS': {'charset': 'utf8mb4'}

-- verify on a live connection:
SHOW VARIABLES LIKE 'character_set%';

3. Find every non-utf8mb4 column first

Inventory the schema so the migration is complete rather than table-by-table whack-a-mole.

SELECT table_name, column_name, character_set_name
FROM information_schema.columns
WHERE table_schema = 'yourdb'
  AND character_set_name IS NOT NULL
  AND character_set_name <> 'utf8mb4';

4. Make utf8mb4 the server default

Prevent new tables from regressing.

# /etc/mysql/my.cnf
[mysqld]
character-set-server = utf8mb4
collation-server = utf8mb4_0900_ai_ci

Frequently Asked Questions

Why is MySQL's 'utf8' not real UTF-8?

For historical reasons, MySQL's utf8 (now aliased utf8mb3) caps characters at 3 bytes, covering only the Basic Multilingual Plane. Real UTF-8 needs up to 4 bytes. utf8mb4, added in MySQL 5.5, is the actual full UTF-8 — always use it.

Will converting to utf8mb4 break my indexes?

On modern MySQL (5.7+ with innodb_large_prefix default, and all of 8.0) index key limits are 3072 bytes and VARCHAR(255) indexes fit fine. Only very old setups (191-character limit era) need column-length adjustments.

Why do I get '???' instead of an error sometimes?

That is the connection charset silently converting characters it cannot represent instead of rejecting them — typically a latin1 connection. Strict SQL mode plus utf8mb4 end-to-end turns silent corruption into either correct storage or a visible error.
