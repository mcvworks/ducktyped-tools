Database Deadlock Detected

Last updated: March 8, 2026

Two or more transactions are waiting for each other's locks

You might see this error as:

  • Deadlock detected
  • Database deadlock
  • InnoDB deadlock
  • Deadlock found when trying to get lock
  • ERROR 1213 (40001): Deadlock

What Does This Error Mean?

A deadlock occurs when two or more transactions each hold locks that the other transactions need, creating a circular dependency where none can proceed. The database detects this cycle and forcibly rolls back one of the transactions (the 'victim') so the others can continue. The rolled-back transaction must be retried by the application.

Common Causes

  • Inconsistent lock ordering — Transactions acquire locks on resources in different orders. Transaction A locks row 1 then tries to lock row 2, while Transaction B locks row 2 then tries to lock row 1.
  • Long-running transactions with many locks — Transactions that hold locks for extended periods and touch many rows increase the probability of deadlocks with other concurrent transactions.
  • High concurrency on the same rows — Multiple transactions frequently updating the same rows or related rows with foreign key constraints, especially in high-traffic applications.

How to Fix It

1. Implement retry logic

When a transaction is rolled back due to a deadlock, catch the error and retry the transaction.

# Python/PostgreSQL example:
import psycopg2

max_retries = 3
for attempt in range(max_retries):
    try:
        cursor.execute("UPDATE accounts SET balance = balance - 100 WHERE id = 1")
        cursor.execute("UPDATE accounts SET balance = balance + 100 WHERE id = 2")
        conn.commit()
        break
    except psycopg2.extensions.TransactionRollbackError:
        conn.rollback()
        if attempt == max_retries - 1:
            raise

2. Use consistent lock ordering

Always access tables and rows in the same order across all transactions. If you need to update rows 1 and 2, always update the lower ID first.

-- Always lock in order of primary key:
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
-- Never reverse this order in other transactions

3. Reduce transaction scope and duration

Keep transactions as short as possible. Do non-database work (API calls, file I/O, calculations) outside the transaction.

-- Bad: long transaction
BEGIN;
SELECT ... FOR UPDATE;
-- expensive computation in application
UPDATE ...;
COMMIT;

-- Better: minimal transaction
-- do computation first, then:
BEGIN;
UPDATE ...;
COMMIT;

Frequently Asked Questions

How does the database choose which transaction to roll back?

The deadlock victim is chosen based on database-specific heuristics. PostgreSQL typically rolls back the transaction that would be cheapest to abort. MySQL/InnoDB rolls back the transaction that has modified the fewest rows. You should not rely on a specific selection policy.

Are deadlocks always a bug?

Not necessarily. Deadlocks can occur in any concurrent system and are not always avoidable. The important thing is that your application handles them gracefully with retry logic. However, frequent deadlocks indicate a design issue that should be addressed.

Can I prevent all deadlocks?

In theory, yes, by always acquiring locks in a consistent global order. In practice, this is difficult in complex applications. The pragmatic approach is to minimize deadlocks through consistent ordering and short transactions, and handle the remaining ones with retry logic.
