SQLite No Such Table

Last updated: July 1, 2026

The SQLite error 'no such table: name' — the table does not exist in the database file the connection actually opened, which is often not the file you intended.

You might see this error as:

  • no such table
  • sqlite3.OperationalError: no such table
  • SQLITE_ERROR: no such table
  • OperationalError: no such table
  • django.db.utils.OperationalError: no such table

What Does This Error Mean?

SQLite has a behavior that turns small path mistakes into confusing errors: opening a database file that does not exist silently creates a new, empty one. So 'no such table: users' very often means 'you are connected to a freshly created empty database at the wrong path' — not that your real data lost its table. The remaining cases are the ordinary ones: migrations never ran on this environment, or the table name differs from what the code expects.

Common Causes

  • Wrong or relative database path — A relative path like 'app.db' resolves against the process's current working directory. Started from a different directory (systemd, cron, IDE), the app opens — and creates — a different, empty file.
  • Migrations never ran — Fresh clones, new containers, and CI environments have the file (or get it auto-created) but nothing created the schema.
  • Table name mismatch — ORM naming conventions (pluralization, prefixes, case) generate a different name than raw SQL expects — 'users' vs 'user' vs 'app_users'.
  • Multiple database files drifting apart — Dev scripts write one file, the app reads another; backups or volume mounts shadow the real file with an older copy.

How to Fix It

1. Confirm which file the connection really opened

Ask the connection itself — this settles the wrong-path hypothesis in one query.

-- inside the connection:
PRAGMA database_list;
-- shows the absolute path of 'main'

# suspicious sign: a tiny/empty db file created recently
ls -la *.db && find . -name '*.db' -newermt '1 day ago'

2. List the tables that actually exist

Compare reality against expectation before touching migrations.

sqlite3 /full/path/app.db '.tables'
sqlite3 /full/path/app.db "SELECT name FROM sqlite_master WHERE type='table';"

3. Use absolute paths from configuration

Remove working-directory dependence so every entry point opens the same file.

# instead of: sqlite3.connect('app.db')
import os
DB_PATH = os.environ.get('DB_PATH', '/var/lib/myapp/app.db')
conn = sqlite3.connect(DB_PATH)

4. Run the migrations for this environment

If the file is correct but empty, create the schema the supported way.

# examples:
alembic upgrade head
python manage.py migrate
npx prisma migrate deploy
npx knex migrate:latest

Frequently Asked Questions

Why does SQLite create a database instead of erroring on a wrong path?

Historical default: opening implies create-if-missing (mode rwc). You can opt out with URI mode=rw — sqlite3.connect('file:app.db?mode=rw', uri=True) — which raises an error when the file does not exist, catching wrong paths immediately. Using it in production apps is a good defensive habit.

The table exists in the SQLite CLI but the app cannot see it — how?

Two different files. The CLI opened the path you typed; the app resolved its relative path from its own working directory. Run PRAGMA database_list in both and compare the absolute paths — they will differ.

Could the table have a different name than I think?

Yes — ORMs pluralize and prefix. Query sqlite_master for names LIKE the expected root ('%user%') and check your ORM's table-naming settings (Django's db_table, SQLAlchemy's __tablename__, Rails/Prisma conventions).
