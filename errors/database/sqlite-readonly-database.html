SQLite Attempt to Write a Readonly Database

Last updated: July 1, 2026

The SQLite error raised when a write is attempted but the database file — or, just as often, its directory — is not writable by the process.

You might see this error as:

  • attempt to write a readonly database
  • SQLITE_READONLY
  • OperationalError: attempt to write a readonly database
  • sqlite3.OperationalError readonly
  • SqliteError: attempt to write a readonly database

What Does This Error Mean?

SQLite needs more than write permission on the .db file: to commit a transaction it creates journal or WAL files next to the database, so the containing directory must be writable too — the detail behind most confusing cases of this error. It is most common in web deployments, where the app runs as a service user (www-data, nginx, apache) that does not own the database the developer created, and in containers where the database sits on a read-only layer or misconfigured volume.

Common Causes

  • The process user cannot write the file — The database belongs to the developer or root, while the application runs as a service account with only read access.
  • The directory is not writable — Even with a writable .db file, SQLite must create -journal or -wal/-shm files in the same directory. A read-only directory produces this exact error on the first write.
  • Read-only filesystem or mount — Container images (anything not on a volume is effectively fixed), ro-mounted volumes, full disks remounted read-only, and app bundles on mobile platforms all reject writes.
  • The connection was opened read-only — URI parameters like mode=ro or immutable=1, or a driver's read-only flag, force the error regardless of file permissions.

How to Fix It

1. Give the service user ownership of file AND directory

Fix both levels — the directory requirement is the one people miss.

sudo chown www-data:www-data /var/www/app/data /var/www/app/data/app.db
sudo chmod 775 /var/www/app/data
sudo chmod 664 /var/www/app/data/app.db
# verify as the service user:
sudo -u www-data sqlite3 /var/www/app/data/app.db 'CREATE TABLE t(x); DROP TABLE t;'

2. Check for read-only mounts

Confirm the filesystem allows writes at all.

mount | grep -E 'ro[,)]'
touch /var/www/app/data/.write-test && rm /var/www/app/data/.write-test

3. In Docker, put the database on a writable volume

Store the file on a volume or bind mount owned by the container's user, never on the image layer.

# docker-compose.yml
services:
  app:
    volumes:
      - ./data:/app/data
# ensure host dir ownership matches the container user (e.g. uid 1000):
sudo chown -R 1000:1000 ./data

4. Check how the connection is opened

Remove read-only flags if writes are intended.

# URI examples:
# read-only:  file:app.db?mode=ro
# read-write: file:app.db?mode=rwc
# python:
sqlite3.connect('file:/app/data/app.db?mode=rwc', uri=True)

Frequently Asked Questions

Why does SQLite need to write to the directory?

Atomic commits work through auxiliary files: rollback journals (app.db-journal) or, in WAL mode, app.db-wal and app.db-shm — created beside the database. Without directory write permission, SQLite cannot create them and the first write fails even though the .db file itself is writable.

How is this different from 'database is locked'?

'Readonly' is a permission/mount problem — writes are impossible for this process, always. 'Locked' is a concurrency problem — another connection holds a lock right now, and the write would succeed later. The fixes are completely different.

It worked in development but is readonly in production — why?

In development the app runs as you, the file's owner. In production it runs as a service user (www-data, a container UID) that lacks write permission on your files. Deploy scripts should chown the data directory to the runtime user.
