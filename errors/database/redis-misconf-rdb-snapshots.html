Redis MISCONF — Unable to Persist to Disk

Last updated: July 1, 2026

The Redis error 'MISCONF Redis is configured to save RDB snapshots, but it is currently not able to persist on disk' — writes are blocked until persistence recovers.

You might see this error as:

  • MISCONF Redis is configured to save RDB snapshots
  • not able to persist on disk
  • redis MISCONF
  • stop-writes-on-bgsave-error
  • redis bgsave failed

What Does This Error Mean?

By default Redis refuses all writes when its last background save (BGSAVE) failed, to make data loss loud instead of silent — that is the stop-writes-on-bgsave-error policy behind MISCONF. The save fails for environmental reasons: the disk is full, the configured dump directory is not writable by the redis user, or the fork() that background saving requires was denied memory by the kernel. Fix the save, and the error clears on the next successful BGSAVE.

Common Causes

  • Disk full — The volume holding the dump file (dir directive, default /var/lib/redis) has no space for a new dump.rdb — the most common cause by far.
  • Directory not writable by the redis user — After migrations, restores from backup, or manual chown, the data directory or existing dump.rdb belongs to root and the redis process cannot replace it.
  • fork() failed due to memory overcommit settings — BGSAVE forks the process; with vm.overcommit_memory=0 the kernel may refuse the fork when Redis uses a lot of memory, even though copy-on-write means the child needs far less than a full copy.
  • AOF rewrite failures with the same roots — If appendonly is enabled, AOF rewrite failures (same disk/permission/fork causes) can block writes the same way.

How to Fix It

1. Read the exact failure from Redis itself

INFO persistence shows the last save status and error; the log names the failing path.

redis-cli INFO persistence | grep -E 'rdb_last_bgsave_status|aof_last_write_status'
sudo tail -50 /var/log/redis/redis-server.log

2. Free disk space or move the dump directory

Check the volume, clear space, or point dir at a volume with room, then trigger a save to confirm.

df -h $(redis-cli CONFIG GET dir | tail -1)
redis-cli CONFIG SET dir /data/redis   # writable volume
redis-cli BGSAVE
redis-cli INFO persistence | grep rdb_last_bgsave_status

3. Fix ownership and permissions

The redis user must own the data directory and be able to replace the dump file.

sudo chown -R redis:redis /var/lib/redis
sudo chmod 750 /var/lib/redis
redis-cli BGSAVE

4. Set vm.overcommit_memory = 1

Allow the kernel to permit the BGSAVE fork under copy-on-write; Redis itself warns about this at startup.

sudo sysctl vm.overcommit_memory=1
# persist:
echo 'vm.overcommit_memory = 1' | sudo tee /etc/sysctl.d/99-redis.conf

5. Only as a stopgap: allow writes despite failed saves

This unblocks the application but disables the safety check — data written now is lost if Redis restarts before a save succeeds. Re-enable after fixing persistence.

redis-cli CONFIG SET stop-writes-on-bgsave-error no
# ...fix disk/permissions/fork...
redis-cli CONFIG SET stop-writes-on-bgsave-error yes

Frequently Asked Questions

Why does a background save block writes at all?

It is a deliberate alarm: if saves fail silently, you discover data loss only after a crash. Blocking writes makes the operational problem impossible to ignore. Cache-only deployments that can tolerate loss may reasonably disable the behavior — persistent-data deployments should not.

Why does fork need so much memory?

It usually does not — Linux forks with copy-on-write, so the child shares pages with the parent. But with vm.overcommit_memory=0 the kernel conservatively assumes a full copy might be needed and can refuse the fork for a large Redis. Setting overcommit to 1 tells the kernel to allow it.

Where does Redis write its dump file?

The 'dir' directive holds the directory and 'dbfilename' the file (default dump.rdb). Check both live with CONFIG GET dir and CONFIG GET dbfilename — the log messages about failed saves refer to that path.
