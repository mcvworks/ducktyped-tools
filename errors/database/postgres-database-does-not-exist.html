PostgreSQL Database Does Not Exist

Last updated: July 1, 2026

PostgreSQL error 3D000 — 'FATAL: database "name" does not exist'. The cluster you reached has no database by that name.

You might see this error as:

  • FATAL: database does not exist
  • database "mydb" does not exist
  • psql: error: FATAL: database
  • 3D000 postgres

What Does This Error Mean?

Authentication succeeded — then PostgreSQL looked for the requested database on the cluster and found nothing. Like the role error, the most common trigger is a default: psql (and many client libraries) default the database name to the username, so 'psql -U alice' looks for a database called alice. The other frequent case is connecting to a different cluster than intended: after a version upgrade or on a machine with several instances, port 5432 may belong to a fresh, empty cluster while your data lives on 5433.

Common Causes

  • The database name defaulted to the username — psql with no -d connects to a database named after the role. 'FATAL: database "alice" does not exist' means exactly that — no database was ever named alice.
  • The database was never created — New environments where migrations create tables but nothing created the database itself; the app's configured name simply is not there.
  • Connected to the wrong cluster — Multiple installed versions each run their own cluster on different ports. After upgrades (especially Homebrew's), the default port can point at a new empty cluster.
  • The database was dropped or renamed — Cleanup scripts, environment resets, or a rename leave clients configured with the old name.

How to Fix It

1. List what actually exists on the cluster

Connect to the always-present postgres maintenance database and list databases.

psql -U postgres -d postgres -c '\l'
# or:
psql -U postgres -lqt | cut -d'|' -f1

2. Create the missing database

Create it owned by the application role.

createdb -U postgres -O appuser appdb
-- or in SQL:
CREATE DATABASE appdb OWNER appuser;

3. Check you are on the right cluster/port

Compare running clusters and their ports; connect explicitly to each until you find your data.

pg_lsclusters              # Debian/Ubuntu
brew services list          # macOS
psql -p 5433 -U postgres -l # try the other port

4. Specify the database explicitly everywhere

Avoid the default-to-username behavior in scripts and CI by always passing -d (or the database in the connection URL).

psql -U appuser -d appdb
# URL form:
postgres://appuser:pass@localhost:5432/appdb

Frequently Asked Questions

Why does psql look for a database named after me?

Convention: psql defaults the database to the connecting role's name. It made sense on classic setups where every user had a personal database. Use -d, PGDATABASE, or a full connection URL to be explicit.

My databases vanished after a brew upgrade — are they gone?

Almost certainly not. Major-version upgrades create a fresh data directory; your old data still sits in the previous version's directory. Run 'brew postgresql-upgrade-database' or start the old version and dump/restore into the new cluster.

Can I connect without naming any database?

No — every PostgreSQL connection attaches to exactly one database. For administration, connect to the built-in 'postgres' database. (template1 also exists, but avoid using it as a habitat: objects created there get copied into every future database.)
