MySQL Lock Wait Timeout Exceeded

Last updated: July 1, 2026

MySQL error 1205 — a transaction waited longer than innodb_lock_wait_timeout for row locks held by another transaction and gave up.

You might see this error as:

  • Lock wait timeout exceeded; try restarting transaction
  • MySQL error 1205
  • ERROR 1205 (HY000)
  • innodb lock wait timeout
  • SQLSTATE[HY000]: General error: 1205

What Does This Error Mean?

InnoDB locks rows that a transaction writes (and rows it reads with SELECT ... FOR UPDATE). If another transaction needs those rows, it waits — up to innodb_lock_wait_timeout seconds (default 50) — then fails with error 1205. Unlike a deadlock (error 1213), which InnoDB detects and resolves instantly, a lock wait timeout means someone was simply holding locks for a long time: an uncommitted transaction, a huge UPDATE, or a session that crashed without rolling back.

Common Causes

  • An uncommitted transaction is holding locks — Code that opens a transaction and never commits (missing COMMIT, an exception path that skips cleanup, a developer's forgotten console session) holds its row locks until the connection dies.
  • Long-running write transactions — A bulk UPDATE or DELETE touching millions of rows holds locks on all of them for the duration. Everything needing those rows queues behind it.
  • Missing indexes widen the lock footprint — An UPDATE whose WHERE clause has no usable index locks far more rows than it modifies (InnoDB locks the rows it scans), turning a small change into a table-wide blockade.
  • Metadata locks from DDL — ALTER TABLE waits for open transactions to finish, and while it waits, every new query on that table queues behind the ALTER — a pileup that surfaces as lock timeouts.

How to Fix It

1. Find and kill the blocking transaction

Identify which transaction holds the locks and how long it has been running, then kill its connection if it is abandoned.

-- MySQL 8+: who blocks whom
SELECT waiting.trx_mysql_thread_id AS waiting_thread,
       blocking.trx_mysql_thread_id AS blocking_thread,
       blocking.trx_started, blocking.trx_query
FROM performance_schema.data_lock_waits w
JOIN information_schema.innodb_trx waiting ON waiting.trx_id = w.REQUESTING_ENGINE_TRANSACTION_ID
JOIN information_schema.innodb_trx blocking ON blocking.trx_id = w.BLOCKING_ENGINE_TRANSACTION_ID;

KILL <blocking_thread>;

2. Keep transactions short

Commit as soon as the logical unit of work is done, never hold a transaction across user interaction or external API calls, and batch big writes into chunks (e.g. 10k rows per transaction).

3. Index the columns used to select rows for writes

Ensure UPDATE/DELETE WHERE clauses hit an index so InnoDB locks only the target rows.

EXPLAIN UPDATE orders SET status='x' WHERE customer_id=42;
-- 'type: ALL' means full scan -> add an index:
ALTER TABLE orders ADD INDEX idx_customer (customer_id);

4. Tune the timeout only as a mitigation

Raising innodb_lock_wait_timeout makes waiters more patient; lowering it fails fast. Neither fixes the blocker — use it alongside, not instead of, the fixes above.

SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';
SET SESSION innodb_lock_wait_timeout = 120;   -- per-session

Frequently Asked Questions

How is this different from a deadlock (error 1213)?

A deadlock is two transactions each waiting for the other — InnoDB detects the cycle instantly and rolls one back. Error 1205 is one-directional waiting that simply exceeded the timeout. Deadlocks need lock-ordering fixes; 1205 needs the long lock-holder found and shortened.

Does 'try restarting transaction' mean a retry will work?

Only if the blocking transaction finished in the meantime. Retrying against the same stuck blocker fails identically. Automatic retries are still good practice — but pair them with monitoring for long-running transactions.

How do I see transactions idle with open locks?

Query information_schema.innodb_trx and compare trx_started with now — transactions running for minutes with trx_query NULL are idle-but-open and are usually the culprits. In MySQL 8 you can also check performance_schema.events_transactions_current.
