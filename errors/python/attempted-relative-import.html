Python ImportError: Attempted Relative Import

Last updated: July 2, 2026

The crash 'ImportError: attempted relative import with no known parent package' — relative imports only work inside a package, and this file was run as a plain script.

You might see this error as:

  • ImportError: attempted relative import with no known parent package
  • attempted relative import beyond top-level package
  • ValueError: attempted relative import
  • python relative import error

What Does This Error Mean?

Relative imports ('from . import utils') resolve against the importing module's package — the dotted path Python knows it by. When you execute a file directly ('python src/app/main.py'), that file runs as the top-level script named __main__ with no package, so '.' points nowhere and Python raises this error. The code is often fine; the invocation is what strips the package context. Running the module through its package ('python -m app.main') restores it.

Common Causes

  • Running a package module as a script — 'python app/main.py' executes the file without its package identity. The same file works when imported by something else — the asymmetry that makes this error confusing.
  • Relative imports in a genuinely top-level script — A standalone script (not part of any package) using 'from . import x' — there is no parent package for '.' to mean, ever.
  • Missing package structure — No __init__.py (in setups not using namespace packages) or a directory layout that does not match the dotted paths used in imports.
  • Tests importing across an src/ layout — pytest collecting tests that relatively import application code without the package being installed or the rootdir configured.

How to Fix It

1. Run the module via -m from the project root

This gives the file its package identity so relative imports resolve.

# layout:
#   project/
#     app/__init__.py
#     app/main.py     (uses: from . import utils)
cd project
python -m app.main

2. Or switch to absolute imports

Absolute imports work under both invocation styles and are the default recommendation in most style guides.

# instead of:  from . import utils
from app import utils
# instead of:  from ..core import db
from app.core import db

3. Install the package in editable mode for tests and tools

With src/ layouts, an editable install makes the package importable from anywhere — pytest, scripts, notebooks.

# pyproject.toml present:
pip install -e .
pytest

4. Give scripts a proper entry point

Rather than executing files inside the package, define a console script so users run a command, not a path.

# pyproject.toml
[project.scripts]
myapp = "app.main:main"
# then: pip install -e .  ->  myapp

Frequently Asked Questions

Why does the same file work when imported but crash when run?

Imported, the module is known as 'app.main' — '.' means 'app'. Run directly, it is '__main__' with no package attribute, so relative dots have no anchor. Same file, two identities; 'python -m app.main' runs it under the imported identity.

Do I still need __init__.py files?

For regular packages, yes — they mark the directory as a package and are where Python looks for package context (namespace packages exist but behave differently with tooling). An empty __init__.py is enough; missing ones are a frequent cause of import weirdness in tests.

Should I just append to sys.path?

sys.path hacks work until they don't — they break under different working directories and confuse tools. The maintainable options are: -m invocation, absolute imports, or an editable install. Reserve sys.path manipulation for quick throwaway scripts.
