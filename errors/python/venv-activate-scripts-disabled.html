venv Activate: Running Scripts Is Disabled on This System

Last updated: July 2, 2026

The PowerShell failure 'Activate.ps1 cannot be loaded because running scripts is disabled on this system' — Windows' execution policy blocks the venv activation script.

You might see this error as:

  • Activate.ps1 cannot be loaded because running scripts is disabled on this system
  • running scripts is disabled on this system
  • Set-ExecutionPolicy RemoteSigned
  • venv activate powershell error
  • UnauthorizedAccess execution policy

What Does This Error Mean?

PowerShell's execution policy defaults to Restricted on Windows client systems: no scripts run, period — including the harmless Activate.ps1 that Python's venv module generated on your own machine. The error is PowerShell policy, nothing to do with Python itself. The standard, Microsoft-recommended developer setting is RemoteSigned scoped to your user: locally-created scripts (like venv activators) run, scripts downloaded from the internet need a signature.

Common Causes

  • Default Restricted execution policy — Fresh Windows installs block all PowerShell scripts. The first venv a developer activates hits it immediately.
  • Corporate policy lockdown — Some managed machines enforce AllSigned or Restricted via Group Policy — user-level changes are then overridden or forbidden.
  • Running the wrong activator for the shell — Each shell has its own script: Activate.ps1 (PowerShell), activate.bat (cmd), activate (bash). Sourcing the wrong one produces different but related confusion.

How to Fix It

1. Set RemoteSigned for your user

The standard developer fix — no admin rights required, scoped to you, keeps protection against unsigned downloads.

Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
# then:
.\.venv\Scripts\Activate.ps1

2. Or bypass for the current session only

Zero persistent change — useful on locked-down machines.

powershell -ExecutionPolicy Bypass
.\.venv\Scripts\Activate.ps1

3. Or sidestep PowerShell

cmd's activator is a .bat (not policy-controlled), and you can run tools without activating at all by calling the venv's executables directly.

:: cmd.exe:
.venv\Scripts\activate.bat

:: no activation needed at all:
.venv\Scripts\python.exe app.py
.venv\Scripts\pip.exe install requests

4. Check what policy applies and from where

On managed machines, see whether Group Policy pins it before fighting it.

Get-ExecutionPolicy -List
# MachinePolicy/UserPolicy set (not Undefined) -> IT-managed; ask IT or use the bypass/cmd routes

Frequently Asked Questions

Is RemoteSigned safe?

It is Microsoft's recommended setting for developers: local scripts run, internet-downloaded scripts must be signed (files carry a zone marker Windows checks). It protects against the realistic threat (running a downloaded script by accident) without breaking local development.

Why does activation work in cmd but not PowerShell?

cmd batch files are not governed by PowerShell's execution policy — only .ps1 files are. That is also the practical workaround on machines where policy cannot be changed: use activate.bat, or skip activation and call .venv\Scripts\python.exe directly.

Do I even need to activate the venv?

Activation just edits PATH and the prompt for convenience. Everything works by absolute path: .venv\Scripts\python.exe, .venv\Scripts\pip.exe. CI scripts and IDE configurations usually use the direct paths precisely to avoid shell-specific activation.
