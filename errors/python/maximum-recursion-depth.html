Python RecursionError: Maximum Recursion Depth Exceeded

Last updated: July 2, 2026

The crash 'RecursionError: maximum recursion depth exceeded' — function calls nested past Python's limit (default 1000), almost always runaway recursion.

You might see this error as:

  • RecursionError: maximum recursion depth exceeded
  • maximum recursion depth exceeded while calling a Python object
  • maximum recursion depth exceeded in comparison
  • sys.setrecursionlimit

What Does This Error Mean?

Python caps the interpreter call stack at sys.getrecursionlimit() frames — 1000 by default — and raises RecursionError beyond it. Like its JavaScript cousin, this is a logic bug far more often than a limit problem: a base case that some input never reaches, __getattr__ or properties that read themselves, __repr__/__eq__ recursing through cyclic objects, or deep recursion over data that should be iterative. The traceback's repeating block names the loop.

Common Causes

  • Base case never reached — Termination depends on a condition an input never satisfies (empty string vs None, negative numbers, off-by-one) — the function descends forever.
  • Dunder-method self-reference — __getattr__ that touches an attribute triggering __getattr__ again, a property whose getter reads the property, or __init__ calling the class — Python-specific loops that surprise even experienced developers.
  • Recursive dunder traversal of cyclic objects — __repr__, __eq__, or serialization walking children on structures with cycles.
  • Legitimately deep recursion — Tree algorithms on deep data, recursive descent parsers on big inputs — correct logic that simply exceeds 1000 frames.

How to Fix It

1. Read the repeating frames and log the arguments

The pattern in the traceback is the diagnosis; seeing the arguments shows why termination fails.

def walk(node, _depth=0):
    assert _depth < 500, f'runaway at {node!r}'   # temporary tripwire
    ...

2. Fix __getattr__ loops with direct dict access

Inside __getattr__ (and __setattr__), bypass normal attribute lookup for internal state.

class Config:
    def __init__(self):
        object.__setattr__(self, '_data', {})
    def __getattr__(self, name):
        try:
            return self._data[name]      # _data found normally -> no loop
        except KeyError:
            raise AttributeError(name) from None

3. Rewrite deep recursion iteratively

An explicit stack removes the depth limit entirely — the robust fix for tree/graph walkers.

def walk_iter(root):
    stack = [root]
    while stack:
        node = stack.pop()
        visit(node)
        stack.extend(node.children)

4. Raise the limit only for known-finite depth

For a correct algorithm slightly over the default on trusted input — never as a fix for infinite loops (you trade a clean exception for a hard crash when the real C stack dies).

import sys
sys.setrecursionlimit(5000)   # measured, bounded need only

Frequently Asked Questions

Why is Python's limit only 1000?

Each Python frame is relatively heavy, and the interpreter guards the underlying C stack: recursing too deep there segfaults the process instead of raising a catchable error. 1000 is a safety margin — algorithms needing much more are usually better iterative, and Python (by design) has no tail-call optimization.

The error mentions 'while calling a Python object' or pickle/repr — what is that?

The recursion is inside a protocol: comparing, representing, or serializing objects that reference each other cyclically. Implement the dunder to handle cycles (track visited ids), or break the cycle in the data model.

Can I catch RecursionError?

Yes — it is a normal exception, and catching it at a boundary to fail one request instead of the process is legitimate. But treat the catch as containment; the loop itself still needs the real fix.
