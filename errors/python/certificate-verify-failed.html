Python SSLCertVerificationError — Certificate Verify Failed

Last updated: July 2, 2026

The failure 'ssl.SSLCertVerificationError: [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: unable to get local issuer certificate' in requests, urllib, or pip.

You might see this error as:

  • ssl.SSLCertVerificationError
  • CERTIFICATE_VERIFY_FAILED
  • certificate verify failed: unable to get local issuer certificate
  • requests.exceptions.SSLError
  • urllib certificate verify failed

What Does This Error Mean?

Python could not validate the TLS certificate chain of the server it connected to. Two environments dominate: macOS python.org installs, which ship without linking to any CA store until you run the bundled 'Install Certificates.command' (the single most famous cause), and corporate networks, where a TLS-intercepting proxy re-signs traffic with a company CA that Python's trust bundle has never heard of. As with Node's equivalent error, the correct fix is teaching Python the right CA — disabling verification hands the connection to whoever is in the middle.

Common Causes

  • macOS python.org install without certificates linked — The installer does not wire the certifi bundle in; every HTTPS request from that interpreter fails until the Install Certificates command runs.
  • Corporate TLS interception — Zscaler/Netskope-style proxies re-encrypt with the company CA. Browsers trust it via the OS store; Python (using certifi's Mozilla bundle) does not.
  • Server with an incomplete chain or expired certificate — If only one site fails from every network, the server likely serves no intermediate certificate (or an expired one) — a server-side problem.
  • Stale certifi or frozen environments — Very old certifi bundles miss newer roots; frozen apps (PyInstaller) can ship without the bundle path resolving.

How to Fix It

1. macOS: run Install Certificates.command

One double-click (or shell line) links the interpreter to certifi's CA bundle.

/Applications/Python\ 3.12/Install\ Certificates.command
# or equivalently:
python3 -m pip install --upgrade certifi

2. Corporate networks: point Python at the company CA

Export the proxy's root CA (from IT or the OS keychain) as PEM and set the bundle env vars — requests, pip, and most libraries honor them.

export REQUESTS_CA_BUNDLE=/etc/ssl/certs/corp-root-ca.pem
export SSL_CERT_FILE=/etc/ssl/certs/corp-root-ca.pem
# pip permanently:
pip config set global.cert /etc/ssl/certs/corp-root-ca.pem

3. Check whether the server is at fault

Test the chain independently; a missing intermediate reproduces from any network and needs fixing server-side.

openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | grep -E 'verify|depth'
# or use an online SSL checker for a second opinion

4. Never ship verify=False

requests.get(url, verify=False) silences the error by trusting anyone — including an attacker. Acceptable for a one-off local experiment; a bug anywhere else. Audit for it before deploys.

grep -rn 'verify=False\|CERT_NONE' --include='*.py' .

Frequently Asked Questions

Why does the same URL work in my browser and in curl but not Python?

Each uses a different trust store: browsers and OS-integrated curl use the system store (where corporate CAs get installed by IT); Python uses certifi's Mozilla-derived bundle. Add the missing CA to the bundle Python reads (REQUESTS_CA_BUNDLE / SSL_CERT_FILE), and the difference disappears.

Where does Python actually look for CA certificates?

python3 -c "import ssl; print(ssl.get_default_verify_paths())" shows the interpreter's default paths; requests uses certifi's bundle (python3 -c "import certifi; print(certifi.where())"). The two can differ — one reason urllib and requests sometimes disagree about the same server.

How is this related to pip's TLS errors?

pip verifies PyPI's certificate the same way; on intercepted networks it fails identically. The pip config 'global.cert' (or --cert) points it at the corporate CA. Never use --trusted-host as a permanent fix — it disables verification for that host entirely.
