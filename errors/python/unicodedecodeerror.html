Python UnicodeDecodeError

Last updated: July 2, 2026

The crash "UnicodeDecodeError: 'utf-8' codec can't decode byte 0x.. in position .." — bytes were decoded with the wrong encoding, or binary data was opened as text.

You might see this error as:

  • UnicodeDecodeError: 'utf-8' codec can't decode byte
  • unicodedecodeerror invalid continuation byte
  • utf-8 codec cant decode byte 0xe9
  • 'charmap' codec can't decode byte
  • python encoding error reading file

What Does This Error Mean?

Text on disk is bytes plus an encoding; decoding with the wrong one crashes at the first byte sequence that is invalid in the assumed encoding. The error names the codec used, the offending byte, and its position — enough to diagnose. Three families: the file is genuinely in another encoding (Latin-1/cp1252 exports from Windows tools are the classic), the platform default was wrong (older Python on Windows defaults to cp1252, not UTF-8), or the 'file' is not text at all (opening a PNG, zip, or pickle in text mode).

Common Causes

  • The file is not UTF-8 — CSV/TXT exports from Excel, legacy systems, and many European-language datasets are cp1252 or latin-1. Byte 0xE9 ('é' in latin-1) at some position is the signature.
  • Relying on the platform default encoding — open() without encoding= uses a locale-dependent default (cp1252 on much of Windows before Python 3.15's UTF-8 default). The same script then behaves differently per machine.
  • Binary data opened in text mode — Images, archives, pickles, or gzip content read with open(path) instead of open(path, 'rb') — typically failing at position 0 with byte 0x89, 0x50, or similar.
  • Mixed or corrupted encodings — Files concatenated from different sources, or double-encoded data — no single codec decodes them cleanly.

How to Fix It

1. Identify the real encoding first

Ask the file before guessing.

file -i data.csv          # quick heuristic (Linux/macOS)
pip install charset-normalizer
python3 -m charset_normalizer data.csv

2. Open with the correct encoding — explicitly, always

Make encoding a visible decision at every open().

with open('export.csv', encoding='cp1252') as f:
    rows = f.read()

# pandas:
df = pd.read_csv('export.csv', encoding='cp1252')

3. Choose an errors= strategy for dirty data

When bytes are genuinely mixed/corrupt, decide explicitly how to degrade: replace marks problems visibly, ignore drops them silently.

with open('messy.log', encoding='utf-8', errors='replace') as f:
    text = f.read()    # bad bytes become \ufffd
# 'ignore' silently deletes — use only when loss is acceptable

4. Use binary mode for binary data

If position 0 fails, it was never text.

with open('image.png', 'rb') as f:
    data = f.read()

Frequently Asked Questions

How do I read what the error is telling me?

"'utf-8' codec can't decode byte 0xe9 in position 2893" says: decoding assumed UTF-8, byte 0xE9 at offset 2893 is invalid in it. 0xE9 is 'é' in latin-1/cp1252 — a strong hint the file is one of those. Position 0 with a weird byte suggests binary data; a large position in a big file suggests one bad record or a late encoding switch.

Why does the script work on Linux but crash on Windows?

open() without encoding= historically follows the locale: UTF-8 on Linux/macOS, cp1252 on most Windows. The same UTF-8 file then decodes fine on one and crashes on the other. Passing encoding='utf-8' everywhere (or running Python in UTF-8 mode with -X utf8) removes the platform dependence.

What about UnicodeEncodeError — the mirror image?

That is writing: text containing characters the target encoding cannot represent (e.g. printing emoji to a cp1252 console). Fixes mirror too — write with encoding='utf-8', or set PYTHONIOENCODING=utf-8 for console output on legacy Windows terminals.
