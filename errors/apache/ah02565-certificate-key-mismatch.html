Apache AH02565 — Certificate and Private Key Do Not Match

Last updated: July 2, 2026

The startup failure 'AH02565: Certificate and private key ... from ... and ... do not match' — SSLCertificateFile and SSLCertificateKeyFile are not a pair.

You might see this error as:

  • AH02565: Certificate and private key
  • certificate and private key do not match
  • ah02565
  • apache ssl key mismatch

What Does This Error Mean?

mod_ssl checks at startup that the public key inside SSLCertificateFile matches the private key in SSLCertificateKeyFile. AH02565 means they are from different keypairs — the vhost fails to start (or the whole server, depending on config). It happens when a certificate is renewed or reissued with a new key while the config still points at the old one, when cert and key from different issuances get copied together, or when two vhosts' file sets get crossed during an edit.

Common Causes

  • Renewal replaced the key but not the cert (or vice versa) — A new CSR generates a new private key; installing the new certificate while keeping the old key path (or copying only one of the two files to the server) guarantees a mismatch.
  • Files from different issuances mixed — Multiple example.com.crt/key files accumulate over the years; the config ends up pointing at a cert from 2025 and a key from 2023.
  • Wrong file entirely — Pointing SSLCertificateFile at the chain/intermediate bundle instead of the leaf-containing file, or at another domain's certificate after a copy-paste between vhosts.
  • Let's Encrypt paths not used consistently — Mixing a copied archive file with a live/ symlink means renewals update one and not the other, breaking the pair at the next renewal.

How to Fix It

1. Prove the mismatch and find the right pair

Compare public-key hashes: cert vs key. Then test other candidate files until the hashes match.

openssl x509 -noout -pubkey -in /etc/ssl/certs/example.com.crt | openssl sha256
openssl pkey  -noout -pubkey -in /etc/ssl/private/example.com.key | openssl sha256
# identical output = matching pair

2. Point both directives at the matching pair

Update the vhost and reload; with Let's Encrypt, always use the live/ symlinks.

<VirtualHost *:443>
    SSLEngine on
    SSLCertificateFile    /etc/letsencrypt/live/example.com/fullchain.pem
    SSLCertificateKeyFile /etc/letsencrypt/live/example.com/privkey.pem
</VirtualHost>
sudo apachectl configtest && sudo systemctl reload apache2

3. Reissue if the matching key is lost

Certificates are replaceable; generate a fresh key + CSR (or run certbot again) and install the new pair.

sudo certbot certonly --apache -d example.com -d www.example.com
# or manual CSR:
openssl req -new -newkey rsa:2048 -nodes -keyout new.key -out new.csr

4. Verify the served certificate afterwards

Confirm from outside that the right certificate is live.

echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -subject -dates

Frequently Asked Questions

Which openssl commands identify what a mystery file is?

'openssl x509 -noout -subject -dates -in file' works if it is a certificate; 'openssl pkey -noout -text -in file | head' if it is a private key; 'openssl crl2pkcs7 -nocrl -certfile file | openssl pkcs7 -print_certs -noout' lists every cert in a bundle. Sorting a directory of mystery PEMs takes minutes with these three.

Where does the chain go in Apache?

Since Apache 2.4.8, SSLCertificateFile accepts the full chain (leaf first, then intermediates) — the same fullchain.pem Let's Encrypt produces. The old SSLCertificateChainFile directive is deprecated; using fullchain in one file is the current practice.

Can I renew without changing the private key?

Yes — reuse the existing key by generating the CSR from it (certbot: --reuse-key). Some teams prefer key rotation each renewal for hygiene; either way, the installed cert and key must come from the same issuance flow.
