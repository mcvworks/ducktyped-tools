Apache AH01630 — Client Denied by Server Configuration

Last updated: July 2, 2026

The error-log line 'AH01630: client denied by server configuration' — an authorization rule (usually Require directives) rejected the request. Visitors see 403 Forbidden.

You might see this error as:

  • AH01630: client denied by server configuration
  • ah01630
  • AH01797
  • client denied by server configuration apache 403
  • require all granted

What Does This Error Mean?

Apache's authorization layer (mod_authz_core) evaluated the Directory/Location rules for the requested path and denied access — the client gets a 403, the log gets AH01630 with the path that was blocked. The single biggest source is the Apache 2.2 → 2.4 migration: the old 'Order allow,deny / Allow from all' syntax was replaced by 'Require' directives, and configs carried forward without conversion deny everything. The second biggest: the docroot lives outside the directories granted in the default config.

Common Causes

  • Apache 2.2 syntax on a 2.4 server — 'Order allow,deny' and 'Allow from all' do nothing useful under 2.4's authz_core (with mod_access_compat absent they can error; with it, subtle mismatches deny). Configs from old tutorials are the classic source.
  • No Require rule grants the directory — Apache 2.4 denies the whole filesystem by default ('Require all denied' on the root Directory block in the stock config). A vhost pointing at /srv/myapp without its own Directory grant inherits the deny.
  • Intentional IP restrictions matching more than intended — 'Require ip 10.0.0.0/8' style rules deny everyone else — surprising when a proxy/load balancer changes the client IP Apache sees.
  • Blocked hidden or sensitive paths — FilesMatch/Directory rules protecting .git, .env, or .ht* fire correctly — the log line names the actual file, revealing crawlers probing those paths.

How to Fix It

1. Read which path and rule denied

The log line includes the filesystem path; match it against your Directory blocks.

sudo tail -20 /var/log/apache2/error.log | grep AH01630
sudo apache2ctl -t -D DUMP_INCLUDES   # what config files are in play

2. Grant the docroot with 2.4 syntax

Add a Directory block using Require for the vhost's document root.

<Directory /srv/myapp/public>
    Options FollowSymLinks
    AllowOverride All
    Require all granted
</Directory>
sudo apachectl configtest && sudo systemctl reload apache2

3. Convert 2.2 access rules to 2.4

Replace Order/Allow/Deny with the Require equivalents everywhere.

# 2.2                         ->  2.4
# Order allow,deny            ->  (remove)
# Allow from all              ->  Require all granted
# Deny from all               ->  Require all denied
# Allow from 192.168.1        ->  Require ip 192.168.1
grep -rn 'Order allow\|Allow from\|Deny from' /etc/apache2/

4. Account for proxies in IP-based rules

Behind a load balancer, Apache sees the proxy's IP. Use mod_remoteip so Require ip evaluates the real client address.

# a2enmod remoteip, then:
RemoteIPHeader X-Forwarded-For
RemoteIPTrustedProxy 10.0.0.0/8

Frequently Asked Questions

How is AH01630 different from a file-permission 403?

AH01630 is Apache's own rules saying no — filesystem permissions never enter into it. Permission problems log different lines (AH00035 'search permissions missing', or Permission denied). Read the error log rather than guessing from the browser's 403 page: same status, three different fixes.

What is AH01797?

The same denial logged by a different authz path ('client denied by server configuration' from authz_core when no Require matched at all). Treat AH01630 and AH01797 identically: find the path, add or fix the Require rules.

Is 'Require all granted' on the docroot safe?

For the public document root, yes — that is exactly what it is for. Keep the deny-by-default on the root Directory block and grant only the specific trees you serve, and keep the .ht*/.git/.env protections in place.
