Apache AH00161 — MaxRequestWorkers Reached

Last updated: July 2, 2026

The warning 'AH00161: server reached MaxRequestWorkers setting, consider raising the MaxRequestWorkers setting' — Apache is out of workers and queueing or refusing requests.

You might see this error as:

  • AH00161: server reached MaxRequestWorkers setting
  • ah00161
  • consider raising the MaxRequestWorkers setting
  • apache maxrequestworkers

What Does This Error Mean?

Apache caps concurrent request handling at MaxRequestWorkers (256 by default with mpm_event; per-process with prefork). When every worker is busy, new connections queue in the listen backlog, users experience hangs and timeouts, and Apache logs AH00161 once per restart period. The right response is not blindly raising the number: workers cost memory (dramatically so with prefork+mod_php), and the limit often gets hit because requests are slow (backend waits) rather than traffic being high. Raise it with memory math, and fix what made workers slow.

Common Causes

  • Legitimate traffic growth — More concurrent users than 256 workers can serve — the setting simply reflects yesterday's capacity planning.
  • Slow requests pinning workers — Each request holds a worker for its full duration. A slow database or an external API taking seconds turns modest traffic into worker exhaustion — the queue explodes during the incident.
  • Keep-alive hogging with prefork — With mpm_prefork, an idle keep-alive connection occupies an entire process. High KeepAliveTimeout plus prefork wastes most of the pool on idle clients (mpm_event exists to solve exactly this).
  • Slowloris-style abuse — Clients deliberately holding connections open trickle-feed headers to pin workers — visible as many workers in 'reading request' state from unfamiliar IPs.

How to Fix It

1. See what the workers are doing

The server-status scoreboard shows busy/idle workers and each one's state — slow backends and slowloris patterns are visible at a glance.

# enable once: a2enmod status  (restrict access!)
curl -s localhost/server-status?auto | grep -E 'BusyWorkers|IdleWorkers|Scoreboard'

2. Raise MaxRequestWorkers with memory math

Budget = available RAM for Apache ÷ average per-process RSS. Exceeding that trades 503s for swapping, which is worse.

# average Apache process memory:
ps -ylC apache2 --sort:rss | awk '{sum+=$8; n++} END {print sum/n/1024 " MB avg"}'

# /etc/apache2/mods-available/mpm_event.conf
<IfModule mpm_event_module>
    ServerLimit              16
    ThreadsPerChild          25
    MaxRequestWorkers       400   # must be <= ServerLimit*ThreadsPerChild
</IfModule>
sudo systemctl restart apache2

3. Switch prefork+mod_php to event+PHP-FPM

The single biggest capacity win on legacy stacks: mpm_event handles keep-alive without dedicating workers, and PHP runs in its own pool.

sudo a2dismod php8.3 mpm_prefork
sudo a2enmod mpm_event proxy_fcgi
sudo a2enconf php8.3-fpm
sudo systemctl restart apache2 php8.3-fpm

4. Shorten what pins workers

Cut KeepAliveTimeout to 2-5s, add timeouts to backend/API calls, and use mod_reqtimeout (default on) against slow-request abuse.

Frequently Asked Questions

What do users experience when the limit is hit?

New connections wait in the TCP backlog — pages hang, then either load late or time out. Apache does not send a clean 503 for this by default, which is why it looks like 'the site is randomly slow' rather than an error.

MaxRequestWorkers vs ServerLimit vs ThreadsPerChild?

With mpm_event/worker: total concurrency = processes × threads. ThreadsPerChild is threads per process, ServerLimit caps processes, and MaxRequestWorkers (≤ ServerLimit × ThreadsPerChild) is the effective total. With prefork there are no threads: MaxRequestWorkers = max processes.

How high can I safely go?

Divide the RAM you can give Apache by the per-process footprint you measured, keep 20-30% headroom, and remember the backend (database, PHP-FPM) must also handle that concurrency. If you need thousands of concurrent connections, put nginx or a CDN in front for static/keep-alive traffic.
