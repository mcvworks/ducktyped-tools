Apache Threaded MPM vs PHP Module Conflict

Last updated: July 2, 2026

The error 'Apache is running a threaded MPM, but your PHP Module is not compiled to be threadsafe. You need to recompile PHP.' — mod_php demands the prefork MPM.

You might see this error as:

  • Apache is running a threaded MPM, but your PHP Module is not compiled to be threadsafe
  • You need to recompile PHP
  • mpm_event php module conflict
  • apache php threadsafe

What Does This Error Mean?

Classic mod_php embeds the PHP interpreter inside every Apache process and is not thread-safe, so it refuses to load under the threaded mpm_event or mpm_worker. The error appears when enabling the PHP module on a modern Apache (where event is the default MPM) — a2enmod phpX.Y even warns and switches MPMs for you, which is how servers silently end up on prefork. You have two coherent setups: prefork + mod_php (old, simple, memory-hungry) or event + PHP-FPM (modern, faster, the recommended path). The error means your server is currently neither.

Common Causes

  • Enabling mod_php while mpm_event is active — Fresh Apache installs default to mpm_event; adding libapache2-mod-php and enabling it triggers the conflict directly.
  • Switching MPM back to event on a mod_php server — Performance tuning that enables mpm_event without migrating PHP to FPM re-creates the conflict on the next configtest.
  • Half-migrated configurations — Both the phpX.Y module and FPM conf enabled, or two PHP versions' modules present — the enabled mod_php is what forces the MPM constraint.

How to Fix It

1. Recommended: switch to PHP-FPM with mpm_event

Drop mod_php entirely; Apache proxies PHP to the FPM pool. Better concurrency, per-pool tuning, opcache preserved across Apache reloads.

sudo a2dismod php8.3
sudo a2dismod mpm_prefork
sudo a2enmod mpm_event proxy_fcgi setenvif
sudo apt install php8.3-fpm
sudo a2enconf php8.3-fpm
sudo systemctl restart php8.3-fpm apache2
php -v && curl -s localhost/info.php | head -3   # verify

2. Alternative: stay on mod_php with prefork

If migrating is not an option today, use the pairing mod_php supports.

sudo a2dismod mpm_event mpm_worker
sudo a2enmod mpm_prefork php8.3
sudo systemctl restart apache2

3. Check which MPM and PHP integration are active

Useful before and after — confirms you are in one coherent setup.

apachectl -M | grep -E 'mpm|php|proxy_fcgi'
apache2ctl -V | grep -i mpm

Frequently Asked Questions

Why is mod_php not thread-safe?

PHP itself can be built thread-safe (ZTS), but many popular extensions are not, and distro packages ship non-ZTS PHP for performance. Under a threaded MPM, multiple threads would run PHP concurrently inside one process — unsafe with non-ZTS builds, so the module refuses to load.

Is PHP-FPM actually faster than mod_php?

For most workloads, yes in aggregate: mpm_event handles keep-alive and static files without dedicating a fat PHP-laden process to each connection, FPM pools are tuned independently, and memory usage drops substantially. mod_php's only remaining advantage is setup simplicity.

How do .htaccess php_value settings migrate to FPM?

php_value/php_flag in .htaccess only work under mod_php. With FPM, set them in the pool config (php_admin_value[...]), in php.ini, or per-directory via .user.ini files — that is the piece most migrations forget.
