Apache AH01071 — Got Error 'Primary Script Unknown' (PHP-FPM)

Last updated: July 2, 2026

The error-log line 'AH01071: Got error \'Primary script unknown\'' — Apache proxied a request to PHP-FPM, which could not find the script. Browsers show 'File not found.'

You might see this error as:

  • AH01071: Got error 'Primary script unknown'
  • ah01071
  • apache php-fpm file not found
  • primary script unknown apache

What Does This Error Mean?

With the modern Apache+PHP setup (mod_proxy_fcgi to PHP-FPM), Apache translates the request into a filesystem path and asks PHP-FPM to execute it. AH01071 wraps PHP-FPM's answer: no such script from where PHP-FPM stands. As with the nginx twin of this error, the mismatch is almost always in path translation — the SetHandler/ProxyPassMatch expression builds a path that is wrong, or PHP-FPM sees a different filesystem (chroot, container) than Apache does.

Common Causes

  • ProxyPassMatch built the wrong path — Old-style ProxyPassMatch rules embed the docroot literally; after a docroot change or on a second vhost, the hardcoded path no longer matches reality.
  • PHP-FPM sees a different filesystem — PHP-FPM in a container or chroot does not share Apache's paths — the path Apache sends does not exist inside PHP-FPM's world.
  • The script genuinely missing — Deploy didn't copy index.php, or the request hits a path where no PHP file exists and the handler still forwarded it.
  • Pool user cannot read the script — PHP-FPM's pool user lacks read permission on the file or traverse permission on its directories — reported identically to absence.

How to Fix It

1. Prefer SetHandler over ProxyPassMatch

SetHandler forwards the request with Apache's own path resolution — no hardcoded docroot to go stale, works across vhosts.

<FilesMatch \.php$>
    SetHandler "proxy:unix:/run/php/php8.3-fpm.sock|fcgi://localhost"
</FilesMatch>
# TCP variant:
# SetHandler "proxy:fcgi://127.0.0.1:9000"
sudo apachectl configtest && sudo systemctl reload apache2

2. Verify the file exists as PHP-FPM sees it

Check from the PHP-FPM side — its container, chroot, or pool user.

# same host:
sudo -u www-data ls -la /var/www/site/public/index.php
# php-fpm container:
docker compose exec php ls -la /var/www/site/public/index.php

3. Align paths across containers

Mount the code at the identical path in both containers so the translated path is valid in both worlds.

# docker-compose.yml
services:
  apache:
    volumes: ['./src:/var/www/html']
  php:
    volumes: ['./src:/var/www/html']

4. Watch the request PHP-FPM receives

Turn on the PHP-FPM access log briefly to see the script path arriving — the mismatch becomes obvious.

; pool config
access.log = /var/log/php-fpm/access.log
access.format = "%R - %u %t \"%m %r\" %s script=%f"
sudo systemctl restart php8.3-fpm

Frequently Asked Questions

The browser shows a plain 'File not found.' — same thing?

Yes — that text is PHP-FPM's stderr for an unknown primary script, passed through Apache with a 404. AH01071 in Apache's error log is the server-side twin of that message.

Why is SetHandler recommended over ProxyPassMatch?

ProxyPassMatch bypasses Apache's normal filesystem mapping and forces you to encode the docroot in the pattern — a second copy of the truth that rots. SetHandler runs after normal URL→file translation, so whatever docroot the vhost uses is automatically correct, per vhost, including aliases.

Does this differ from nginx's 'Primary script unknown'?

Same PHP-FPM message, different translation layer: nginx builds SCRIPT_FILENAME from fastcgi_param; Apache from the handler/proxy config. The diagnosis is shared (does the file exist where PHP-FPM looks?), the fix lives in each server's own config.
