Apache AH00526 — Syntax Error in Configuration

Last updated: July 2, 2026

The configtest/startup failure 'AH00526: Syntax error on line N of file' — Apache cannot parse the configuration and refuses to start or reload until it is fixed.

You might see this error as:

  • AH00526: Syntax error on line
  • ah00526
  • apachectl configtest syntax error
  • apache syntax error won't start

What Does This Error Mean?

AH00526 is Apache's parse-failure header: it names the file and line where reading the configuration stopped, followed by a second line describing the actual problem — an unclosed VirtualHost block, a file referenced by Include or SSLCertificateFile that does not exist, an invalid argument, or a directive that needs a missing module. The named line is where parsing failed, which for unclosed blocks can be the end of the file rather than where the mistake began.

Common Causes

  • Unclosed or mismatched block directives — A VirtualHost, Directory, or IfModule block without its closing tag — the reported line is often the file's end, the real error higher up.
  • Referenced file missing — SSLCertificateFile, Include/IncludeOptional targets, or an ErrorLog directory that does not exist — the second message line says which path failed.
  • Invalid arguments to a directive — Wrong number of arguments, a typo in an option name, or quotes broken across lines.
  • Directive requiring an unloaded module — Overlaps 'Invalid command' territory: SSLEngine without mod_ssl, ProxyPass without mod_proxy — enabling the module resolves it.

How to Fix It

1. Always run configtest and read BOTH lines

The AH00526 line locates, the following line explains. Fix, re-test, repeat until Syntax OK.

sudo apachectl configtest
# AH00526: Syntax error on line 34 of /etc/apache2/sites-enabled/example.conf:
# SSLCertificateFile: file '/etc/ssl/certs/missing.pem' does not exist or is empty

2. Hunt unclosed blocks when the line number is unhelpful

Count opening and closing tags per file; mismatched counts point at the broken block type.

f=/etc/apache2/sites-enabled/example.conf
for t in VirtualHost Directory IfModule Location FilesMatch; do
  printf '%s open=%s close=%s\n' $t $(grep -ci "<$t" $f) $(grep -ci "</$t>" $f)
done

3. Check which files are actually included

See the full include tree to find where a broken file enters the config.

sudo apache2ctl -t -D DUMP_INCLUDES

4. Reload, never restart, after edits

A failed reload leaves the old config serving; a failed restart leaves nothing running. Combine with configtest in one command so bad configs never even attempt.

sudo apachectl configtest && sudo systemctl reload apache2

Frequently Asked Questions

Apache is down and won't start — same workflow?

Yes: configtest first, since a config error is the most common reason a previously working Apache refuses to start after edits. If configtest passes and it still fails, move to 'journalctl -xeu apache2' — the failure is then ports (AH00072), certificates (AH02565), or resources (AH00023), each with their own guide.

The error names line 34 but line 34 looks fine — why?

Parsing failed at line 34; the mistake may be earlier — typically an unclosed quote or block that made everything after it part of the previous construct. Scan upward from the named line, or use the tag-count trick to find mismatched blocks.

Can I validate a config change without touching the running server?

configtest itself does not disturb the running server — it parses the on-disk config and reports. That is why the 'configtest && reload' idiom is safe to script: reload only fires when parsing succeeded.
