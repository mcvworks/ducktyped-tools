Apache AH00035 — Search Permissions Missing on a Component of the Path

Last updated: July 2, 2026

The error-log line 'AH00035: access to / denied ... because search permissions are missing on a component of the path' — the Apache user cannot traverse a directory above the docroot.

You might see this error as:

  • AH00035: access to / denied
  • search permissions are missing on a component of the path
  • ah00035
  • apache permission denied docroot

What Does This Error Mean?

To open /home/deploy/site/index.html, the Apache worker (www-data or apache) needs execute (traverse) permission on /home, /home/deploy, and /home/deploy/site — every directory on the way, not just the file. AH00035 means one of those parents lacks the execute bit for Apache's user. The textbook case is a docroot inside a home directory: modern distros create /home/user with 750, so www-data cannot pass through it no matter how permissive the docroot itself is.

Common Causes

  • Docroot under a 700/750 home directory — /home/deploy is rwx------ or rwxr-x---; www-data is neither owner nor group member, so traversal stops there.
  • A parent directory lost its execute bit — A recursive chmod with 644 (files-style mode applied to directories) strips the x bit; everything below becomes unreachable for everyone but root.
  • Deployment created paths with a restrictive umask — CI or rsync running with umask 077 creates directories as 700 owned by the deploy user — fine for the deployer, invisible to Apache.
  • SELinux context, not classic permissions — On RHEL-family with enforcing SELinux, a docroot outside the standard locations needs the httpd_sys_content_t context; without it the denial can surface alongside permission errors.

How to Fix It

1. Walk the path and find the blocking directory

namei prints the permission of every component in one shot — the culprit is instantly visible.

namei -l /home/deploy/site/public/index.html
# look for a directory row without 'x' for other/group

2. Add traverse permission to the parents

Execute-only (no read) on parents is enough for traversal and keeps listings private.

sudo chmod o+x /home/deploy
# or group-based, cleaner:
sudo chgrp www-data /home/deploy && sudo chmod g+x /home/deploy

3. Fix directories mangled by a recursive chmod

Restore x on directories only, leaving files at 644.

sudo find /srv/site -type d -exec chmod 755 {} +
sudo find /srv/site -type f -exec chmod 644 {} +

4. Label the docroot for SELinux if applicable

On enforcing systems with a non-standard docroot location.

sudo semanage fcontext -a -t httpd_sys_content_t '/srv/site(/.*)?'
sudo restorecon -Rv /srv/site

Frequently Asked Questions

What is a 'search permission' on a directory?

The execute (x) bit on directories means permission to traverse — to reach things inside by name. Read (r) on a directory only lists names. Apache needs x on every ancestor of the served file; it does not need r on them.

Is moving the site out of /home the better fix?

Often yes. /srv or /var/www are conventional, avoid fighting home-directory privacy defaults, and keep web content separate from user data. If the site must stay under /home, the group + g+x approach is the tidiest.

Why does everything work as root but not via Apache?

Root bypasses permission checks entirely, so testing as root proves nothing about the worker user. Test as Apache's user: 'sudo -u www-data cat /path/to/file' reproduces exactly what the server experiences.
