Apache Invalid Command 'RewriteEngine'

Last updated: July 2, 2026

The error "Invalid command 'RewriteEngine', perhaps misspelled or defined by a module not included in the server configuration" — mod_rewrite (or another module) is not enabled.

You might see this error as:

  • Invalid command 'RewriteEngine'
  • perhaps misspelled or defined by a module not included in the server configuration
  • a2enmod rewrite
  • apache invalid command htaccess

What Does This Error Mean?

Apache parsed a directive that no loaded module defines. RewriteEngine is the most famous case — WordPress and framework .htaccess files use mod_rewrite, which Debian-family installs ship disabled — but the same error fires for Header (mod_headers), ExpiresActive (mod_expires), ProxyPass (mod_proxy), and any directive whose module is missing. Where it appears matters: in the main config it blocks startup; in an .htaccess file it turns every request to that directory into a 500 Internal Server Error.

Common Causes

  • The module is not enabled — mod_rewrite, mod_headers, mod_expires, and mod_proxy are all opt-in on Debian/Ubuntu. Config copied from a working server fails on a host where the module was never enabled.
  • Directive arrived via .htaccess — An application's shipped .htaccess assumes modules the server lacks — every hit to the directory 500s, and the error log shows the Invalid command line with the .htaccess path.
  • Genuine misspelling — RewriteEngin, ProxyPas — the message's 'perhaps misspelled' branch. The quoted token in the error is exactly what Apache read.
  • Directive from a third-party module that is not installed — Directives from mod_security, mod_pagespeed, or mod_wsgi require installing the package, not just a2enmod.

How to Fix It

1. Enable the module that defines the directive

On Debian-family, a2enmod; the directive-to-module mapping is in the Apache docs header of each directive.

sudo a2enmod rewrite headers expires
sudo apachectl configtest
sudo systemctl restart apache2

2. On RHEL-family, check the LoadModule line

Modules load via LoadModule in conf.modules.d; most ship enabled, but verify.

grep -rn 'mod_rewrite' /etc/httpd/conf.modules.d/
# ensure uncommented:
# LoadModule rewrite_module modules/mod_rewrite.so
sudo apachectl configtest && sudo systemctl restart httpd

3. Confirm which modules are loaded

List live modules to verify the fix took.

apachectl -M | grep -E 'rewrite|headers|expires'

4. Guard optional directives in shared configs

Configs that must work with or without a module can wrap directives in IfModule so absence degrades instead of erroring.

<IfModule mod_headers.c>
    Header set X-Frame-Options "SAMEORIGIN"
</IfModule>

Frequently Asked Questions

Why does my site 500 on every page after deploying the app's .htaccess?

The .htaccess is parsed on each request; an Invalid command in it aborts request processing with a 500. Check the error log for the Invalid command line naming the file, then enable the missing module — for typical app .htaccess files that means mod_rewrite.

RewriteEngine works but rules are ignored — related?

Different problem: the module is loaded but .htaccess processing is off. AllowOverride None (the default since 2.4) makes Apache skip .htaccess entirely. Set 'AllowOverride All' (or the specific override classes) in the Directory block for the docroot.

Should rewrite rules live in .htaccess or the vhost?

If you control the server config, the vhost: it is parsed once at startup instead of on every request, and it cannot be broken by an app deploy. .htaccess exists for shared hosting where users cannot touch the vhost.
