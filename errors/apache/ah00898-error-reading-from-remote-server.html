Apache AH00898 — Error Reading from Remote Server (mod_proxy)

Last updated: July 2, 2026

The error-log line 'AH00898: Error reading from remote server' (with AH01102 'error reading status line') — Apache's reverse proxy lost the backend mid-request. Visitors see 502.

You might see this error as:

  • AH00898: Error reading from remote server
  • AH01102: error reading status line from remote server
  • ah00898
  • ah01102
  • apache proxy 502 error reading

What Does This Error Mean?

Apache (acting as reverse proxy via ProxyPass) connected to the backend, sent the request, and then the response never arrived properly — the connection died, timed out, or returned garbage where a status line should be. The client gets a 502 Bad Gateway. The two log lines travel together: AH01102 is the low-level read failure on the status line, AH00898 the request-level consequence. Behind them is a backend that crashed mid-request, took longer than ProxyTimeout, or closed a kept-alive connection just as Apache reused it.

Common Causes

  • Backend exceeded the proxy timeout — ProxyTimeout (default = Timeout, 60s) fires while the backend is still working — slow queries and long report endpoints are the usual content.
  • Backend crashed or restarted mid-request — The worker handling the request died (app crash, OOM kill, deploy restart) and the socket closed with no response.
  • Keep-alive reuse race — Apache reuses pooled backend connections; if the backend's idle timeout is shorter, it closes the socket just as Apache sends the next request — intermittent one-off 502s under low traffic are the signature.
  • Response not valid HTTP — Pointing ProxyPass at a non-HTTP port (a database, an AJP port without the ajp:// scheme) yields bytes that fail status-line parsing.

How to Fix It

1. Correlate with backend logs first

The timestamps in Apache's error log tell you where to look in the app's logs — crash, restart, or slow request will be visible there.

sudo grep -E 'AH00898|AH01102' /var/log/apache2/error.log | tail -5
# then check the app around those times:
journalctl -u myapp --since '10 minutes ago'

2. Raise the proxy timeout for genuinely slow endpoints

Scope it to the slow location rather than globally.

<Location /reports/>
    ProxyPass http://127.0.0.1:3000/reports/ timeout=300
    ProxyPassReverse http://127.0.0.1:3000/reports/
</Location>
sudo apachectl configtest && sudo systemctl reload apache2

3. Defuse the keep-alive race

Make Apache's pooled connections expire before the backend's idle timeout, or disable reuse for a problematic backend.

# backend closes idle conns at 5s? keep Apache's below it:
ProxyPass http://127.0.0.1:3000/ ttl=4
# or bypass pooling entirely (small perf cost, kills the race):
SetEnv proxy-nokeepalive 1

4. Confirm the backend speaks HTTP on that port

A quick manual request distinguishes protocol mismatch from instability.

curl -v http://127.0.0.1:3000/ 2>&1 | head -15
# garbage or immediate close -> wrong port/protocol in ProxyPass

Frequently Asked Questions

Is AH00898 the same as a 502 Bad Gateway?

It is the main Apache-side reason for one. The visitor sees 502; AH00898/AH01102 in the error log explain that the proxy read failed. If you see 502s without these lines, another layer (CDN, second proxy) produced them.

Why do I get exactly one 502 every few minutes, then it works on refresh?

Classic keep-alive race: an idle pooled connection was closed by the backend, Apache's first reuse attempt fails, the retry on a fresh connection succeeds. Set the ttl= on ProxyPass below the backend's idle timeout and the pattern disappears.

ProxyTimeout vs Timeout — which applies?

ProxyTimeout (or the timeout= key on ProxyPass) governs waiting on the backend and defaults to the global Timeout value. The per-ProxyPass key wins over ProxyTimeout, which wins over Timeout — use the narrowest scope that fits.
