Apache AH00023 — No Space Left on Device (Mutex/Semaphore)

Last updated: July 2, 2026

The startup failure 'No space left on device: AH00023: Couldn't create the mpm-accept mutex' — usually exhausted semaphores, not an actually full disk.

You might see this error as:

  • No space left on device: AH00023: Couldn't create the mpm-accept mutex
  • ah00023
  • apache mutex semaphore
  • apache no space left on device

What Does This Error Mean?

Misleading by design: 'no space left on device' here usually refers to kernel IPC resources, not the filesystem. Apache creates System V semaphores for its internal mutexes; repeated crashes or kill -9 restarts leak them, and once the kernel's semaphore limit fills, the next start fails with AH00023. The same message can occasionally be literal — a full disk or exhausted inodes preventing lock/log file creation — so check both, in that order of likelihood when disks look fine.

Common Causes

  • Leaked System V semaphores — Every unclean Apache death (segfault, OOM kill, kill -9) can orphan its semaphore sets. They accumulate invisibly until semmni/semmns limits are hit.
  • Kernel semaphore limits too low for the workload — Hosts running many Apache instances (or other IPC-heavy software like PostgreSQL and Oracle) can exhaust default limits without any leak.
  • Actually out of disk or inodes — The literal reading: no room for pid files, lock files, or logs. Rare for this specific AH code, quick to rule out.

How to Fix It

1. Rule out the literal disk case

Two commands settle it.

df -h /var /tmp
df -i /var   # inodes

2. List and clean leaked semaphores

Remove semaphore sets owned by the Apache user while Apache is stopped, then start.

sudo systemctl stop apache2
ipcs -s | grep -E 'www-data|apache'
# remove them all for that user:
for id in $(ipcs -s | awk '/www-data|apache/ {print $2}'); do sudo ipcrm -s $id; done
sudo systemctl start apache2

3. Raise kernel semaphore limits if legitimately needed

The four sem values are SEMMSL SEMMNS SEMOPM SEMMNI; raise MNS/MNI for many concurrent semaphore sets.

cat /proc/sys/kernel/sem
echo 'kernel.sem = 250 32000 100 1024' | sudo tee /etc/sysctl.d/99-sem.conf
sudo sysctl -p /etc/sysctl.d/99-sem.conf

4. Fix the crash loop that leaks them

Leaked semaphores are a symptom: find why Apache keeps dying uncleanly (segfaulting module, OOM) in the error log and journal, or the leak returns.

sudo journalctl -u apache2 | grep -iE 'segfault|killed|oom' | tail
sudo dmesg | grep -i apache | tail

Frequently Asked Questions

Why does Linux call semaphore exhaustion 'no space left on device'?

The semget() syscall reuses ENOSPC to signal 'no space in the kernel's semaphore tables'. Apache just relays the errno text. Once you have seen it, the phrasing plus AH00023's mutex context is unambiguous.

Is it safe to remove semaphores with ipcrm?

Safe for sets owned by the Apache user while Apache is stopped — they are orphans by definition. Do not bulk-remove other users' semaphores (databases hold live ones). The awk filter on the owner column is what keeps the operation surgical.

Which mutexes does this affect — and can I change their type?

mpm-accept, ssl-cache, rewrite-map and others. The Mutex directive can switch mechanisms (e.g. 'Mutex posixsem default' or file-based), which sidesteps SysV limits — an option when you cannot control kernel settings, at slight performance/portability trade-offs.
