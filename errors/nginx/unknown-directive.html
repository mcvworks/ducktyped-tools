Nginx Unknown Directive

Last updated: July 2, 2026

The config-test error 'nginx: [emerg] unknown directive' — a directive is misspelled, belongs to a module that is not loaded, or is not an nginx directive at all.

You might see this error as:

  • nginx: [emerg] unknown directive
  • nginx unknown directive
  • nginx -t unknown directive
  • unknown directive "stream"
  • nginx directive is not allowed here

What Does This Error Mean?

While parsing the configuration, nginx met a word it does not recognize as a directive, and refused to start or reload. Three families of cause: the directive is misspelled; the directive is real but implemented by a module this nginx build does not have loaded (common with stream, headers-more, brotli); or the line was copied from Apache or another server and simply is not nginx syntax. The error message includes the file and line number — start there.

Common Causes

  • Typo or wrong directive name — proxy_passs, server_names, fastcgi_passs — one letter is enough. The message quotes the exact token nginx could not resolve.
  • Module not compiled in or not loaded — Directives like 'stream', 'more_set_headers' (headers-more), 'brotli' or 'rtmp' need their module present. Dynamic modules also need an explicit load_module line before use.
  • Apache (or other server) syntax pasted in — RewriteRule, AllowOverride, Header set — Apache directives have nginx equivalents but are not valid as-is. Tutorials mixing servers cause this regularly.
  • Directive in a config for a different nginx flavor — OpenResty/Tengine-specific directives (content_by_lua_block and friends) fail on stock nginx builds that lack those modules.

How to Fix It

1. Test the config and read the exact location

nginx -t prints the file and line of the unknown directive. Fix or remove that line, then test again before reloading.

sudo nginx -t
# nginx: [emerg] unknown directive "more_set_headers" in /etc/nginx/conf.d/site.conf:12

2. Check whether the directive needs a module

See what your build includes, and install + load the module if it is missing.

nginx -V 2>&1 | tr ' ' '\n' | grep module
# Debian/Ubuntu example for headers-more:
sudo apt install libnginx-mod-http-headers-more-filter
# then ensure it is loaded (usually automatic via /etc/nginx/modules-enabled):
# load_module modules/ngx_http_headers_more_filter_module.so;

3. Translate foreign syntax to nginx

Replace Apache-isms with the nginx equivalent instead of pasting them: RewriteRule becomes rewrite/return, Header set becomes add_header, and .htaccess logic moves into the server block.

4. Mind the context for block directives

'stream {}' must sit at the top level of nginx.conf (not inside http {}), and it requires the stream module. A right directive in the wrong file can also surface as unknown when the including context does not support it.

# /etc/nginx/nginx.conf
load_module modules/ngx_stream_module.so;
stream {
    # TCP/UDP proxying here — NOT inside http {}
}

Frequently Asked Questions

The directive is spelled correctly — why is it still unknown?

Then the module implementing it is missing from your build or not loaded. Compare 'nginx -V' output against the module the directive belongs to (the nginx docs name it at the top of each directive's page), and add the package plus a load_module line if it is dynamic.

What is the difference between 'unknown directive' and 'directive is not allowed here'?

'Unknown' means nginx has never heard of the word — spelling or missing module. 'Not allowed here' means the directive exists but sits in the wrong context (e.g. server-only directive inside http). The second one is fixed by moving the line, not by installing anything.

Is it safe to reload if nginx -t fails?

A reload with a broken config is rejected and the old config keeps running — nginx protects you there. A full restart, however, leaves you DOWN with nothing running. Habit worth keeping: nginx -t before every reload, and never restart when a reload will do.
