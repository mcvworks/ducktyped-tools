Nginx bind() Failed — Address Already in Use

Last updated: July 2, 2026

The startup error 'nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)' — another process already owns the port nginx wants.

You might see this error as:

  • nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)
  • nginx bind failed
  • nginx address already in use
  • nginx port 80 already in use
  • bind() to [::]:80 failed

What Does This Error Mean?

Nginx refused to start (or reload into a new configuration) because it could not bind its listen port — something else is already listening there. The 'something else' is usually Apache installed alongside nginx, a stale nginx master process left over from a crashed restart, or a second copy of the same listen directive loaded from two config files. Until the port is free, systemd will show the service as failed.

Common Causes

  • Another web server owns port 80/443 — Apache (httpd) is the classic conflict — many distro LAMP packages start it on port 80 by default, and both servers cannot bind the same port.
  • A stale nginx process is still running — After a crashed upgrade or a kill of the master process, old worker or master processes can survive and hold the sockets, so a fresh start finds its own ghost in the way.
  • Duplicate listen directives across config files — The same server block loaded twice — a file present in both sites-enabled and conf.d, or a leftover backup like site.conf.save being included — makes nginx try to bind the same address twice.
  • Another service squatting the port — Node apps, Docker containers publishing 80/443, or a debugging tool can hold the port. On IPv6-enabled hosts, a conflict can also exist only on [::]:80.

How to Fix It

1. Identify the process holding the port

This one command names the culprit and its PID; everything else follows from what it shows.

sudo ss -tlnp | grep -E ':80 |:443 '
# or:
sudo lsof -i :80 -sTCP:LISTEN

2. Stop or disable the conflicting service

If Apache (or another server) owns the port and nginx should have it, stop and disable it so it does not return on reboot.

sudo systemctl stop apache2 && sudo systemctl disable apache2
# RHEL-family: httpd instead of apache2
sudo systemctl start nginx

3. Clear stale nginx processes

If ss shows nginx itself holding the port while systemd says the service is dead, kill the orphaned processes and start cleanly.

ps aux | grep [n]ginx
sudo pkill -f 'nginx: master'
sudo systemctl start nginx

4. Find duplicate listen directives

Dump the fully assembled configuration and look for the same listen address appearing in more than one server block that also shares a default_server flag or the whole block.

sudo nginx -T | grep -n 'listen'
ls -la /etc/nginx/sites-enabled/ /etc/nginx/conf.d/

Frequently Asked Questions

Why does this happen right after I stop nginx and start it again?

Usually a not-quite-dead master or worker still holds the socket for a moment. 'systemctl restart nginx' handles ordering correctly; if you killed processes manually, check with 'ps aux | grep nginx' that everything is gone before starting. Sockets in TIME_WAIT do not cause this error — only a live listener does.

The error mentions [::]:80 instead of 0.0.0.0:80 — what is different?

That is the IPv6 listener. If another service bound IPv6 port 80 (or nginx has both 'listen 80' and 'listen [::]:80' duplicated across blocks), the IPv4 bind can succeed while the IPv6 one fails. The diagnosis is identical: ss -tlnp, but look at the IPv6 rows.

Can two services share port 80 on the same machine?

Not directly — one listener per address:port. The standard patterns are: give nginx port 80 and proxy_pass to the other service on another port, or bind each service to different IP addresses. SO_REUSEPORT exists but is for multiple workers of the same server, not for two different daemons.

Related Errors

  • Docker Port Already Allocated — the same conflict from the container side.
  • Nginx Too Many Open Files — another resource-limit startup failure.
