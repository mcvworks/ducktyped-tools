Nginx Directory Index Forbidden

Last updated: July 2, 2026

The error-log line 'directory index of "/var/www/html/" is forbidden' — a request hit a directory, no index file matched, and autoindex is off, so nginx returned 403.

You might see this error as:

  • directory index of "/var/www/html/" is forbidden
  • nginx directory index is forbidden
  • nginx 403 directory index
  • autoindex nginx 403

What Does This Error Mean?

When a request maps to a directory rather than a file, nginx tries the filenames in the index directive (index.html by default). If none exists and directory listing (autoindex) is off — the safe default — nginx answers 403 and logs this line. It is a mismatch between what is on disk and what the config expects: the index file is missing or named differently, root points at the wrong directory, or the app needed a try_files fallback (single-page apps, PHP frontends) that is not configured.

Common Causes

  • No index file in the directory — The directory exists but contains no index.html (or nothing matching your index directive) — a deploy that did not copy files, or an intentionally file-less directory being hit by crawlers.
  • root points at the wrong directory — The index file exists — one level above or below where root says. Misplaced root inside location blocks (root + location paths concatenate) is a classic source.
  • index directive does not include the real filename — The app's entry point is index.php or app.html, while the directive only lists index.html — nginx never tries the file that exists.
  • SPA or PHP app without try_files — Client-side routed apps need every path to fall back to /index.html; PHP apps need index.php routing. Without try_files, directory URLs dead-end into this 403.

How to Fix It

1. Compare disk contents with the effective config

Look at what is really in the directory and what root/index nginx computed for the request.

ls -la /var/www/html/
sudo nginx -T | grep -E 'root|index' 
# the error log line names the exact directory nginx looked in

2. Fix root or add the right index

Point root at the directory that holds the entry file, and list the real filename in index.

server {
    root /var/www/myapp/public;
    index index.php index.html;
    ...
}
sudo nginx -t && sudo systemctl reload nginx

3. Add try_files for SPAs and PHP apps

Route directory and virtual paths to the app's entry point instead of the filesystem.

# single-page app:
location / {
    try_files $uri $uri/ /index.html;
}
# PHP front controller:
location / {
    try_files $uri $uri/ /index.php?$query_string;
}

4. Enable autoindex only for real file shares

If a browsable listing is the intent (downloads, mirrors), turn it on for that location only — never globally.

location /downloads/ {
    autoindex on;
    autoindex_exact_size off;
}

Frequently Asked Questions

How is this different from a permissions 403?

This 403 is about a missing index in a directory, and shows this exact 'directory index ... is forbidden' log line. A permissions 403 logs 'Permission denied' instead and involves file ownership/modes (or SELinux). Same status code to the client, entirely different fixes — always read the error log line.

Why does /page work but /page/ give 403?

Without the trailing slash nginx matched a file; with it, the request maps to a directory and enters index processing, which failed. A try_files fallback handles both forms uniformly for app-routed sites.

Is turning autoindex on a security risk?

It exposes every filename in the directory to anyone, including files you forgot were there (backups, dumps). It is fine for content that is deliberately public, dangerous as a global setting. If you only need to silence crawler noise on directories, returning 404 for them is cleaner than listing them.
