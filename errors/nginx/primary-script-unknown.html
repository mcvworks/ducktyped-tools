Nginx Primary Script Unknown (PHP-FPM)

Last updated: July 2, 2026

The error-log line 'FastCGI sent in stderr: "Primary script unknown"' — PHP-FPM could not find the script nginx asked it to run. Browsers show a bare 'File not found.'

You might see this error as:

  • FastCGI sent in stderr: "Primary script unknown"
  • Primary script unknown
  • php-fpm File not found.
  • nginx php file not found
  • SCRIPT_FILENAME nginx

What Does This Error Mean?

Nginx passed a request to PHP-FPM with a SCRIPT_FILENAME telling it which .php file to execute — and PHP-FPM answered that no such file exists from where it stands. The message is PHP-FPM's, but the bug is almost always in the nginx config: root is set in the wrong place so the computed path is wrong, or nginx and PHP-FPM see different filesystems (chroot, separate containers) so a path valid for nginx does not exist for PHP. The browser output is an unhelpful 'File not found.' — the error log has the real story.

Common Causes

  • SCRIPT_FILENAME resolves to the wrong path — root declared inside 'location /' but not visible to 'location ~ \.php$', or a hardcoded wrong path in fastcgi_param SCRIPT_FILENAME — the computed file simply is not there.
  • Nginx and PHP-FPM see different filesystems — In two-container setups, nginx's /var/www/html is not automatically PHP-FPM's /var/www/html. Without the same volume mounted at the same path in both, every path nginx sends is unknown to PHP.
  • The file genuinely is not there — Deploy did not copy the file, wrong document root after a migration, or a typo in the requested URL that ends in .php.
  • PHP-FPM cannot read the file — Less common: the pool user (www-data) lacks read/execute permission on the path, which PHP-FPM reports the same way as absence.

How to Fix It

1. Log what SCRIPT_FILENAME actually contains

Print the computed value into a header or check the standard snippet — most fixes are visible immediately once you see the path.

location ~ \.php$ {
    include snippets/fastcgi-php.conf;
    fastcgi_pass unix:/run/php/php8.3-fpm.sock;
    # ensure this resolves correctly:
    fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
}

2. Declare root at server level

Put root once on the server block (not inside location /) so $document_root is correct in the PHP location too.

server {
    root /var/www/myapp/public;   # HERE, not inside location /
    index index.php;
    location / { try_files $uri $uri/ /index.php?$query_string; }
    location ~ \.php$ { ... }
}

3. In Docker, share the code with both containers at the same path

Mount the application into nginx and php-fpm identically, and make SCRIPT_FILENAME use the path as PHP-FPM sees it.

# docker-compose.yml
services:
  nginx:
    volumes: ['./src:/var/www/html']
  php:
    volumes: ['./src:/var/www/html']
# nginx: fastcgi_param SCRIPT_FILENAME /var/www/html$fastcgi_script_name;

4. Verify the file exists as the PHP-FPM user

Check from PHP-FPM's perspective — inside its container or as its user.

# same host:
sudo -u www-data ls -la /var/www/myapp/public/index.php
# php container:
docker compose exec php ls -la /var/www/html/index.php

Frequently Asked Questions

The browser just says 'File not found.' — is that this error?

Yes — that plain-text response is PHP-FPM's output when the primary script is unknown; nginx forwards it with a 404. Confirm in /var/log/nginx/error.log, which will show the 'Primary script unknown' stderr line with the upstream details.

Why does it break only in Docker while the same config worked on a VM?

On a VM, nginx and PHP-FPM share one filesystem, so any correct path works for both. Two containers have two filesystems: SCRIPT_FILENAME is evaluated by nginx but opened by PHP-FPM. The volume must be mounted in the PHP container, and the path in SCRIPT_FILENAME must be the PHP container's path.

What does snippets/fastcgi-php.conf do for this?

Debian/Ubuntu's snippet sets the pieces that prevent this class of bug: splits path info correctly, checks the script exists (try_files $fastcgi_script_name =404), and includes fastcgi_params with SCRIPT_FILENAME built from $document_root. Using it plus a server-level root removes most footguns.
