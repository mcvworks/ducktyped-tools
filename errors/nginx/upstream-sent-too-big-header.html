Nginx Upstream Sent Too Big Header

Last updated: July 2, 2026

The error-log line 'upstream sent too big header while reading response header from upstream' — the backend's response headers overflowed nginx's buffer. Visitors see a 502.

You might see this error as:

  • upstream sent too big header while reading response header from upstream
  • nginx too big header
  • proxy_buffer_size 502
  • fastcgi_buffer_size error
  • nginx 502 after login oauth

What Does This Error Mean?

Nginx reads the backend's response status line and headers into a fixed buffer — proxy_buffer_size for proxied apps, fastcgi_buffer_size for PHP-FPM — sized 4KB or 8KB by default. If the headers alone exceed it, nginx aborts the response with this log line and serves a 502. The overflow is nearly always cookies: bloated session payloads, OAuth/OpenID flows stuffing tokens into Set-Cookie, or frameworks storing entire carts and view-states client-side. Raising the buffer unblocks; shrinking the headers is the real fix.

Common Causes

  • Very large Set-Cookie headers — Sessions serialized into cookies (JWTs with generous claims, framework view-state, multi-kilobyte carts) push header size past 4–8KB on exactly the responses that set them.
  • Authentication flows with long headers — OAuth2/OIDC callbacks and SAML responses commonly emit multiple long Set-Cookie and Location headers in one response — the classic 'login works everywhere except behind nginx' report.
  • Apps emitting debugging or custom headers — Verbose tracing headers, oversized CSP policies, or a bug that dumps data into a header can each singlehandedly overflow the buffer.
  • PHP-FPM with default fastcgi buffers — The FastCGI path has its own fastcgi_buffer_size; PHP apps with heavy cookies fail on it even after proxy_* was raised elsewhere.

How to Fix It

1. Measure the actual header size

Reproduce against the backend directly and see how big the response headers really are — this tells you buffer size vs. app bug.

curl -sS -D - -o /dev/null http://127.0.0.1:3000/auth/callback | wc -c
# dump them to inspect the offender:
curl -sS -D - -o /dev/null http://127.0.0.1:3000/auth/callback

2. Raise the proxy buffers

Set proxy_buffer_size big enough for your largest legitimate headers; keep proxy_buffers consistent (busy buffers must fit).

location / {
    proxy_pass http://backend;
    proxy_buffer_size   16k;
    proxy_buffers       8 16k;
    proxy_busy_buffers_size 32k;
}
sudo nginx -t && sudo systemctl reload nginx

3. Raise the FastCGI buffers for PHP

The same tuning on the FastCGI path.

location ~ \.php$ {
    fastcgi_pass unix:/run/php/php8.3-fpm.sock;
    fastcgi_buffer_size 16k;
    fastcgi_buffers     8 16k;
}

4. Shrink the headers at the source

Move session data server-side (store an ID in the cookie, not the data), trim JWT claims, and delete debug headers. Headers ride on every request and response — smaller is faster for everyone, not just for nginx.

Frequently Asked Questions

Users see 502 only on login/callback pages — why there?

Those responses carry the largest headers (multiple Set-Cookie with tokens plus redirects), so they are the first to overflow the buffer. It is the signature symptom of this error — check the error log for 'too big header' at those timestamps.

What are sane buffer values?

16k for proxy_buffer_size/fastcgi_buffer_size covers almost all legitimate applications; 32k is a generous ceiling. If you need more than that, treat it as an application bug — some component is stuffing data into headers that belongs in a store.

Is this related to '400 Request Header Or Cookie Too Large'?

Mirror images: this error is response headers from the backend overflowing proxy buffers (client sees 502). The 400 is request headers from the client overflowing large_client_header_buffers (client sees 400, often from the same oversized cookies on the way back in). Fixing cookie bloat addresses both.
