Nginx Permission Denied While Connecting to Upstream

Last updated: July 2, 2026

The error-log line 'connect() to ... failed (13: Permission denied) while connecting to upstream' — the OS blocked nginx's connection to the backend, classically SELinux.

You might see this error as:

  • connect() to failed (13: Permission denied) while connecting to upstream
  • 13 permission denied nginx upstream
  • selinux nginx proxy denied
  • httpd_can_network_connect
  • php-fpm socket permission denied nginx

What Does This Error Mean?

Unlike 'connection refused' (nothing listening) or 'timed out' (no answer), errno 13 means the operating system forbade nginx from even attempting the connection. On RHEL, CentOS, Fedora, Rocky, and Alma, that is SELinux: the default policy stops the web-server domain from initiating arbitrary network connections, so a proxy_pass to a backend port dies with permission denied even though curl from the same shell works fine. The Unix-socket variant is ordinary file permissions: nginx's worker user cannot read/write the backend's socket file.

Common Causes

  • SELinux blocks httpd network connections — The boolean httpd_can_network_connect defaults to off. Any proxy_pass/fastcgi_pass over TCP from nginx (which runs in the httpd_t domain) is denied — the single most common cause on RHEL-family systems.
  • Backend port not in SELinux's http_port_t — Even with narrower booleans, connecting to unusual ports (3000, 8081, 5000) can be denied unless the port is labeled appropriately.
  • Unix socket file permissions — fastcgi_pass/proxy_pass to a unix: socket requires the nginx user to have write access to the socket file — PHP-FPM pools default their socket owner to www-data or apache, which may not match.
  • AppArmor or other MAC on Debian-family — Rare by default, but a strict AppArmor profile for nginx can produce the same errno 13 on Ubuntu — check the audit log if SELinux is absent.

How to Fix It

1. Confirm SELinux is the blocker

Check enforcement and look for the denial in the audit log — the denial names nginx and the target port.

getenforce
sudo ausearch -m avc -ts recent | grep -i nginx
# or:
sudo grep denied /var/log/audit/audit.log | tail -5

2. Allow web-server network connections

Set the boolean persistently. Use the narrower relay/db variants when they fit your topology.

sudo setsebool -P httpd_can_network_connect 1
# narrower options:
#   httpd_can_network_relay 1     (reverse-proxy only)
#   httpd_can_network_connect_db 1 (database ports only)

3. Fix Unix socket permissions

Align the socket's owner/group with the nginx user in the backend's pool config, then restart the backend.

# /etc/php-fpm.d/www.conf
listen = /run/php-fpm/www.sock
listen.owner = nginx
listen.group = nginx
listen.mode = 0660

sudo systemctl restart php-fpm
ls -la /run/php-fpm/www.sock

4. Never fix this by disabling SELinux

setenforce 0 'works' by removing a security layer from the whole system. The boolean above grants exactly the permission nginx needs and nothing else — there is no good reason to trade the entire policy for it.

Frequently Asked Questions

Why does curl to the backend work while nginx gets denied?

SELinux rules are per-domain: your shell runs unconfined, nginx runs in httpd_t with restricted network permissions. Same destination, different subject, different verdict. That asymmetry — 'it works from the terminal' — is the tell that you are looking at SELinux rather than the network.

How do I see exactly what SELinux denied?

'ausearch -m avc -ts recent' lists denials with the source process, target port, and context. Piping a denial into 'audit2why' explains it and often names the boolean to set. That workflow beats guessing.

Does this explain permission denied on port 80 binding too?

Different mechanism: binding low ports needs CAP_NET_BIND_SERVICE (nginx's master runs as root, so it usually has it). Errno 13 'while connecting to upstream' is specifically about outbound connections — SELinux territory on RHEL-family systems.
