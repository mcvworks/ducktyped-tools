Nginx Cannot Load Certificate

Last updated: July 2, 2026

Startup/reload errors like 'nginx: [emerg] cannot load certificate' or 'SSL_CTX_use_PrivateKey_file failed (key values mismatch)' — the TLS files are missing, unreadable, or mismatched.

You might see this error as:

  • nginx: [emerg] cannot load certificate
  • SSL_CTX_use_PrivateKey_file failed
  • key values mismatch nginx
  • PEM_read_bio_X509_AUX failed
  • nginx ssl certificate error emerg

What Does This Error Mean?

Nginx validates every ssl_certificate and ssl_certificate_key at config load. Failure here blocks the reload (or the whole start), and the message narrows it down: 'No such file or directory' is a path problem, 'Permission denied' is filesystem access, 'PEM routines' errors mean the file content is not what nginx expects, and 'key values mismatch' means the certificate and the private key are not a pair — typically one was renewed or copied while the other was not.

Common Causes

  • Wrong file path — The config points at a moved or deleted file — common after switching from self-signed to Let's Encrypt paths, or copying a config between servers whose cert locations differ.
  • Certificate and key do not match — The cert was replaced (renewal, re-issue) but the old key stayed, or files from two different issuances got mixed. OpenSSL's pair check settles it in seconds.
  • Not PEM, or PEM assembled wrongly — A DER/.pfx file where PEM is expected, Windows line endings, a missing final newline, or a fullchain built in the wrong order (intermediates before the leaf) all trigger PEM routine errors.
  • Permissions or dangling symlinks — Keys locked to another user, or Let's Encrypt's /etc/letsencrypt/live symlinks pointing at archive files that were cleaned up or not copied when migrating servers.

How to Fix It

1. Check the files exist and are readable

Follow symlinks — Let's Encrypt's live/ directory is all symlinks into archive/.

ls -lL /etc/letsencrypt/live/example.com/
sudo head -1 /etc/letsencrypt/live/example.com/fullchain.pem
# should print: -----BEGIN CERTIFICATE-----

2. Verify the cert and key are a pair

Compare the public-key fingerprints derived from each file; they must be identical.

openssl x509 -noout -pubkey -in fullchain.pem | openssl sha256
openssl pkey  -noout -pubkey -in privkey.pem  | openssl sha256
# identical hashes = matching pair

3. Use fullchain, in the right order

Point ssl_certificate at the full chain (leaf first, then intermediates). Serving only the leaf 'works' in some browsers but fails strict clients.

ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
sudo nginx -t && sudo systemctl reload nginx

4. Convert non-PEM formats

If the file came from a Windows export or a provider bundle, convert it to PEM first.

# DER -> PEM
openssl x509 -inform der -in cert.der -out cert.pem
# PFX/PKCS12 -> PEM cert + key
openssl pkcs12 -in bundle.pfx -clcerts -nokeys -out cert.pem
openssl pkcs12 -in bundle.pfx -nocerts -nodes  -out key.pem

Frequently Asked Questions

What exactly does 'key values mismatch' mean?

The modulus/public key inside the certificate does not equal the one derived from the private key file — they are from different generations or different CSRs. Find the key that was created with the CSR for this certificate, or re-issue the certificate from the key you have.

cert.pem, chain.pem, fullchain.pem — which goes where?

For nginx: ssl_certificate = fullchain.pem (leaf + intermediates), ssl_certificate_key = privkey.pem. cert.pem (leaf only) causes chain errors for strict clients; chain.pem alone is never what ssl_certificate wants. Modern nginx has no separate directive for the chain — it all goes in fullchain.

Why did this break right after a certbot renewal?

Renewal rotates files under /etc/letsencrypt/archive and updates the live/ symlinks. If your config points at a copied file rather than the symlink, or a deploy hook copies only the cert and not the new key, you end up mismatched. Point nginx at the live/ symlinks and reload in a certbot deploy hook.
