Nginx Conflicting Server Name

Last updated: July 2, 2026

The warning 'nginx: [warn] conflicting server name "example.com" on 0.0.0.0:80, ignored' — two server blocks claim the same name, and nginx is silently ignoring one of them.

You might see this error as:

  • nginx: [warn] conflicting server name
  • conflicting server name ignored
  • nginx duplicate server_name
  • nginx duplicate server block

What Does This Error Mean?

Two (or more) server blocks declare the same server_name for the same listen address. Nginx does not fail — it keeps the first block it loaded and ignores the duplicate name in later ones, printing this warning at config test or reload. The danger is precisely that it is only a warning: your edits to the ignored block do nothing, redirects seem not to apply, certificates appear stale — because a different block than the one you are editing is serving the traffic.

Common Causes

  • The same vhost loaded from two places — A config present in both /etc/nginx/conf.d/ and /etc/nginx/sites-enabled/, or an old copy left beside the new one — both get included, the name collides.
  • Backup files caught by the include glob — include sites-enabled/*; loads everything — site.conf.bak, site.conf.save, site.conf.orig included. Editor backups quietly become live duplicate vhosts.
  • Tool-generated duplicates — Certbot's --nginx installer, control panels, or provisioning scripts sometimes write a new server block instead of editing the existing one — same server_name, different files.
  • Same name intentionally split across HTTP/HTTPS gone wrong — Having example.com on :80 and :443 in separate blocks is normal and does NOT warn. The warning appears when the same name doubles up on the same port — often after copy-pasting the HTTPS block to make the HTTP one.

How to Fix It

1. Find every block claiming the name

Dump the effective config with filenames and locate all declarations of the conflicting name and their listen ports.

sudo nginx -T | grep -nE 'configuration file|server_name .*example.com|listen '
# or across the config tree:
sudo grep -rn 'server_name' /etc/nginx/ | grep example.com

2. Delete or merge the duplicate

Keep exactly one block per name+port. If both blocks contain needed directives, merge them, then remove the loser and reload.

sudo rm /etc/nginx/sites-enabled/example.com.conf.bak
sudo nginx -t && sudo systemctl reload nginx
# warning gone = resolved

3. Tighten the include pattern

Restrict includes to *.conf so backup files can never go live again.

# /etc/nginx/nginx.conf
http {
    include /etc/nginx/conf.d/*.conf;
    include /etc/nginx/sites-enabled/*.conf;   # not sites-enabled/*
}

Frequently Asked Questions

Which of the duplicate blocks actually serves traffic?

The first one nginx loads — include order is alphabetical within each include directive, in the order the includes appear. That is why symptoms feel random: it depends on filenames. 'nginx -T' prints blocks in load order, so the first block showing that server_name is the winner.

It is just a [warn] — can I ignore it?

The process runs fine, but one of your config files is dead weight that looks alive. Sooner or later someone edits the ignored block and loses hours wondering why nothing changes — or worse, the wrong block serves an old certificate. Treat the warning as a to-do, not noise.

Is the same server_name on ports 80 and 443 a conflict?

No — the conflict space is name + listen address:port. One block for :80 (usually a redirect to HTTPS) and one for :443 with the same name is the standard pattern and produces no warning.
