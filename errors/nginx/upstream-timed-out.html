Nginx Upstream Timed Out

Last updated: July 2, 2026

The error-log line 'upstream timed out (110: Connection timed out) while reading response header from upstream' — the backend took longer than nginx was willing to wait. Visitors see a 504.

You might see this error as:

  • upstream timed out (110: Connection timed out) while reading response header from upstream
  • nginx upstream timed out
  • 110 connection timed out nginx
  • nginx 504 upstream timeout
  • proxy_read_timeout exceeded

What Does This Error Mean?

Nginx connected to the backend fine, sent the request, and then waited for a response that did not arrive within the timeout — 60 seconds by default. The client gets a 504 Gateway Timeout. Which timeout fired matters: 'while connecting' means the TCP connection itself stalled (network/firewall); 'while reading response header' — by far the most common — means the backend accepted the request but is too slow to answer: a heavy query, a stuck external call, or exhausted workers.

Common Causes

  • The backend is genuinely slow — A report endpoint, a huge unindexed database query, an external API call without its own timeout — the request needs more than 60 seconds and nginx gives up first.
  • Backend worker pool is exhausted — All PHP-FPM children / gunicorn workers / Node event loop capacity are busy, so new requests queue until they either get served late or time out.
  • Timeout directives are set too low for specific routes — A global proxy_read_timeout tuned for fast pages also applies to the one endpoint that legitimately takes two minutes, guaranteeing 504s there.
  • Network path problems on 'while connecting' timeouts — If the log says 'while connecting to upstream', the TCP handshake itself hung — a firewall dropping packets, wrong routes, or a dead host, not a slow application.

How to Fix It

1. Confirm how slow the backend really is

Time the backend directly, bypassing nginx, to separate 'slow app' from 'network problem'.

time curl -sS -o /dev/null http://127.0.0.1:3000/slow-endpoint
# detailed timing through the public URL:
curl -w 'connect=%{time_connect}s ttfb=%{time_starttransfer}s total=%{time_total}s\n' -o /dev/null -sS https://example.com/slow-endpoint

2. Raise the timeout only where it is legitimate

Scope longer timeouts to the specific slow location instead of globally, so real failures elsewhere still fail fast.

location /reports/ {
    proxy_pass http://backend;
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
}
# PHP-FPM equivalent:
# fastcgi_read_timeout 300s;  (and max_execution_time in PHP)

3. Fix the slowness at the source

EXPLAIN the query and add the missing index, put a timeout on outbound API calls, or move multi-minute work to a background job that the client polls — a 5-minute HTTP request is fragile no matter the timeout settings.

4. Check worker saturation

If fast endpoints also time out under load, the pool is exhausted — scale workers within memory limits.

# PHP-FPM: watch for 'max children reached' warnings
sudo grep -i 'max_children' /var/log/php*-fpm.log*
# gunicorn/node: check process CPU and event-loop lag during the incident

Frequently Asked Questions

Is this the same as a 504 Gateway Timeout?

This log line is the usual cause of the 504 the visitor sees. 504 is the symptom on the client side; 'upstream timed out' in the error log is nginx's reason. If you see 504s without this line, something else in the chain (a CDN or another proxy layer) timed out instead.

Which timeout directive actually applies?

For proxy_pass: proxy_connect_timeout (TCP connect), proxy_send_timeout (sending the request), proxy_read_timeout (waiting between reads of the response — the one that fires for slow backends). For PHP, the fastcgi_* equivalents. WebSockets need long proxy_read_timeout since frames can be minutes apart.

Should I just set the timeout to 10 minutes?

Usually no. Long timeouts keep connections and workers pinned during incidents and hide real performance regressions. Raise it surgically for endpoints that legitimately take long, and prefer converting those to async jobs; keep everything else fast-failing.
