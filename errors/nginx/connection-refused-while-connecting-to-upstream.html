Nginx Connection Refused While Connecting to Upstream

Last updated: July 2, 2026

The error-log line 'connect() failed (111: Connection refused) while connecting to upstream' — nginx reached the backend host, but nothing was listening. Visitors see a 502.

You might see this error as:

  • connect() failed (111: Connection refused) while connecting to upstream
  • nginx upstream connection refused
  • nginx 502 connection refused
  • 111 connection refused nginx
  • fastcgi connection refused

What Does This Error Mean?

Nginx accepted a client request and tried to hand it to the backend named in proxy_pass or fastcgi_pass — and the backend's machine answered 'nothing listens on that port'. The client gets a 502 Bad Gateway; this log line is the server-side reason. It always means the network path worked but the destination was wrong or dead: the app crashed or never started, the port in proxy_pass does not match the app's real port, or (very common in containers) 'localhost' does not mean what the config assumes.

Common Causes

  • The backend application is down — Crashed, OOM-killed, failed to boot after deploy, or never enabled at boot. Nothing listens, so the kernel refuses the connection.
  • proxy_pass points at the wrong port or interface — App listens on 3000, config says 8000; or the app binds 127.0.0.1 while nginx connects to the machine's external IP (or the reverse).
  • 'localhost' inside a container is not the host — When nginx runs in a container, 127.0.0.1 is the container itself. A proxy_pass to localhost:3000 for an app in another container (or on the host) refuses — use the service name or host gateway instead.
  • PHP-FPM socket/TCP mismatch — fastcgi_pass says 127.0.0.1:9000 while PHP-FPM listens on a Unix socket (or the other way round), or the socket path differs per PHP version (/run/php/php8.3-fpm.sock).

How to Fix It

1. Check the backend is running and where it listens

Confirm the process exists and note the exact address:port it bound — then compare with proxy_pass.

sudo ss -tlnp | grep -E '3000|9000'
systemctl status myapp
# test from the nginx host/container itself:
curl -sS http://127.0.0.1:3000/health

2. Fix the proxy_pass target

Make the config match reality — port, host, and scheme.

location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
sudo nginx -t && sudo systemctl reload nginx

3. In Docker, address containers by service name

On a shared network, the service name resolves to the right container. For an app on the host, use host.docker.internal (add the host-gateway mapping on Linux).

# docker-compose.yml
services:
  nginx:
    ...
  app:
    ...
# nginx.conf inside the nginx container:
#   proxy_pass http://app:3000;
# app on the HOST instead:
#   extra_hosts: ["host.docker.internal:host-gateway"]
#   proxy_pass http://host.docker.internal:3000;

4. Align PHP-FPM's listen with fastcgi_pass

Check the pool config and use the same socket or TCP address in nginx.

grep -r '^listen' /etc/php/*/fpm/pool.d/
# if it shows: listen = /run/php/php8.3-fpm.sock
fastcgi_pass unix:/run/php/php8.3-fpm.sock;

Frequently Asked Questions

Visitors see 502 Bad Gateway — is that this error?

This log line is one of the causes behind a 502. The 502 page is what the client sees; 'connection refused while connecting to upstream' in /var/log/nginx/error.log tells you why — the backend was not listening. Other 502 flavors (timeouts, oversized headers) have their own log lines and their own guides.

Why does it happen intermittently, a few seconds at a time?

The backend is restarting — crash loops, deployment restarts, or OOM kills. Check the app's logs and 'journalctl -u yourapp' around the timestamps in the nginx error log. Zero-downtime deploys (start new instance, then switch) or a second upstream server remove the visible blips.

Connection refused vs timed out — what is the difference?

Refused (111) is an active 'no' — the host is reachable, the port is closed; look at the backend process. Timed out (110) is silence — packets go unanswered; look at firewalls, network paths, or an overloaded backend that cannot even accept.
