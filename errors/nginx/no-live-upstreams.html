Nginx No Live Upstreams

Last updated: July 2, 2026

The error-log line 'no live upstreams while connecting to upstream' — every server in the upstream block is currently marked failed, so nginx has nowhere to send the request.

You might see this error as:

  • no live upstreams while connecting to upstream
  • nginx no live upstreams
  • nginx all upstreams failed
  • nginx 502 no live upstreams

What Does This Error Mean?

When proxying to an upstream {} group, nginx tracks failures per server. A server that fails max_fails times (default 1) within fail_timeout (default 10s) is taken out of rotation for fail_timeout seconds. 'No live upstreams' means every server in the group is in that penalty box at once — nginx did not even attempt a connection for this request, and the client gets an instant 502. It is the aggregate symptom; the individual failures (refused, timeout) that got the servers marked down are logged just before it.

Common Causes

  • All backends are actually down — A deploy restarted every instance at once, a shared dependency (database) is down making all health checks fail, or there is only one server in the group and it died.
  • Aggressive max_fails with transient blips — With the default max_fails=1, a single hiccup per server within 10 seconds can knock the whole pool out — a brief network wobble becomes a full outage window.
  • Slow backends being marked failed by timeouts — If proxy timeouts are shorter than real response times under load, every server keeps 'failing' by timeout and rotation empties itself in a load spiral.
  • Stale IPs after backend redeployment — nginx resolves upstream hostnames at config load. If the backends moved (containers rescheduled, autoscaling), nginx still tries the old IPs until reload — all of which fail.

How to Fix It

1. Read the log lines just before this one

The refused/timeout entries preceding 'no live upstreams' name the real failure per server — fix that first (see the related guides).

sudo tail -100 /var/log/nginx/error.log | grep -B3 'no live upstreams'

2. Verify each upstream server directly

Hit every backend one by one from the nginx host to see which are genuinely dead.

# for each server in the upstream block:
curl -sS -o /dev/null -w '%{http_code}\n' http://10.0.0.11:3000/health
curl -sS -o /dev/null -w '%{http_code}\n' http://10.0.0.12:3000/health

3. Soften failure marking and add a backup

Allow a few failures before eviction, keep eviction short, and give nginx a last-resort server so the pool never goes completely empty.

upstream app {
    server 10.0.0.11:3000 max_fails=3 fail_timeout=15s;
    server 10.0.0.12:3000 max_fails=3 fail_timeout=15s;
    server 10.0.0.13:3000 backup;
}

4. Reload nginx after backends move

If IPs changed, a reload re-resolves the hostnames. For dynamic environments, use a resolver with variables in proxy_pass (or nginx Plus / a service-discovery template) so re-resolution happens automatically.

sudo nginx -s reload
# dynamic re-resolution pattern (open source nginx):
# resolver 127.0.0.11 valid=10s;   # Docker's DNS
# set $backend http://app:3000;
# proxy_pass $backend;

Frequently Asked Questions

How long does a server stay marked down?

fail_timeout seconds (default 10). After that, nginx sends it a real request as a probe; success returns it to rotation, another failure re-evicts it. There is no background health check in open-source nginx — recovery only happens via live traffic.

Why do I get this with only one backend server?

A single-server upstream block still uses the failure accounting: one refused connection can put your only server in the penalty box for 10 seconds, during which every request instantly 502s with 'no live upstreams' instead of retrying. Either fix the backend blip or set max_fails=0 (never mark down) for single-server groups.

Rolling deploys briefly trigger this — how do teams avoid it?

Restart backends one at a time, keeping the rest serving; use max_fails/fail_timeout values that tolerate the restart window; and drain by removing a server from the upstream (reload) before restarting it. A 'backup' server also bridges short gaps.
