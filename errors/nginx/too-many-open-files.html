Nginx Too Many Open Files

Last updated: July 2, 2026

Error-log lines like 'socket() failed (24: Too many open files)' or 'accept4() failed' — nginx hit its file-descriptor limit and is dropping connections.

You might see this error as:

  • socket() failed (24: Too many open files)
  • accept4() failed (24: Too many open files)
  • nginx too many open files
  • worker_connections exceed open file resource limit

What Does This Error Mean?

Every client connection, upstream connection, open log file, and cached file costs nginx a file descriptor. When a worker reaches the per-process limit (ulimit -n, often a paltry 1024 from the OS default), new sockets fail with errno 24 and requests start erroring under load. The trap: worker_connections promises capacity that the descriptor limit silently cannot back — proxying needs roughly two descriptors per active connection (client side + upstream side), so worker_connections 4096 needs a limit comfortably above 8192.

Common Causes

  • Default 1024 descriptor limit — Distro defaults are made for shell sessions, not busy servers. The nginx service inherits the limit unless it is raised explicitly for the service.
  • worker_connections exceeds the real limit — Setting worker_connections high without worker_rlimit_nofile means nginx will accept work it cannot open descriptors for — the mismatch only shows under real traffic.
  • Proxying doubles descriptor usage — A reverse proxy holds the client socket and the upstream socket simultaneously. Keepalive pools to upstreams add more standing descriptors on top.
  • Descriptor leaks from many log/cache files — Per-vhost access logs across hundreds of server blocks, open_file_cache with large limits, and proxy_cache activity all consume descriptors before the first client connects.

How to Fix It

1. See the limits nginx is actually running with

Check the live process (not your shell — its ulimit is irrelevant to the service).

cat /proc/$(pgrep -f 'nginx: master')/limits | grep 'open files'
# current usage per worker:
ls /proc/$(pgrep -f 'nginx: worker' | head -1)/fd | wc -l

2. Raise the limit in nginx itself

worker_rlimit_nofile lets the master raise its workers' limit directly — the simplest reliable fix.

# /etc/nginx/nginx.conf (top level)
worker_rlimit_nofile 65536;

events {
    worker_connections 16384;
}
sudo nginx -t && sudo systemctl restart nginx

3. Raise the systemd service limit too

Belt and braces for the master process and anything it opens before workers spawn.

sudo systemctl edit nginx
# add:
[Service]
LimitNOFILE=65536

sudo systemctl daemon-reload && sudo systemctl restart nginx

4. Check the system-wide ceiling

On very busy hosts, confirm the kernel-wide limit dwarfs the per-process one.

cat /proc/sys/fs/file-max
cat /proc/sys/fs/file-nr   # allocated vs max
# raise if needed:
echo 'fs.file-max = 2097152' | sudo tee /etc/sysctl.d/99-nginx.conf && sudo sysctl -p /etc/sysctl.d/99-nginx.conf

Frequently Asked Questions

How do worker_connections and the descriptor limit relate?

worker_connections caps concurrent connections per worker; each connection needs at least one descriptor, two when proxying, plus nginx's own files. Rule of thumb: worker_rlimit_nofile at least 2× worker_connections, with headroom. The effective client capacity of the server is worker_processes × worker_connections (halved when proxying).

Why did changing /etc/security/limits.conf not help?

limits.conf applies to PAM login sessions. Services started by systemd never pass through PAM, so nginx ignores it entirely. Use worker_rlimit_nofile in nginx.conf or LimitNOFILE in the systemd unit.

Clients see errors — what does this look like from outside?

A mix of refused/reset connections and 500s while established connections keep working — capacity exhaustion rather than a hard outage. The error log correlates exactly: bursts of '(24: Too many open files)' during traffic peaks.
