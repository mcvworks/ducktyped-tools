Node.js ERR_REQUIRE_ESM

Last updated: July 2, 2026

The crash 'Error [ERR_REQUIRE_ESM]: require() of ES Module ... not supported' — CommonJS code tried to require() a package that ships only as an ES module.

You might see this error as:

  • ERR_REQUIRE_ESM
  • require() of ES Module not supported
  • Error [ERR_REQUIRE_ESM]
  • chalk require error
  • node-fetch esm require

What Does This Error Mean?

Packages like chalk 5, node-fetch 3, got 12, and execa 6 dropped CommonJS builds and ship pure ESM. On older Node versions, CommonJS require() cannot load an ES module synchronously, so Node throws ERR_REQUIRE_ESM — usually right after an innocent-looking dependency upgrade. You have four ways out: await a dynamic import() from CJS, pin the last CJS version of the package, migrate your project to ESM, or run a recent Node — since Node 22.12, require() of ES modules works natively in most cases, making this error largely historical on current runtimes.

Common Causes

  • A dependency went ESM-only in a major release — The upgrade from chalk 4→5 or node-fetch 2→3 changes the packaging, not just the API — CJS consumers break immediately.
  • TypeScript compiling to CommonJS — With module: commonjs, tsc turns your import statements into require() calls — which then hit the ESM-only package at runtime even though the source looked like ESM.
  • Old Node version — Node before 22.12 cannot require() ES modules (Node 20.17+ could with a flag). The same code may work on a colleague's newer runtime and fail on yours.
  • Tooling that loads config via require — Task runners and older frameworks require() user configs; writing that config as ESM (or importing ESM inside it) triggers the error inside the tool.

How to Fix It

1. Use dynamic import() from CommonJS

import() works in CJS and returns a promise — the standard bridge.

// before (crashes):
// const chalk = require('chalk');

// after:
async function main() {
  const { default: chalk } = await import('chalk');
  console.log(chalk.green('ok'));
}
main();

2. Or pin the last CommonJS major version

Legitimate for stable code you do not want to migrate — the old majors still receive no new features but work fine.

npm install chalk@4 node-fetch@2 got@11
# note the pin's reason in package.json or a comment file

3. Or migrate the project to ESM

The long-term direction: declare type module, convert requires to imports, adjust TS config.

// package.json
{ "type": "module" }
// tsconfig.json (TS projects)
{ "compilerOptions": { "module": "nodenext", "moduleResolution": "nodenext" } }

4. Or upgrade Node

On Node 22.12+ require() of ES modules is supported natively (unless the module uses top-level await); the error disappears without code changes.

node --version
nvm install 22 && nvm use 22

Frequently Asked Questions

Why did package authors drop CommonJS at all?

Maintaining dual builds (CJS + ESM) is genuinely painful — conditional exports, duplicated tests, subtle interop bugs. ESM is the standard module system for both browsers and Node, so many authors cut over. The friction landed on CJS consumers during the transition years.

Does dynamic import() have downsides in CJS?

It is asynchronous, so top-level synchronous initialization patterns need restructuring (an async init function, or caching the promise). Bundle-analysis tools also treat it as a code-split point. Otherwise it is well-supported and the official interop path.

How does TypeScript fit in — my source already uses import?

What matters is the emitted JavaScript. module: commonjs emits require() calls. Set module/moduleResolution to nodenext and type: module in package.json so tsc emits real ESM — then ESM-only dependencies load naturally.
