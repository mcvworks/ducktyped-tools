Node.js error:0308010C — Digital Envelope Routines Unsupported

Last updated: July 2, 2026

The build crash 'Error: error:0308010C:digital envelope routines::unsupported' — Node 17+ (OpenSSL 3) rejects legacy hash usage in older webpack toolchains.

You might see this error as:

  • error:0308010C:digital envelope routines::unsupported
  • ERR_OSSL_EVP_UNSUPPORTED
  • digital envelope routines unsupported
  • openssl-legacy-provider
  • node 17 webpack openssl error

What Does This Error Mean?

Node 17 switched to OpenSSL 3, which disables legacy crypto algorithms by default — including the MD4 hashing that webpack 4 used internally for module identifiers. Any toolchain built on webpack 4 (create-react-app's react-scripts 4, vue-cli 4, older Angular, countless custom configs) crashes with error:0308010C the moment it runs on Node 17+. Nothing is wrong with your application code; the build tool's internal hashing is what OpenSSL rejects. The real fix is upgrading the toolchain to webpack 5-based versions; the documented stopgap is enabling OpenSSL's legacy provider.

Common Causes

  • webpack 4-era toolchain on Node 17+ — react-scripts 4, vue-cli 4, webpack 4 configs — all hash with MD4 via Node's crypto, which OpenSSL 3 refuses by default.
  • Node upgraded underneath a frozen project — CI images and dev machines move to current LTS; a project pinned to old build tooling starts failing without any code change.
  • A dependency calling a legacy algorithm directly — Less common: application code or a library invoking crypto.createHash('md4') or other removed-by-default algorithms.

How to Fix It

1. Upgrade the toolchain (real fix)

Move to the webpack 5 generation of your framework tooling.

# create-react-app projects:
npm install react-scripts@5
# vue-cli:
npm install @vue/cli-service@5
# raw webpack:
npm install webpack@5 webpack-cli@5
npm run build

2. Stopgap: enable OpenSSL's legacy provider

Unblocks the build today. It re-enables legacy algorithms inside this process only — treat it as technical debt with the upgrade scheduled.

NODE_OPTIONS=--openssl-legacy-provider npm run build
# or per-script:
"build": "cross-env NODE_OPTIONS=--openssl-legacy-provider webpack --mode production"

3. Alternative stopgap: run the build on Node 16

Node 16 predates OpenSSL 3 — but it is end-of-life (no security updates), so use only as a bridge in isolated CI, not as the resting state.

nvm install 16
nvm exec 16 npm run build

4. If your own code hashes with MD4

Switch to a supported algorithm — MD4 is cryptographically broken anyway.

// before: crypto.createHash('md4')
const crypto = require('crypto');
const h = crypto.createHash('sha256').update(data).digest('hex');

Frequently Asked Questions

Is --openssl-legacy-provider dangerous?

It re-enables old algorithms for that Node process. For a build step hashing module names, the practical risk is negligible; the danger is normalizing it in servers doing real cryptography. Scope it to the build command, and schedule the toolchain upgrade that removes the need.

Why exactly did OpenSSL 3 break MD4?

OpenSSL 3 moved obsolete algorithms (MD4 among them — broken since the 1990s for cryptographic purposes) into a 'legacy provider' that is off by default. webpack 4 used MD4 not for security but as a fast content hash; harmless use, same locked door.

I upgraded react-scripts and got a wall of new errors — expected?

The 4→5 jump swaps webpack majors, so plugin and polyfill differences surface (webpack 5 stopped auto-polyfilling Node core modules for the browser). It is one afternoon of migration in most apps — resolve the polyfill errors with the fallbacks the messages suggest, and drop obsolete plugins.
