Node.js UNABLE_TO_GET_ISSUER_CERT_LOCALLY

Last updated: July 2, 2026

TLS failures like 'npm ERR! UNABLE_TO_GET_ISSUER_CERT_LOCALLY' or fetch failing with 'unable to get local issuer certificate' — Node cannot verify the server's certificate chain, typically behind a corporate proxy.

You might see this error as:

  • UNABLE_TO_GET_ISSUER_CERT_LOCALLY
  • unable to get local issuer certificate
  • npm ERR! request failed unable to get local issuer certificate
  • NODE_EXTRA_CA_CERTS
  • self signed certificate in certificate chain

What Does This Error Mean?

Node ships its own bundle of trusted certificate authorities and, unlike browsers, does not use the operating system's store. When a TLS connection presents a chain Node cannot verify against that bundle, requests fail with this error. In practice that means one of two things: a corporate network is intercepting TLS (Zscaler, Netskope, Palo Alto and friends re-sign every connection with the company CA — which Node has never heard of), or you are talking to an internal service with a self-signed or private-CA certificate. The correct fix is always to teach Node the extra CA — not to switch verification off.

Common Causes

  • Corporate TLS interception — The proxy re-encrypts all traffic with the company's own CA. Browsers work (the CA was pushed to the OS store); Node and npm fail because they use their own bundle.
  • Internal services with a private CA or self-signed cert — Registries, Git servers, and APIs inside the company signed by a CA that public bundles do not contain.
  • Server serving an incomplete chain — If the failure is only with one external site and happens outside corporate networks, that server may be missing its intermediate certificate — a server-side bug.
  • Minimal containers without CA certificates — Slim images missing the ca-certificates package fail verification for everything — a different but similar-looking failure.

How to Fix It

1. Add the corporate/private CA for Node

NODE_EXTRA_CA_CERTS appends to Node's trust bundle process-wide — the single most useful fix. Get the CA PEM from your IT team (or export it from the OS keychain).

export NODE_EXTRA_CA_CERTS=/etc/ssl/certs/corp-root-ca.pem
# persist in ~/.bashrc / ~/.zshrc; CI: set as a pipeline env var

2. Tell npm as well

npm reads its own config; point cafile at the same PEM.

npm config set cafile /etc/ssl/certs/corp-root-ca.pem
# verify:
npm config get cafile
npm ping

3. Do NOT disable verification

strict-ssl=false and NODE_TLS_REJECT_UNAUTHORIZED=0 make every connection blindly trust anyone — removing exactly the protection that flagged the interception. They also leak into production if set globally. Treat any tutorial recommending them as a red flag.

# audit for the dangerous settings:
npm config get strict-ssl        # should be true
printenv NODE_TLS_REJECT_UNAUTHORIZED   # should be empty

4. Fix containers and server-side chains

Install CA bundles in slim images; if one public site fails everywhere, test its chain — the server may be missing an intermediate.

# Debian-based image:
RUN apt-get update && apt-get install -y ca-certificates
# check a site's served chain:
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | grep -E 'depth|verify'

Frequently Asked Questions

Why do browsers work when Node fails on the same network?

Browsers trust the operating system's certificate store, where corporate IT installs the interception CA via device management. Node ships a fixed Mozilla-derived bundle and ignores the OS store — so the same connection verifies in Chrome and fails in Node until you add the CA via NODE_EXTRA_CA_CERTS.

Where do I get the corporate CA file?

Ask IT for the root CA in PEM format, or export it yourself: on macOS from Keychain Access (the proxy's root cert → export as .pem), on Windows via certmgr. You can also capture what the proxy serves with openssl s_client and take the top certificate of the chain — verify its subject matches your company's proxy vendor.

Is UNABLE_TO_VERIFY_LEAF_SIGNATURE the same problem?

Same family, different link: issuer-cert-locally means the chain's issuer is unknown; leaf-signature usually means the server sent an incomplete chain (missing intermediate). The CA-file fix helps the first; the second is fixed server-side, or by adding the intermediate to your bundle as a workaround.
