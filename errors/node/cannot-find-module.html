Node.js Cannot Find Module

Last updated: July 2, 2026

The crash "Error: Cannot find module 'x'" (code MODULE_NOT_FOUND) — Node's resolver could not locate a package or file your code requires or imports.

You might see this error as:

  • Error: Cannot find module
  • MODULE_NOT_FOUND
  • cannot find module 'express'
  • node cannot find module
  • require stack module not found

What Does This Error Mean?

Node resolves each require/import against node_modules directories and relative paths. MODULE_NOT_FOUND means that search came up empty. The message tells you which of the two families you are in: a bare name ('express') means the package is not installed where Node is looking; a path ('./utils/helpers') means the file is not there under that exact name — including letter case, which is the classic 'works on my Mac, crashes on the Linux server' failure, since macOS filesystems are case-insensitive and Linux is not.

Common Causes

  • Dependencies not installed — Fresh clone, CI job, or Docker image where npm install never ran (or ran in a different directory) — node_modules simply is not there.
  • Case mismatch in a path — require('./Utils/Helpers') finds utils/helpers.js on macOS/Windows but not on Linux. Deploy-only MODULE_NOT_FOUND on a relative path is this until proven otherwise.
  • Package's entry point does not exist — The message names a path inside node_modules: the package's main/exports field points at a dist/ file that needs a build step, or the install was corrupted.
  • Wrong working directory or misplaced node_modules — Running from a subdirectory, monorepo packages resolving against the wrong workspace, or a dependency used without being declared (relying on hoisting) that disappears when the tree changes.

How to Fix It

1. Install, or reinstall cleanly

First response for bare module names — and when the tree looks corrupted, remove and reinstall from the lockfile.

npm install
# clean reinstall, reproducible from the lockfile:
rm -rf node_modules
npm ci

2. Check the exact file name and case

Compare the required path with what is really on disk, character by character.

ls -la src/utils/
# git can carry a wrong-case file forever; fix the name git tracks:
git mv src/utils/helpers.js src/utils/Helpers.js.tmp
git mv src/utils/Helpers.js.tmp src/utils/helpers.js

3. Confirm the dependency is actually declared

If it works locally but dies elsewhere, it may be a phantom dependency — used but never added to package.json.

npm ls express
grep '"express"' package.json || npm install express

4. For paths inside node_modules, check the package's build

When the missing file is another package's dist output, reinstall that package; if you are the package author, ensure prepare/prepublishOnly builds it.

npm ls broken-package
npm install broken-package@latest --force
cat node_modules/broken-package/package.json | grep -E '"main"|"exports"'

Frequently Asked Questions

Why does this only happen in production/CI and not on my machine?

Three usual suspects: case-sensitive Linux filesystems exposing a wrong-case path, devDependencies missing because the install ran with NODE_ENV=production (or npm ci --omit=dev) while the code needs the package at runtime, and phantom dependencies that were hoisted locally but not in the fresh install.

What is the difference between this and ERR_MODULE_NOT_FOUND?

MODULE_NOT_FOUND comes from the CommonJS require() resolver; ERR_MODULE_NOT_FOUND from the ESM import resolver. The ESM one is stricter — relative imports need explicit file extensions ('./util.js', not './util'), which trips people migrating to ESM.

Does deleting package-lock.json help?

Rarely, and it costs you reproducible installs. Prefer 'rm -rf node_modules && npm ci' — it rebuilds from the lockfile exactly. Only regenerate the lockfile when it is genuinely inconsistent with package.json (npm will say so).

Related Errors

  • ERR_REQUIRE_ESM — requiring ESM-only packages.
