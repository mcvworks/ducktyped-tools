Maximum Call Stack Size Exceeded

Last updated: July 2, 2026

The crash 'RangeError: Maximum call stack size exceeded' — function calls nested deeper than the stack allows, almost always runaway recursion.

You might see this error as:

  • RangeError: Maximum call stack size exceeded
  • maximum call stack size exceeded
  • call stack exceeded node
  • infinite recursion error javascript

What Does This Error Mean?

Every function call pushes a frame onto the call stack; V8 caps that stack (roughly ten thousand frames, size-dependent). Exceeding it throws this RangeError. Unlike heap exhaustion, this is nearly always a logic bug: recursion without a reachable base case, two functions calling each other forever, a getter that reads itself, or deep recursion over data (tree traversal on a huge or cyclic structure). The repeating pattern in the stack trace is the diagnosis — the same function name(s) over and over.

Common Causes

  • Recursion without a reachable base case — The termination condition never becomes true for some input (off-by-one, unexpected empty value), so the function calls itself until the stack dies.
  • Accidental self-reference — A getter returning itself (get name() { return this.name; }), a wrapper calling the function it wraps by the same name, or an event handler re-emitting the event it handles.
  • Mutual recursion — A calls B calls A — visible as two names alternating in the stack trace. Often introduced by refactors that split one function into two.
  • Legitimately deep recursion over big or cyclic data — Tree/graph algorithms recursing per node blow the stack on deep structures — or loop forever on cycles the code did not guard against.

How to Fix It

1. Read the repeating frames

The loop is right there in the trace; log the arguments at the top of the recursing function to see why the base case never hits.

function walk(node, depth = 0) {
  if (depth > 1000) {           // temporary tripwire while debugging
    console.error('runaway at', JSON.stringify(node).slice(0, 120));
    throw new Error('recursion tripwire');
  }
  ...
  return walk(node.child, depth + 1);
}

2. Fix the base case (and validate inputs)

Make termination provable: handle empty/null/zero explicitly, and ensure each call strictly progresses toward it.

function sum(list) {
  if (list.length === 0) return 0;        // base case FIRST
  return list[0] + sum(list.slice(1));    // strictly smaller input
}

3. Convert deep recursion to iteration

An explicit stack turns unbounded call depth into bounded heap usage — the standard fix for tree walkers on real-world data.

function walkIterative(root) {
  const stack = [root];
  while (stack.length) {
    const node = stack.pop();
    visit(node);
    for (const child of node.children ?? []) stack.push(child);
  }
}

4. Guard against cycles in graph-shaped data

Track visited nodes so cyclic references terminate.

function walkGraph(node, seen = new Set()) {
  if (seen.has(node)) return;
  seen.add(node);
  for (const next of node.edges) walkGraph(next, seen);
}

Frequently Asked Questions

Can I just increase the stack size?

node --stack-size exists, but it treats the symptom: infinite recursion exhausts any size, and deep-but-finite recursion is more robustly fixed by iteration. Raising the stack is defensible only for a known-finite algorithm slightly over the default on trusted input.

Why does JSON.stringify throw this on my object?

If the object is cyclic, stringify usually throws 'Converting circular structure to JSON' (TypeError) instead — but custom toJSON methods or replacer functions that recurse can produce the stack error. Either way the fix is breaking the cycle or using a structured-clone/serializer that handles cycles.

Does async/await recursion also blow the stack?

Each await unwinds the stack before continuing, so truly asynchronous recursion (awaiting something that yields to the event loop) does not accumulate frames the same way — it can still loop forever, but as a hang or memory growth rather than this RangeError. Synchronous recursion inside async functions crashes identically.
