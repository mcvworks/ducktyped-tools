Cannot Use Import Statement Outside a Module

Last updated: July 2, 2026

The crash "SyntaxError: Cannot use import statement outside a module" — ES-module syntax ran in a CommonJS context, in Node, Jest, or a browser script tag.

You might see this error as:

  • SyntaxError: Cannot use import statement outside a module
  • cannot use import outside module
  • jest cannot use import statement
  • type module package.json
  • unexpected token import

What Does This Error Mean?

JavaScript has two module systems: CommonJS (require/module.exports — Node's historical default) and ES modules (import/export). This error means import syntax was parsed by an engine currently in CommonJS mode. Node decides mode per file: .mjs is always ESM, .cjs always CJS, and .js follows the nearest package.json 'type' field — no 'type': 'module' means CJS. The same message from a browser means a script tag without type="module"; from Jest, it means untransformed ESM (often in node_modules) hit Jest's CJS runtime.

Common Causes

  • package.json lacks "type": "module" — Your .js files use import/export, but Node treats them as CommonJS because nothing declared the package ESM.
  • Running TypeScript source directly — node src/index.ts (or misconfigured runners) hands raw TS with import statements to a CJS parser.
  • Jest meets untransformed ESM — Jest's default runtime is CJS; ESM-only dependencies (or your own ESM) reach it unconverted — the stack trace points into node_modules.
  • Browser script tag without type="module" — Classic scripts cannot use import; the identical message appears in the browser console.

How to Fix It

1. Declare the package as ESM (or use .mjs)

Pick a lane per package: add the type field for whole-project ESM, or rename individual files.

// package.json
{
  "type": "module"
}
// per-file alternative: rename entry.js -> entry.mjs
// keep a legacy CJS file working inside an ESM package: rename it .cjs

2. Run TypeScript through a runner or compile first

Use tsx (or ts-node with ESM support) in dev, and compiled output in production.

npm i -D tsx
npx tsx src/index.ts
# production:
npx tsc && node dist/index.js

3. Let Jest transform the offending ESM dependency

By default Jest ignores node_modules in transforms; whitelist the ESM package.

// jest.config.js
module.exports = {
  transformIgnorePatterns: [
    '/node_modules/(?!(ky|nanoid|other-esm-pkg)/)'
  ],
};

4. Fix the browser side

Module syntax needs a module script tag.

<script type="module" src="/js/app.js"></script>

Frequently Asked Questions

What exactly do .mjs and .cjs mean?

Explicit per-file mode markers that override the package.json 'type' field: .mjs is always parsed as an ES module, .cjs always as CommonJS. They are the escape hatch for mixing — an ESM project can keep one legacy .cjs config file, and a CJS project can have one .mjs script.

I switched to "type": "module" and now require is not defined — why?

The flip side: ESM files have no require, module, __dirname, or __filename. Convert requires to imports, and rebuild __dirname via 'import.meta.url' with fileURLToPath. Config files that must stay CJS (some tools) get renamed to .cjs.

Why does Jest hit this when my app runs fine?

Your app runs as ESM natively; Jest executes tests in a CommonJS runtime and transforms your code — but skips node_modules by default. An ESM-only dependency then reaches the CJS runtime raw. transformIgnorePatterns (or Jest's experimental ESM mode) closes the gap.
