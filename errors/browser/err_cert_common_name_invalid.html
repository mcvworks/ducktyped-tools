ERR_CERT_COMMON_NAME_INVALID

Last updated: March 8, 2026

This error means the SSL certificate does not match the domain you are visiting. The hostname in the certificate does not cover the address in your browser.

You might see this error as:

  • NET::ERR_CERT_COMMON_NAME_INVALID
  • ERR_CERT_COMMON_NAME_INVALID Chrome
  • Your connection is not private
  • SSL certificate name mismatch
  • Certificate common name invalid
  • Subject Alternative Name missing

What Does This Error Mean?

Every SSL certificate contains a list of hostnames it is valid for — either in the Common Name (CN) field or the Subject Alternative Names (SAN) extension. When your browser connects to a site, it checks that the server's certificate covers that exact hostname.

ERR_CERT_COMMON_NAME_INVALID appears when the certificate does not list the hostname you are connecting to. For example, a certificate for example.com will trigger this error if you visit www.example.com and the certificate does not also cover www.example.com.

Common Causes

  • www vs. non-www mismatch — certificate covers example.com but not www.example.com, or vice versa.
  • Wrong subdomain — accessing app.example.com with a certificate only covering example.com.
  • Wildcard certificate doesn't match — a *.example.com wildcard covers one subdomain level but not www.sub.example.com.
  • Self-signed certificate — development servers often use certificates for localhost or an internal IP.
  • CDN or reverse proxy misconfiguration — the proxy presents its own certificate which does not match your domain.
  • Expired certificate replaced incorrectly — a new certificate was installed that does not include all the same hostnames.

How to Fix It

For Site Owners

1. Reissue the Certificate With All Hostnames

When requesting a certificate, include all hostnames as Subject Alternative Names. For a typical site, include both example.com and www.example.com. Let's Encrypt allows multiple SANs at no cost.

2. Use a Wildcard Certificate

A wildcard certificate (*.example.com) covers all direct subdomains. If you serve content on multiple subdomains, this simplifies certificate management.

3. Verify Your Certificate

Use the SSL Checker to confirm which hostnames your current certificate covers and when it expires.

For Visitors

4. Check the URL

Confirm you are visiting the intended address. Phishing sites sometimes use certificates for a slightly different domain to appear legitimate.

5. Check Your Hosts File

If you have modified your hosts file to point a domain to a different IP, the server at that IP may present a certificate for a different hostname.

Frequently Asked Questions

What is a Subject Alternative Name (SAN)?

A SAN is an extension in an SSL certificate that lists additional hostnames the certificate is valid for. Modern browsers require hostnames to be listed as SANs — they no longer accept the Common Name field alone for hostname verification.

Does a wildcard certificate cover all subdomains?

A wildcard like *.example.com covers one subdomain level: www.example.com, api.example.com, etc. It does not cover example.com itself (without a SAN entry) or deeper subdomains like a.b.example.com.

My development server shows this error — is that normal?

Yes. Self-signed certificates on localhost or internal hostnames will always trigger this in browsers. You can safely proceed on internal development servers you trust. For production, use a valid certificate from a trusted CA.

Related Errors

  • SSL Certificate Expired — certificate has passed its validity date.
  • SSL Certificate Invalid — certificate failed validation for other reasons.
  • NET::ERR_CERT_AUTHORITY_INVALID — certificate issued by an untrusted CA.
  • ERR_SSL_VERSION_OR_CIPHER_MISMATCH — TLS version or cipher incompatibility.
