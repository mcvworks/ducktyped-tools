ERR_CONNECTION_REFUSED

Last updated: March 8, 2026

This error means the server actively rejected the connection attempt. Nothing is listening on the requested port, or a firewall is blocking access. Here is what causes it and how to fix it.

You might see this error as:

  • net::ERR_CONNECTION_REFUSED
  • ERR_CONNECTION_REFUSED Chrome
  • localhost refused to connect
  • This site can't be reached
  • Connection refused
  • 127.0.0.1 refused to connect
  • ECONNREFUSED

What Does This Error Mean?

When your browser tries to connect to a server, it initiates a TCP connection to the server's IP address on a specific port (usually port 80 for HTTP or 443 for HTTPS). ERR_CONNECTION_REFUSED means the server responded with a TCP RST (reset) packet immediately — it is not listening on that port, or a firewall has been configured to explicitly refuse connections rather than silently drop them.

This is different from a timeout (no response at all) and different from a connection reset after a connection has been established. A refusal happens before any data is exchanged.

Common Causes

  • Web server is down — the application (nginx, Apache, Node.js, etc.) has crashed or is not running.
  • Wrong port number — you are connecting to a port where nothing is listening. Common mistake with dev servers.
  • Firewall blocking the port — a server-side or network-level firewall is rejecting inbound connections on that port.
  • Service not started — common in local development when the development server has not been started yet.
  • Proxy misconfiguration — your browser or system proxy settings are pointing to an unreachable proxy server.
  • Server overloaded — in extreme cases, an overloaded server may refuse new connections to protect existing ones.
  • IP address blocked — the server may have blocked your IP address due to security rules or rate limiting.

How to Fix It

1. Check Whether the Site Is Down for Everyone

Use the HTTP Latency Checker to test whether the server is responding at all. If it times out or refuses from our side too, the server is down.

2. Verify the Port Number

If you are working with a local dev server or connecting to a custom port, confirm you are using the correct port. For example, a React dev server typically runs on port 3000, not 80.

Use the Port Scanner to check whether the expected port is open on the target host.

3. Check Proxy Settings

An incorrectly configured proxy causes this error for all sites. Check your browser's proxy settings:

  • Chrome/Edge: Settings → System → Open your computer's proxy settings
  • Windows: Settings → Network & Internet → Proxy → disable if not needed

4. For Local Development (localhost errors)

If you see this on localhost or 127.0.0.1, your development server is not running. Start the server and ensure it is listening on the port you are connecting to. Check the terminal output for the port number.

5. Check the Server Firewall

If you manage the server, verify that the firewall allows inbound traffic on the relevant port. On Linux with UFW:

sudo ufw status
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

6. Restart the Web Server

If you have server access, restart the web server process:

# nginx
sudo systemctl restart nginx

# Apache
sudo systemctl restart apache2

7. Disable Browser Proxy or VPN

If a VPN or proxy is active, it may be routing your requests to an unreachable endpoint. Disable it and retry.

  • HTTP Latency Checker — verify whether the server is responding at all.
  • DNS Record Checker — confirm the domain resolves to the correct IP address.

Frequently Asked Questions

Why does ERR_CONNECTION_REFUSED appear on localhost?

This is the most common scenario for developers. It means your local development server is not running, or it is running on a different port than the one you typed in the browser. Check your terminal for the server's actual port number.

Can a firewall cause ERR_CONNECTION_REFUSED?

Yes, but only if the firewall is configured to reject (actively deny) connections rather than drop (silently ignore) them. A dropping firewall causes a timeout, while a rejecting firewall causes a refused connection.

How is this different from ERR_CONNECTION_RESET?

A refused connection happens immediately during the TCP handshake — the server sends a RST before accepting the connection. A reset (ERR_CONNECTION_RESET) occurs after the connection was already established and the server (or something in between) forcibly closed it mid-session.

Related Errors

  • ERR_CONNECTION_RESET — connection established but then abruptly closed.
  • DNS_PROBE_FINISHED_NXDOMAIN — domain could not be resolved before a connection was even attempted.
  • 503 Service Unavailable — server is running but not able to handle requests.
