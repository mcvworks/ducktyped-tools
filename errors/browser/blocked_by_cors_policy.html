Blocked by CORS Policy

Last updated: July 3, 2026

This error appears in the browser console when your JavaScript tries to read a response from a different origin and the server did not grant permission with the right CORS headers. The full message is usually "Access to fetch at '…' from origin '…' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource." The key thing to understand: the request usually reaches the server and succeeds — the browser simply refuses to hand the response back to your code.

You might see this error as:

  • has been blocked by CORS policy
  • No 'Access-Control-Allow-Origin' header is present on the requested resource
  • Response to preflight request doesn't pass access control check
  • The 'Access-Control-Allow-Origin' header has a value that is not equal to the supplied origin
  • Request header field authorization is not allowed by Access-Control-Allow-Headers
  • net::ERR_FAILED

What Does This Error Mean?

Browsers enforce the same-origin policy: by default, JavaScript on one origin cannot read responses from another. An origin is the combination of scheme, host, and port — so https://app.example.com and https://api.example.com are different origins, and so are http://localhost:3000 and http://localhost:8080.

CORS (Cross-Origin Resource Sharing) is the mechanism a server uses to opt in to being read across origins. When your page makes a cross-origin request, the browser checks the response for an Access-Control-Allow-Origin header. If that header is missing, or its value does not cover your origin, the browser blocks your JavaScript from seeing the response and logs the CORS error — even though the server may have returned a normal 200 response. CORS is a browser protection, not a server-side rejection.

Common Causes

  • The server sends no Access-Control-Allow-Origin header at all — the default for most APIs, and the most common cause.
  • The header value does not match your origin — it allows a different domain, or omits the port, and is not a wildcard.
  • The OPTIONS preflight is not handled — requests with custom headers or methods like PUT/DELETE trigger a preflight that the server answers with an error or a redirect.
  • Credentials with a wildcard — the request sends cookies, but the server replies Access-Control-Allow-Origin: *, which browsers reject for credentialed requests.
  • A required header is not allowed — the request sends Authorization or a custom header that is missing from Access-Control-Allow-Headers.
  • A redirect on the request — the API redirects (for example HTTP to HTTPS), and the redirected response lacks CORS headers.

How to Fix It

1. Add Access-Control-Allow-Origin on the Server

The real fix lives on the server that receives the request (your API), not on the front end. Return the requesting origin — or a wildcard for public data. In Node/Express, the cors package handles this:

const cors = require('cors');

// Allow a specific origin (recommended)
app.use(cors({ origin: 'https://app.example.com' }));

// Or, for a public API with no cookies, allow any origin
app.use(cors());   // sends Access-Control-Allow-Origin: *

The equivalent raw header, if you set it by hand or in a reverse proxy like nginx:

add_header Access-Control-Allow-Origin "https://app.example.com" always;
add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE, OPTIONS" always;
add_header Access-Control-Allow-Headers "Content-Type, Authorization" always;

2. Handle the OPTIONS Preflight

For anything beyond a simple request, the browser first sends an OPTIONS preflight and expects a 2xx response carrying the allowed methods and headers. The cors middleware answers preflights automatically; by hand, make sure OPTIONS returns 204 and does not fall through to a 404 or 405:

app.options('/api/*', cors());   // respond to all preflight requests

3. Configure Credentials Correctly

If the request includes cookies or an Authorization header via credentials, a wildcard is not allowed. Echo the exact origin and add the credentials header on the server:

app.use(cors({
  origin: 'https://app.example.com',   // must be specific, NOT *
  credentials: true,                   // sends Access-Control-Allow-Credentials: true
}));

And set the matching option on the client:

fetch('https://api.example.com/data', { credentials: 'include' });

4. Use a Dev-Server Proxy Locally

During development you often cannot change the API. Instead, have your dev server proxy the request so the browser sees a same-origin call and CORS never applies. For Vite:

// vite.config.js
export default {
  server: {
    proxy: { '/api': 'https://api.example.com' }
  }
};

Now your code calls /api/data on your own origin, and the dev server forwards it server-to-server. Create React App (proxy in package.json) and Next.js rewrites do the same thing.

5. Verify the Response Headers

Confirm the server is really sending the header with the Security Headers Checker, or replay the exact request with the HTTP Request Builder and inspect what comes back. Avoid the temptation to route production traffic through a public CORS proxy or to launch the browser with web security disabled — both defeat a protection that exists to keep your users safe.

Related Tools

  • HTTP Request Builder — replay a request and see exactly which CORS headers come back.
  • URL Parser — break a URL into scheme, host, and port to confirm two origins really differ.

Frequently Asked Questions

Is a CORS error a client-side or server-side problem?

It is fixed on the server. The browser enforces CORS, but the fix is to make the server that receives the request return the correct Access-Control-Allow-Origin header. You cannot resolve a genuine CORS error purely from front-end JavaScript.

Why does the request work in Postman or curl but fail in the browser?

CORS is enforced only by web browsers, to protect logged-in users. Tools like curl and Postman do not apply the same-origin policy, so they receive the response normally. The server usually returns a valid response in the browser too — the browser just refuses to expose it to your JavaScript.

Can I fix it from my front-end code?

No. Changing your fetch options cannot add a header that only the server can send. If you do not control the API, route the request through your own backend or a dev-server proxy so the browser sees a same-origin request.

Is Access-Control-Allow-Origin: * safe?

A wildcard is fine for public APIs that return non-sensitive data and use no cookies. It cannot be combined with credentialed requests — for those, the server must echo the specific origin and send Access-Control-Allow-Credentials: true. Never use a wildcard on a private, authenticated endpoint.

Related Errors

  • 405 Method Not Allowed — a server that does not handle the OPTIONS preflight often returns this.
  • net::ERR_FAILED — CORS-blocked requests frequently surface under this generic failure.
  • 403 Forbidden — some servers reject a disallowed origin outright with a 403.
