Kubernetes CrashLoopBackOff

Last updated: March 8, 2026

Pod is crashing repeatedly and Kubernetes is backing off restarts

You might see this error as:

  • CrashLoopBackOff
  • Kubernetes CrashLoopBackOff
  • Back-off restarting failed container
  • Pod CrashLoopBackOff
  • kubectl pod crash loop

What Does This Error Mean?

CrashLoopBackOff means a Kubernetes pod's container starts, crashes, and keeps restarting in a loop. Kubernetes uses exponential backoff to delay restarts (10s, 20s, 40s, up to 5 minutes) to avoid overwhelming the system. The pod status shows CrashLoopBackOff during these backoff periods.

Common Causes

  • Application crashes on startup — The application inside the container exits with a non-zero exit code due to bugs, missing configuration, unhandled exceptions, or failed initialization.
  • Missing configuration or secrets — The pod references ConfigMaps, Secrets, or environment variables that do not exist or contain incorrect values, causing the application to fail on startup.
  • Failed health checks — Liveness probes fail repeatedly, causing Kubernetes to kill and restart the container. This can happen when the probe endpoint is wrong or the initial delay is too short.
  • Insufficient resources — The container's memory or CPU limits are too low, causing the application to be OOM-killed (Out of Memory) during startup.
  • Incorrect container command — The container's entrypoint or command is wrong, causing it to exit immediately. This includes typos in the command or referencing a binary that does not exist in the image.

How to Fix It

1. Check pod logs

View the logs from the crashing container to identify the error message or stack trace.

kubectl logs <pod-name>
# If the container has already restarted:
kubectl logs <pod-name> --previous

2. Describe the pod for events

Check the pod's events for Kubernetes-level errors like image pull failures, mounting issues, or OOM kills.

kubectl describe pod <pod-name>

3. Debug with an interactive shell

Override the container command to start a shell instead of the application, allowing you to investigate inside the container.

kubectl run debug --image=<your-image> --rm -it -- /bin/sh

4. Check resource limits

Verify that the container has enough memory and CPU allocated. OOM kills show as exit code 137.

kubectl get pod <pod-name> -o jsonpath='{.status.containerStatuses[0].lastState.terminated}'

Frequently Asked Questions

What is the backoff timing for CrashLoopBackOff?

Kubernetes uses exponential backoff: 10 seconds, 20 seconds, 40 seconds, 80 seconds, and so on, capping at 5 minutes. After the pod runs successfully for 10 minutes, the backoff timer resets.

How is CrashLoopBackOff different from ImagePullBackOff?

CrashLoopBackOff means the container image was pulled successfully but the application inside keeps crashing. ImagePullBackOff means Kubernetes cannot even download the container image.

Can I force restart a pod in CrashLoopBackOff?

You can delete the pod with 'kubectl delete pod <name>'. If it is managed by a Deployment, a new pod will be created. However, if the underlying issue is not fixed, the new pod will also enter CrashLoopBackOff.
